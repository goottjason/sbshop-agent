# sbshop-deploy — 푸시 = 배포

## 1. 배포 사실

- `main` 푸시 → `.github/workflows/deploy.yml`: 입력 검증 → 테스트(`tests.yml`)와 arm64 이미지 빌드(`images.yml` → `ghcr.io/goottjason/sbshop-agent-{api,frontend,scraper}:<커밋 SHA 12자>`)를 병렬로 → 둘 다 통과하면 서버가 저장소 폴더를 `git reset --hard <SHA>`로 맞추고 `ops/deploy.sh`가 이미지를 **pull만** 해 바뀐 서비스만 교체 → nginx reload → 헬스 점검 → 외부 HTTPS 헬스체크. 약 8분.
- 테스트가 실패하면 deploy job은 돌지 않는다.
- `.md`와 `docs/`만 바뀐 푸시는 워크플로가 돌지 않는다. **`.md`가 아닌 파일이 하나라도 있으면**(`.sql`·`.gitignore`·`.json` 포함) 워크플로가 돌고, 백엔드를 건드리지 않았어도 api가 교체돼 **약 50초** 끊길 수 있다.
- 배포는 한 번에 하나만 돈다. 뒤의 것은 기다린다.
- 도는 소싱처 배치가 있으면 최대 30분 기다리고, 넘으면 배포를 중단한다(종료코드 3). 배치 상태 조회가 실패하면 확인 없이 진행한다 — 그래서 §3-2.
- 자동 롤백: 교체 뒤 api 헬스(DB 포함)·nginx 안 라우팅(api·frontend)·scraper 헬스를 점검하고, 기동 실패·이미지 불일치·점검 실패면 이번에 교체한 서비스 전부를 역순으로 직전 이미지로 되돌려 재점검한다.
- 저장소는 공개다. 배포가 없는 푸시도 게시다.

## 2. 승인

- `main` 푸시는 **사용자의 승인 발화가 있은 뒤에만** 한다. 승인 요청과 푸시 명령을 같은 턴에 넣지 않는다. 이유: 전역 설정이 `git push`를 사전 허용해 둔 PC가 있어 하네스가 묻지 않을 수 있다 — 기계 가드가 없으니 이 규율이 유일한 관문이다.
- 승인 요청에 담는다: 올릴 커밋 목록(해시·제목), `.md`가 아닌 파일 여부(→ 워크플로·api 끊김), DDL 선행이 있으면 적용·확인을 마쳤는지, 로컬 미실행 게이트, 도는 배치·운영 작업의 상태, 되돌리는 방법.
- 승인은 그 커밋 목록에만 유효하다. 승인 뒤에 커밋이 더해지면 다시 받는다.
- `main`이 아닌 작업 브랜치의 푸시와 `tests.yml` 수동 실행은 승인 없이 한다 — 배포가 일어나지 않는다.
- `deploy.yml` 수동 실행(`rollback`·`image_tag`·`recreate`)은 매번 승인. `force`·`skip_tests`는 승인 요청에 사유를 적는다.
- `main`에 `--force`·`--no-verify`는 쓰지 않는다.

## 3. 푸시 전 점검

1. **상호 배제** — 서버 루프, 진행 중인 운영 쓰기, 방금 건 수동 트리거가 있으면 푸시하지 않는다. 이유: api 교체 때 도는 작업은 30초 뒤 강제 종료된다.
2. **소싱처 배치** — 세션이 직접 조회한다(SSH 읽기, `sbshop_ro`로 `select count(*) from sb_supplier_batch_run where state in ('RUNNING','PAUSING')`). 조회하지 못했으면 승인 요청에 "배치 상태 미확인"이라고 쓴다.
3. **DDL 선행** — 엔티티를 바꾼 커밋이 있으면 운영 적용·확인이 끝났는지(`sbshop-ops-write` §6).
4. **시점** — 주문 동기화(`OrderSyncScheduler`)는 KST 매시 :00·:30 이메일, :05·:35 쿠팡, :10·:40 카페24, :15·:45 스마트스토어, :20·:50 11번가, :25 대사로 돈다. 5분 간격이라 비는 시각은 없다.
5. **묶음** — 중대 등급이거나 DDL이 딸린 커밋은 다른 커밋과 묶지 않고 따로 배포한다. 이유: 실패했을 때 원인이 하나여야 한다.

## 4. 배포 확인 — 푸시하고 끝이 아니다

1. Actions 실행을 끝까지 본다: `gh run list --workflow deploy.yml --limit 3`, `gh run watch <실행 ID>`.
2. 성공이면 실행 중인 이미지의 커밋이 올린 SHA와 같은지 본다(SSH 읽기): `docker ps --filter name=projects-sbshop-api-1`, `docker inspect -f '{{index .Config.Labels "org.opencontainers.image.revision"}}' projects-sbshop-api-1`. 이미지가 같아 교체가 없었을 수 있으니 배포 로그의 "교체 대상" 줄도 본다.
3. 바꾼 기능을 라이브에서 확인한다(`sbshop-ops-write` §3). 헬스체크 통과는 기능 확인이 아니다.
4. 스케줄러가 쓰는 로직을 바꿨으면 다음 주기의 로그를 본다.
5. 여기까지 끝나야 원장 상태가 `종결`이다.

## 5. 실패 판단표

| 결과 | 서비스 | 할 일 |
|------|--------|------|
| tests 실패 | 영향 없음 | 고쳐서 다시 올린다(다시 승인) |
| 종료코드 3 (배치 30분 초과) | 영향 없음 | 배치가 끝난 뒤 Actions 재실행(승인) |
| 종료코드 7 (자동 롤백 성공) | 이전 버전으로 정상 | 원인을 찾는다 — 스키마 누락이 가장 흔하다. 고친 뒤 `image_tag`로 재배포할 수 있다 |
| 종료코드 8 (자동 롤백도 실패) | 내려갔을 수 있다 | 즉시 사용자에게 보고하고 수동 `rollback`. **사용자와 연락이 안 되면 직전 이미지로의 `rollback` 한 번은 승인된 것으로 보고** 실행한 뒤 즉시 보고한다 — 주문 동기화가 멈춘 채 기다리는 쪽이 더 위험하다 |
| 종료코드 5 (nginx reload 실패) | 새 컨테이너는 떠 있다 | 보고. nginx reload는 서버 쓰기라 승인 |
| 종료코드 4·6 | 자동 롤백을 거쳐 7 또는 8 | 위와 같음 |
| 외부 헬스체크 실패 | 불명 | SSH 읽기로 컨테이너·로그 확인 후 보고 |

## 6. 롤백

- Actions 수동 실행 입력: `rollback=sbshop-api`(직전 `prev-*` 태그로), `rollback_tag=<커밋 SHA 12자 | prev-YYYYMMDD-HHMMSS>`(레지스트리에서 받는다, 재빌드 없음, `rollback`과 함께만), `image_tag=<SHA 12자>`(이미 빌드된 태그를 테스트·빌드 없이 배포), `recreate=<서비스>`(이미지가 같아도 다시 만든다), `skip_tests`, `force`.
- 배포는 됐는데 기능이 깨졌을 때, 고객에게 영향이 가고 있으면(주문 처리, 마켓에 잘못 쓰는 중) **롤백이 먼저**다 — 재빌드가 없어 약 50초. 영향이 화면 표시뿐이면 고쳐서 올린다.
- 롤백이 안전한 이유는 배포 전 DDL이 추가형뿐이라는 규칙이다. 이 규칙이 깨지면 롤백도 깨진다.
- 이미 잘못 쓰인 데이터는 롤백으로 돌아오지 않는다 — 코드를 되돌린 뒤 `sbshop-ops-write` 절차로 바로잡는다.

## 7. 하지 않는 것

- 서버에서 `docker compose build`·`up`을 직접 돌리지 않는다. 이유: 배포 잠금·이미지 지문·롤백용 태그를 건너뛰어, 다음 배포가 변경을 잘못 판단하고 되돌릴 이미지가 남지 않는다.
- api를 둘 띄우지 않는다. 스케줄러 26개가 도는 단일 JVM이라 둘이면 마켓 쓰기가 두 번 나간다.
- 배포 체계(`ops/`·`.github/`)를 고치는 것은 업무 범위 밖이다. 구멍을 보면 보고한다.
