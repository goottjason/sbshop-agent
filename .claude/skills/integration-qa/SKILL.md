# integration-qa — 검증

각각 올바른 두 컴포넌트가 연결 지점에서 어긋나는 것이 이 코드베이스 런타임 오류의 주원인이다. 그래서 존재 확인이 아니라 **경계면 교차 비교**로 검증한다.

## 절차

1. **결함 해소** — 인계서(`_workspace/fixes/{ID}_fix.md`)의 Red 테스트를 직접 실행해 Green인지 본다. 인계서의 주장을 그대로 믿지 않는다.
2. **회귀** — `.github/workflows/tests.yml`에서 바뀐 영역 job의 `run` 줄을 그 순서대로 실행한다(명령의 원본은 CI 파일이다).
3. **경계면** — 아래 표에서 수정이 걸친 경계면만, 양쪽 코드를 같이 열어 대조한다.
4. **판정서** — `_workspace/verify/{ID}_verdict.md`(양식: `sbshop-change/references/handoff.md` §3).

## 경계면 체크리스트

| 경계면 | 생산자 | 소비자 | 확인 |
|--------|--------|--------|------|
| API ↔ 프런트 | `backend/api/.../dto/` 응답 DTO | `frontend/src/api/*.ts` 타입·unwrap | 필드명, 래핑(프런트 `PageResponse<T>`의 `content`처럼 프런트가 기대하는 모양과 실제 응답이 같은가 — 백엔드에는 그 이름의 타입이 없다), null 처리 |
| 스케줄러 ↔ 서비스 | `@Scheduled` 메서드(`worker/.../scheduler/`, core의 두 Worker) | 부르는 서비스의 쓰기 로직 | 이 변경으로 스케줄러가 다음 주기에 마켓·DB에 **무엇을 쓰게 되는가** |
| 운영 스키마 ↔ 엔티티 | `backend/docs/ddl/`의 DDL 파일 | `core/.../domain/` `@Entity`·`@Embeddable` | 엔티티 변경에 맞는 DDL 파일이 같은 커밋에 있는가. 있으면 판정서에 "배포 전 운영 DDL 적용 필요"를 조건으로 적는다 |
| 포트 ↔ 어댑터 | core의 port 인터페이스 | infrastructure 구현체 | 구현이 정확히 1벌인가 |
| 설정 ↔ 빈 | `@Configuration` | 주입 지점(`@Qualifier`, executor 이름) | `@Bean` 누락·모듈 간 중복·이름 충돌 |
| 프런트 라우트 ↔ 링크 | `frontend/src/App.tsx` 라우트 | `frontend/src/layouts/MainLayout.tsx` nav·페이지 내 이동 | base path `/sbshop-agent` 일관성 |

## 운영 쓰기 도구 체크리스트

운영에 쓰는 코드(내부 엔드포인트·스크립트)는 중대 등급이고, 검증자 PASS 없이 운영에서 실행하지 않는다. 이유: 검증자가 최근 잡은 결함 셋 가운데 둘(D-349·D-361)이 운영 쓰기 가드의 결함이었다. 해당 없는 항목은 "해당 없음 — 이유"로 적는다.

- dry-run이 정말로 쓰기를 건너뛰는가(조회만 하는가) · 건수 상한·throttle이 실효인가
- 대상을 고르는 쿼리가 계획서의 기준과 같은가 · 제외 가드(진행 중 주문·클레임)가 실효인가
- 다른 쓰기 경로(스케줄러·배치)가 같은 대상에 쓰지 못하게 막혔는가 · 회차 도중의 취소·중단이 반영되는가 (둘 다 D-361 1차 반려 사유)
- 쓰기 응답과 반영 확인이 분리돼 있는가(D-345·D-346) · 항목 단위로 실패가 격리되는가
- 다시 실행해도 안전한가(멱등) · 의존 순서가 코드로 강제되는가(D-361: 카페24 삭제는 ESM 부재 확인 뒤에만)
- 일회성 SQL도 W3·대량이면 SQL·대상 쿼리·백업 문을 읽어 계획서와 맞는지 본다.

## 판정

- **PASS** — 결함 해소 + 회귀 통과 + 해당 경계면 불일치 없음.
- **부분** — 실행 검증은 통과했으나 정적 대조에서 이슈, 또는 환경 제약으로 일부 미검증. 근거를 붙여 주 세션 판단으로 넘긴다.
- **FAIL** — Red가 여전히 실패, 회귀 발생, 또는 경계면 불일치 확인. 파일:줄과 기대·실제 동작을 판정서에 적는다.
- 판정을 후하게 주지 않는다 — 여기서 새는 결함은 커밋 게이트를 그대로 통과한다. 근거가 상충하거나 불확실하면 PASS가 아니라 `부분`이다.

## 환경 한계 (침묵 생략 금지)

- 실행할 수 없으면 정적 대조로 할 수 있는 만큼 하고 미검증 항목을 판정서에 적는다.
- H2 테스트는 PostgreSQL(JSONB·DB 함수·쿼리 계획) 동작을 보증하지 않는다 — 해당 경로는 "H2 한계로 미검증", testcontainers 테스트를 로컬에서 못 돌렸으면 "로컬 미실행 — CI로 대신"을 적는다.
- 운영 서버·DB·마켓에 접근하지 않는다(읽기 포함). 라이브 대사가 필요하면 판정서에 적어 주 세션에 넘긴다 — 운영 접근은 주 세션의 일이다.
