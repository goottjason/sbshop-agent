# sbshop-ops-write — 운영 작업

**운영에 닿는 것은 주 세션뿐이다. 하위 에이전트는 읽기도 하지 않는다.** 이유: 하위 에이전트는 사용자의 승인 대화를 보지 못하고, 주 세션은 하위 에이전트가 무엇을 실행하는지 지켜볼 수 없다.

## 1. 분류

**불가역** = 실행한 뒤 우리 손만으로 실행 전 상태를 복원할 수 없는 쓰기. 하나라도 걸리면 불가역이다: ① 실행 전 값을 보관하고 있지 않다 ② 그 값을 다시 써 넣는 경로가 없거나 시험된 적이 없다 ③ 원복 전에 제3자(고객·마켓)가 그 변화를 보고 움직일 수 있다. **확신이 서지 않으면 불가역이다.**

| 등급 | 무엇 | 예 |
|------|------|-----|
| R 읽기 | 상태를 바꾸지 않는 조회 | 운영 DB `SELECT`, 마켓 조회 API, `docker ps`·`docker logs`, Actions 로그 |
| W1 가역 | 백업으로 원복할 수 있고 제3자가 보기 전에 되돌릴 수 있는 소량 쓰기 | 쓰기 도구로 한 정정, 추가형 DDL, 함수 속성 변경, 정기 작업의 수동 트리거, Actions `rollback`·`recreate` |
| W2 마켓 가역 | 같은 API로 원래 값을 다시 쓸 수 있는 마켓 쓰기 | 가격 **인상**, 재고, 표시 필드, 판매중지(재개 가능) |
| W3 불가역 | 아래 목록 | |
| 대량 | 마켓 한 작업 **20건 초과**, DB **200행 초과 또는 한 테이블의 5% 초과**. 등급과 무관하게 W3 절차 | |

W3: 마켓 상품·리스팅 삭제 · 마켓 심사 제출(쿠팡 판매요청·승인요청 — 제출 뒤 못 바꾸는 필드가 있다) · 주문 상태를 바꾸는 쓰기(발주확인·송장 전송·취소·반품 승인) · 가격을 **내리는** 쓰기 · 파괴형 DDL(`DROP`·`TRUNCATE`·컬럼 삭제·타입 변경·`NOT NULL` 추가·이름 변경) · 백업 없는 `UPDATE`·`DELETE`, 하드 삭제 · 백업 테이블 삭제 · 고객 통지(메일·알림)를 일으키는 것.

틀리기 쉬운 곳:
- `/internal/*`는 이름으로 분류하지 않는다. 마켓을 조회해 DB를 고치는 것이 있다 — 처음 쓰는 엔드포인트는 코드를 읽어 부작용을 확인한 뒤 분류한다.
- 정기 작업의 수동 트리거는 W1이다(스케줄러와 결과 집합이 같다). 단 이메일 수집은 송장을 마켓 배송 처리로 넘긴다 — 사용자가 지시했을 때만: `docker exec projects-sbshop-api-1 curl -s -X POST localhost:8080/internal/email/fetch`.
- 소프트 삭제는 행 단위로는 W1이지만 건수로 본다(D-362는 1,571행 소프트 삭제 뒤에 났다).
- 스케줄러가 쓰는 로직을 바꾸는 배포는 다음 주기에 dry-run 없이 실행되는 운영 쓰기다(`sbshop-change` 등급 절).

## 2. 승인

| 행위 | 승인 |
|------|------|
| R 읽기, 서버 SSH 읽기 | 불요 |
| W1·W2, 서버 SSH 쓰기(파일 생성·스크립트 실행·컨테이너 조작) | 매번, 실행 계획서를 보여 준 뒤 |
| W3·대량 | 매번 두 번 — 파일럿 승인 → 본 실행 승인. 대상 기준은 사용자가 직접 확정 |
| 정기 작업의 수동 트리거 | 사용자가 그 실행을 지시했을 때(지시가 곧 승인) |

승인의 요건 — 이유: 승인 표만으로는 "승인받은 것 = 실행한 것"이 보장되지 않는다.
1. 요청에 담는다: 무엇을, 몇 건, 어떤 기준으로 고른 대상에, 되돌리는 방법(또는 "되돌릴 수 없음"), 실제로 실행할 명령.
2. 승인은 그 요청에만 유효하다. 대상·건수·명령이 달라지면 다시 받는다.
3. 앞선 승인이나 "진행해" 같은 일반 승인을 W3에 끌어다 쓰지 않는다.
4. 세션이 바뀌면 승인도 끝난다. STATUS에 "승인됨"이라고 있어도 다시 확인한다.
5. 세션이 범위를 넓히지 않는다. "이 20개"를 승인받고 나머지를 이어서 하지 않는다.
6. 승인을 기다리는 동안 승인이 필요 없는 일은 계속한다.

## 3. 읽기 (R)

- 운영 DB 조회는 읽기 전용 역할로: `docker exec projects-postgres-1 psql -U sbshop_ro -d sbshop`. 이유: 관리 계정 `goottjason`은 superuser라 오타 하나가 쓰기가 된다. 이 역할은 `statement_timeout` 60초다 — 무거운 조회에는 `LIMIT`을 건다.
- 원격 heredoc 안의 `docker exec -i … psql -c …`는 heredoc의 나머지를 먹는다 — `-c` 호출에 `</dev/null`을 붙인다.
- 조회 결과의 고객 정보를 저장소·원장·보고에 옮기지 않는다. 원시 출력은 `_workspace/ops/`(gitignore)에만, 사례는 주문 id로.
- 라이브 검증의 표준: "화면이 받은 API 응답"과 "운영 DB 정답 쿼리"를 맞춘다.
- api 헬스(8080은 호스트에 노출돼 있지 않다): `docker exec projects-sbshop-api-1 curl -s localhost:8080/internal/health`.

## 4. 쓰기 절차 — 순서를 건너뛰지 않는다

1. **분류·대상 확정** — §1로 등급을 정하고, 읽기만으로 대상 집합(고르는 쿼리·건수·표본)을 확정한다.
2. **간섭 확인** — 도는 소싱처 배치(`sb_supplier_batch_run`의 `state IN ('RUNNING','PAUSING')`), 진행 중인 배포, 서버에서 도는 루프, 대상에 걸린 진행 중 주문·클레임. 이유: 다른 쓰기 경로가 같은 대상에 쓰면 결과를 믿을 수 없다(D-361).
3. **의존 순서** — 지우거나 끊는 작업은 무엇이 이것에 매달려 있는지 먼저 본다. D-358: 카페24 상품이 먼저 지워져 G마켓 리스팅이 판매중인 채 끊겼다.
4. **실행 계획서** — 목적·근거(결함 ID, 사용자 지시) / 등급과 이유 / 대상 기준(WHERE)과 예상 건수 / 제외 기준 / 백업 / 그대로 실행할 명령 / 단계 / 쓰기 뒤 재조회와 기대 값 / 원복 절차 / 중단 조건 / 쓰기 뒤 확인 범위(§7). W3·대량은 `docs/normalize/plans/`에 설계서로 쓰고, 그 설계는 페이블 승급 대상이다.
5. **dry-run** — 도구가 지원하면 반드시 먼저. **건수가 예상과 다르면 멈춘다** — 대상 기준을 잘못 이해한 것이다. dry-run이 없는 마켓 쓰기는 1건 실행이 대신한다(W3이면 그 1건도 승인 범위 안).
6. **백업** — DB 정정은 쓰기 도구가 `bak_d{번호}_…`를 만든다(§5). 마켓 W2는 쓰기 전 현재 값을 조회해 `_workspace/ops/`에. 마켓 W3은 백업이 불가능하다 — 계획서에 "없음". 남은 백업 테이블은 STATUS에 이름·만든 날·지울 조건과 함께 적는다.
7. **단계 실행** — 1~2건 → 재조회 → 20건 이하 → 재조회. W3·대량은 여기까지가 파일럿이고 본 실행 승인을 따로 받는다. 본 실행은 회차 단위(마켓은 회차당 100건 이하, 마켓별 호출 간격 — 네이버 1,200ms 이상). 승인이 덮는 건수는 계획서의 건수이고 넘으면 멈춘다. 중단 기본값: 연속 3건 실패 또는 회차 실패율 10% 초과(계획서에서 바꿀 수는 있어도 없앨 수는 없다). 항목 하나의 오류가 전체를 멈추거나 실패로 만들지 않게 한다.
8. **재조회 확인** — 쓰기 요청의 성공 응답을 반영으로 치지 않는다. 같은 계정·같은 경로의 재조회로 확인한 것만 완료다. 마켓 반영은 늦을 수 있어 간격을 두고 여러 번 본다(D-346: 1.5초 간격 5회). 묶음 응답은 항목별 결과를 본다(D-345). "0건 처리 성공"은 확인할 대상이다(D-348). 확인 안 된 항목은 "미확인"으로 남긴다.
9. **기록** — 원장 레코드의 "운영 조치" 줄: 일시 · 대상 기준 · 건수 · 백업 위치 · 재조회 결과 · 잔여. 고객 정보는 옮기지 않는다.

## 5. 운영 DB 데이터 정정 — 쓰기 도구로만

데이터 정정(UPDATE·DELETE·INSERT)은 `psql`에 직접 치지 않고 서버의 `~/ops-write/sbshop_db_write.py`로만 한다. 이유: 승인은 승인받은 SQL의 오타나 잘못 잡은 WHERE를 막지 못한다 — 도구가 한 트랜잭션·백업 테이블·예상 건수 대조·쓰기 전 덤프를 강제한다. 작업 파일 형식과 되돌리기는 `tools/dbwrite/README.md`.

1. 작업 파일(TOML)을 서버 `~/ops-write/jobs/`에 쓴다. `title`·주석에 개인정보를 쓰지 않는다.
2. `python3 -I ~/ops-write/sbshop_db_write.py check JOB` — 조립된 SQL과 해시 앞 12자. **이 출력으로 승인을 받는다**(승인 대상 = 그 해시의 파일).
3. `python3 -I ~/ops-write/sbshop_db_write.py dry-run JOB` — 단계별 `rows`가 예상과 같은지, `bulk` 표시를 본다.
4. `~/ops-backup/sbshop-db-backup.sh pre` — 쓰기 직전 전체 덤프. `~/ops-backup/sbshop-db-backup.log`의 `OK kind=pre` 줄을 확인하고 30분 안에 apply한다.
5. `python3 -I ~/ops-write/sbshop_db_write.py apply JOB --confirm <해시12> [--bulk]` — 결과의 `committed=`를 본다. `unknown`이면 2분 뒤 백업 테이블과 대상 행을 직접 조회한다.
6. 재조회 → 원장 기록(작업 해시, 백업 테이블, 덤프 파일명, 재조회 결과).

도구 파일을 고치면 해시가 바뀐다 — 단위 시험, 서버 임시 DB 통합 시험, 재설치, 해시 대조를 다시 한다(절차는 원장 D-364). 이유: 서버 설치본이 시험한 코드와 같다는 증거가 해시뿐이다.

## 6. DDL — 배포보다 먼저, 추가형만

DDL은 쓰기 도구의 대상이 아니다. 운영 DB가 스키마의 단일 원본이고 운영은 `ddl-auto=validate`다.

1. 엔티티(또는 DB 함수·인덱스)를 바꾸는 커밋은 같은 커밋에 `backend/docs/ddl/YYYY-MM-DD-{내용}.sql`을 멱등 문(`IF NOT EXISTS`)으로 넣는다.
2. 순서: DDL 파일 → 검증자의 엔티티 ↔ DDL 대조 → 사용자 승인(DDL 적용과 푸시를 한 요청에, 항목은 나눠서) → `pre` 덤프·`OK kind=pre` 확인 → **세션이 운영에 적용** → `\d`로 재조회 → 푸시 → 배포 확인. 이유: D-361 첫 배포는 테이블이 없어 기동에 실패해 자동 롤백됐다.
3. 배포 전 DDL은 추가형만 — 컬럼·테이블·인덱스 추가, nullable 또는 기본값 있는 컬럼. 이유: 적용 시점에는 옛 코드가 돌고, 배포가 실패해 롤백되면 옛 코드가 새 스키마 위에서 다시 돈다.
4. 파괴형 DDL은 그것을 쓰지 않는 코드가 배포된 뒤 별도 작업(W3)으로 한다.
5. 소유자를 확인한다 — 기존 테이블의 소유자가 관리 계정이면 앱 계정으로 컬럼을 못 더한다(D-349). 새 테이블은 앱 계정(`sbshop`) 소유로 만든다.
6. 큰 테이블의 인덱스는 `CREATE INDEX CONCURRENTLY`, `lock_timeout`을 건다.
7. 테스트는 엔티티로 스키마를 새로 만들어 이 드리프트를 잡지 못한다 — 이 절차가 보증한다.

## 7. 대량 쓰기 뒤 확인

D-362: 맞게 쓴 1,571행이 통계를 바꿔 쿼리 계획이 병렬로 넘어갔고, 잠복해 있던 결함(`PARALLEL SAFE` 함수)이 상품 목록을 깨뜨렸다. 쓴 것만 재조회해서는 보이지 않고, 파일럿(20건)은 통계를 바꾸지 않아 잡지 못한다. 대량 쓰기 뒤:

1. 바꾼 테이블에 `ANALYZE` — 계획이 바뀐다면 지켜보는 지금 바뀌게.
2. 그 테이블을 읽는 화면의 API를 실제로 부른다(최소: 상품 목록, 주문 그리드, 대시보드 summary). HTTP 200이고 데이터가 오는지.
3. 쓰기 직후부터 api 로그의 ERROR·SQLState를 본다.
4. 주문 동기화 한 주기(30분) 뒤 스케줄러 로그에 새 오류가 없는지 본다.
5. 다른 쓰기 경로(소싱처 배치, 가격·재고 동기화)가 방금 쓴 것을 되돌리거나 다시 쓰지 않는지 본다.
6. 한 테이블의 5%를 넘게 바꾸면 계획서에 쓰기 뒤 상태 분포를 적고, 주요 쿼리를 `EXPLAIN`으로 전후 비교한다.

2~4의 결과를 원장 "운영 조치" 줄에 적는다. 이 확인이 끝나기 전에는 완료로 보고하지 않는다.

## 8. 서버에서 도는 작업 · 판매자센터

- 스크립트·로그는 서버 저장소 폴더(`~/projects/sbshop-agent`) 밖에 둔다. 배포가 그 폴더를 `git reset --hard`로 맞춰 추적 파일의 수정이 사라진다. 서버에서 추적 파일을 고치지 않는다.
- 세션이 끝나도 도는 루프는 계획서에 중단 방법·회차 상한·로그 위치를 적고 STATUS에 올린다. 상한 없는 루프는 만들지 않는다. 루프가 도는 동안 푸시하지 않는다.
- 묶음 전체가 낙관락 충돌로 거부되면 더 작은 단위로 나눠 다시 넣는다(D-361: 20개 단위).
- API가 없어 브라우저로 하는 판매자센터 쓰기도 같은 절차다. 화면에서 고른 대상이 계획서와 같은지 실행 전에 개수로 맞추고, 조작 뒤 API 재조회로 확인한다. 조작 도구가 없으면 대상 목록을 만들어 사용자에게 넘긴다.

## 9. 비밀과 접근

1. 추적 파일에 자격증명(비밀번호·토큰·키·접속 문자열)을 두지 않는다 — 편집기 설정과 일회성 스크립트도. 이유: 저장소는 공개이고, 자격증명은 바로 그런 편의 파일로 들어왔다.
2. 이미 올라간 비밀은 교체가 먼저, 파일 정리는 그다음이다. 이력은 다시 쓰지 않는다 — 지워도 이력에 남는다.
3. 비밀을 보면 값을 어디에도 옮겨 적지 않고 위치만 사용자에게 알린다. 계정을 바꾸는 것은 사용자다.
4. SSH 키 파일은 읽지도, 출력하지도, 커밋하지도 않는다. 명령에 경로로만 쓴다.
5. 서버 `.env`의 내용을 출력하지 않는다. 키 이름이 있는지만 본다. 고치는 것은 사용자다.
6. 운영 데이터·비밀을 외부 서비스에 보내지 않는다. 토큰·API 키를 로그·보고·원장에 쓰지 않는다.
