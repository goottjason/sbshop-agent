# 인계 양식

작업을 다른 세션·검증자에게 넘길 때 쓰는 세 가지 양식이다. 받는 쪽은 여기 적힌 것만 가지고 시작하므로, 해당 없는 항목은 지우지 말고 "없음"이라고 적는다. 이유: 빈칸은 "확인했다"로도 "잊었다"로도 읽힌다.

## 1. 설계서 — 설계 세션(페이블) → 구현 세션(오푸스)

- 위치: `docs/normalize/plans/{결함ID}_{제목}.md`. 추적 파일이라 공개된다 — 개인정보·비밀을 쓰지 않는다.
- 쓰는 때: `sbshop-change` "설계서와 페이블 승급" 절. 경량·표준의 한 세션 작업에는 쓰지 않는다 — 원장 레코드로 충분하다.
- 필수 항목:
  1. 목적과 배경 — 누가 무엇을 언제 요청했나.
  2. 확인한 사실과 근거(파일:줄, 실행한 쿼리·명령). 확인하지 못한 것은 "미확인"으로 따로.
  3. 고정 결정(구현자가 바꾸면 안 되는 것)과 이유. 위임(구현자가 정해도 되는 것).
  4. 구현 단계 — 단계마다 `[단계] → 검증: [확인 방법]`.
  5. 리스크 등급과 운영 쓰기 유무. 운영 쓰기가 있으면 `sbshop-ops-write`의 실행 계획서 항목.
  6. 멈춤 조건 — 무엇이 보이면 구현을 멈추고 보고하는가.
  7. 완료 기준.
- 구현 중 고정 결정과 다르게 가야 하거나 "확인한 사실"이 틀렸으면 **고쳐 쓰지 말고 멈춰서 보고한다.** 이유: 틀린 사실 위에 내린 결정은 구현 세션이 혼자 고쳐도 설계 전체가 맞는지 알 수 없다. 위임 범위 안의 차이는 진행하고 인계서·보고에 적는다.

## 2. 인계서 — 수정한 세션 → 검증자

- 위치: `_workspace/fixes/{ID}_fix.md` (gitignore — 휘발).
- 필수 항목:
  1. ID, 한 줄 요약, 등급.
  2. 원인 — 확인/추정을 구분.
  3. 변경 파일 목록. 변경은 스테이징돼 있다 — `git diff HEAD`로 본다.
  4. Red 테스트 위치와 **Red였을 때의 실패 메시지**. 테스트로 재현이 안 되는 유형이면 성공 기준으로 삼은 검증 명령.
  5. 실행한 게이트 명령과 결과. **로컬에서 못 돌린 게이트와 그 이유.**
  6. 경계면을 바꿨으면 반대편 영향(프런트↔백엔드, 스케줄러↔서비스, 엔티티↔운영 스키마).
  7. 운영에 필요한 것 — DDL 문, 배포 선행 조건, 운영 쓰기 계획.
  8. 막힌 지점·못 한 것·의심 가는 곳.
- 이유: 검증자는 독립된 컨텍스트에서 시작한다. 5·6·8이 빠지면 수정자가 이미 의심한 곳을 검증자가 다시 찾거나 놓친다.
- 경량에서 검증자를 부르지 않으면 파일을 만들지 않고 1~5를 보고에 적는다.

## 3. 판정서 — 검증자 → 주 세션

- 위치: `_workspace/verify/{ID}_verdict.md` (gitignore — 휘발).
- 필수 항목: 판정(PASS·부분·FAIL), 직접 실행한 명령과 결과 요지, 발견 사항(파일:줄, 기대 동작·실제 동작), 미검증 항목과 이유.
- 주 세션은 판정 요지(판정, 반려 사유, 미검증 항목)를 원장 레코드의 "검증" 줄에 옮긴다. 이유: `_workspace/`는 다른 PC로 넘어가지 않는다 — 전 담당자의 판정서는 남아 있지 않다.
