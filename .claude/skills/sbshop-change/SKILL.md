# sbshop-change — 코드 변경 절차

흐름: 등급 판정 → (설계서) → 수정(TDD) → 인계·검증 → 게이트 → 커밋 → 기록. **판정과 커밋은 주 세션이 한다.** 이유: 하위 에이전트는 사용자의 승인 대화를 보지 못한다.

## 시작

- `docs/normalize/STATUS.md`를 먼저 읽고, 진행 중·배포 대기인 작업이 있으면 그것부터 잇는다. 원장은 ID로 찾아 해당 레코드만 읽는다. 이유: 원장은 6천 줄이 넘고, 휘발 산출물(`_workspace/`)은 다른 PC로 넘어오지 않는다.
- 원인이 확정되지 않은 결함은 `defect-triage`로 먼저 진단한다.

## 등급 판정

| 등급 | 조건 | 게이트 |
|------|------|--------|
| 경량 | 파일 하나, 그리고 바뀌는 것이 표시 문구·라벨·주석·테스트·문서뿐. 마켓 쓰기·DB 스키마·스케줄러·금액 계산에 닿지 않는다 | 해당 영역 게이트. 검증자는 선택 |
| 표준 | 기능 수정, 여러 파일. 중대 조건에 닿지 않는다 | 게이트 + 검증자 PASS |
| 중대 | 하나라도: ① 마켓에 쓰는 코드 경로(클라이언트·어댑터의 쓰기, 쓰기를 막는 가드) ② 스케줄러의 추가·주기·대상 변경, 스케줄러가 부르는 쓰기 로직 ③ 엔티티·스키마 ④ 가격 산정에서 마켓 반영까지의 경로 ⑤ 운영 쓰기 도구(내부 엔드포인트·스크립트) ⑥ 인증·권한 | 게이트 + 검증자 PASS + **커밋 전 사용자 승인** |

- 애매하면 높은 쪽이다. 경량 조건에 조금이라도 안 맞으면 표준이다. 이유: 검증자가 잡은 결함은 모두 표준·중대에서 나왔고, 경량을 좁게 잡아야 검증자를 빼도 안전하다.
- 대시보드 KPI처럼 금액을 다뤄도 마켓에 쓰지 않는 표시용 집계는 표준이다.
- **스케줄러가 쓰는 로직의 변경은 중대다.** 배포되면 다음 주기에 스케줄러가 dry-run·건수 상한 없이 마켓·DB에 쓴다. 승인 요청에 "다음 주기에 무엇을 몇 건 쓰게 되는지"를 운영 DB 읽기로 추정해 적고, 예상보다 많으면 멈춘다. 스케줄러는 `worker/.../scheduler/`와 core(`ProductContentWorker`·`ProductSourceWorker`)에 있다.

## 설계서와 페이블 승급

- 중대 등급, 한 세션에 안 끝나는 작업, 불가역·대량 운영 쓰기가 있는 작업은 구현 전에 설계서를 쓴다 — 양식은 `references/handoff.md` §1.
- `페이블 필요: 예`의 기준(하나라도): ① 불가역·대량 운영 쓰기의 설계(대상 기준·가드·단계) ② 여러 기능이 기대는 상태 모델·스키마의 변경 ③ 마켓에 새 종류의 쓰기를 여는 변경 ④ 원인을 모르는 P0·P1에서 수정이 두 번 실패 ⑤ 고정 결정을 바꿔야 할 때 ⑥ 규율 자체의 변경. 그 밖(대조·검색·문구·구현·실행 검증)은 `아니오`. 이유: 틀리면 이후를 다시 해야 하거나 운영 사고로 이어지는 결정만 상위 모델에 맡긴다.

## 수정 사이클

일반 원칙은 `references/tdd-doctrine.md`·`references/dev-rules.md`이고, 이 절은 그것을 이 저장소에 적용하는 방법이다.

1. **Red** — 결함이 속한 모듈의 테스트 폴더에 동작 설명형 이름으로 재현 테스트를 쓰고, 실행해 **실패를 눈으로 확인한다.** 이유: 실패를 본 적 없는 테스트는 결함을 재현한다는 증거가 아니다.
   - Red가 통과하면 고치지 않는다. 재현 방법이 틀렸거나 이미 고쳐진 것이다 — 원장에 적고 다시 진단한다.
2. **Green** — 테스트를 통과시키는 최소 변경만. 인접 코드는 개선하지 않는다. 이유: 섞인 변경은 검증 범위를 흐린다.
3. **Refactor** — 통과 상태에서만, 한 번에 하나씩, 매 단계 뒤 테스트를 다시 돈다.
4. 한 번에 결함 하나. 다른 결함을 보면 고치지 말고 원장에 `발견`으로 적는다. 이유: 한 커밋에 한 원인이어야 실패했을 때 되돌릴 단위가 분명하다.
5. 실패하는 테스트를 지우거나 `@Disabled`로 돌려 Green을 만들지 않는다.
6. 수정이 두 번 실패하거나 설계 방향이 틀렸다고 보이면 멈추고 막힌 지점·시도 내역을 보고한다. `git reset --hard`는 쓰지 않는다(롤백은 `tdd-doctrine.md`).

| 유형 | 성공 기준 |
|------|----------|
| 결함 수정(A)의 로직 결함 | 재현 단위 테스트 Red → Green |
| 기능 작업(B) | 로직은 동작을 서술한 테스트 먼저. 화면 배치·시각 조정은 TDD를 강제하지 않고 성공 기준을 먼저 적는다 |
| 빈 등록·설정 오류 | 컨텍스트 로드 테스트 또는 `getBean` 검증 테스트 |
| 테스트로 재현이 안 되는 유형(설정·인프라) | 성공 기준으로 삼을 검증 명령을 먼저 정한다 |
| 구조 변경(수정에 딸린 것만) | 전후 테스트 전체 통과로 동작 불변 확인. 구조 커밋을 먼저 |
| 프런트 | vitest 단위 테스트(`frontend` job) |

- 독립 리팩토링은 업무 범위 밖이다. 결함 수정·기능 작업에 딸린 구조 변경만 한다.
- **H2 ≠ PostgreSQL.** JSONB·DB 함수·쿼리 계획에 기대는 경로는 H2 통과가 보증이 아니다 — testcontainers PostgreSQL 테스트(`:api`)로 확인한다. 이유: D-362는 PostgreSQL 병렬 계획에서만 터졌다.
- **테스트에서 실제 마켓 API를 부르지 않고 실제 자격증명을 넣지 않는다.** mock은 Mockito·`MockRestServiceServer`. 이 금지는 테스트 코드에 한한다 — 운영 쓰기는 `sbshop-ops-write`가 다룬다.

## 스키마 변경

엔티티·DB 함수·인덱스를 바꾸면 같은 커밋에 `backend/docs/ddl/YYYY-MM-DD-{내용}.sql`(멱등 문)을 넣고, 운영 적용은 `sbshop-ops-write`의 DDL 절차로 **배포보다 먼저** 한다. 이유: 운영은 `ddl-auto=validate`라 테이블이 없으면 기동에 실패한다(D-361 첫 배포가 자동 롤백됐다).

## 인계·검증

- 표준·중대는 검증자(`qa-verifier`)를 부른다. 인계서는 `references/handoff.md` §2.
- **검증을 요청한 뒤에는 판정이 올 때까지 그 파일을 고치지 않는다.** 더 고쳐야 하면 검증자를 먼저 멈추고 다시 요청한다. 사고: 2026-07-07 검증 도중 편집해 중간 상태가 검증됐다.
- **같은 임무의 하위 에이전트를 둘 띄우지 않는다.** 응답이 없어 보여도 다시 부르기 전에 `git status`와 산출물 수정 시각으로 흔적을 보고, 흔적이 없어도 5분 간격으로 두 번 확인한다. 불가피하면 먼저 중단시킨다. 사고: 2026-07-07 응답 없는 에이전트를 죽은 줄 알고 다시 띄워 둘이 같은 파일을 고쳤다.
- 검증을 `qa-verifier`가 아닌 에이전트에게 맡길 때도 프롬프트에 "작업 트리를 바꾸는 명령 금지"를 적는다.
- 하위 에이전트는 커밋·푸시·브랜치 조작·`git reset`과 운영 접근을 하지 않는다.
- 검증자가 오류로 끝나면 한 번 다시 부른다. 또 실패하면 PASS로 치지 않고 보고한다.
- 반려가 두 번을 넘으면 `보류(사유)`로 돌리고 사용자에게 보고한다. 이유: 같은 지점에서 세 번 갈리면 수정이 아니라 판단이 필요한 문제다.
- 판정이 `부분`이면 주 세션이 근거를 보고 정한다.

## 게이트

- **게이트 명령의 원본은 `.github/workflows/tests.yml`이다.** 바꾼 영역의 job에 있는 `run` 줄을 그 순서대로 로컬에서 실행한다: `backend/` → `backend`, `frontend/` → `frontend`, `scraper/`·`tools/`·`ops/` → `scraper-and-operations`. 경계면(API 응답 ↔ 프런트 타입)을 바꾸면 양쪽. 이유: 명령을 문서에 복사하면 다시 어긋난다(예전 규율의 게이트 명령은 세 파일에서 서로 달랐다).
- 작업 중에는 모듈 단위(`./gradlew :모듈:test`)로 빨리 보고, 커밋 전에는 해당 job 전체를 돈다.
- **검사 대상이 0건인 명령은 통과가 아니다** — 예: `-p tsconfig.app.json` 없는 `tsc`.
- 외부 리뷰(codex 등)는 게이트가 아니다.
- 빌드 자체가 깨지면 다른 작업을 멈추고 그것부터 고친다(P0). 환경 문제(DB 미기동 등)로 테스트를 못 돌리면 정적 대조로 진행하고 그 사실을 적는다.

**로컬에서 못 도는 게이트** (Docker가 없으면 testcontainers 테스트가 돌지 않는다):

1. 로컬 실패를 "환경 때문"으로 넘기지 않는다. 변경 전 기준선의 실패 목록과 변경 후 목록을 비교해 새 실패가 0건임을 확인한다.
2. CI로 대신한 게이트는 인계서와 승인 요청에 "로컬 미실행: {무엇} — CI로 대신"이라고 적는다.
3. CI가 통과하기 전에는 원장 상태를 `검증통과`로 올리지 않는다.
4. 경량·표준은 main 푸시의 CI로 대신해도 된다 — tests가 실패하면 deploy job이 돌지 않는다.
5. 중대 등급은 작업 브랜치를 올려 `gh workflow run tests.yml --ref <브랜치>`로 CI를 먼저 돌리고, 성공을 본 뒤 main 푸시 승인을 요청한다(브랜치 푸시와 이 실행은 승인 불요). 이유: PostgreSQL 고유 동작을 건드리는 변경이 바로 로컬에서 못 도는 테스트에 걸린다. 이 명령은 첫 사용 때 동작을 확인한다.
6. 이 PC 고유의 사정(JDK 경로 등)은 규율에 쓰지 않는다 — 다른 PC에서는 틀린 말이 된다.
7. H2로만 검증된 PostgreSQL 의존 경로는 "H2 한계로 미검증"이라고 적는다.

## 실패 처리

방향이 틀렸거나 여러 수정이 함께 무너지면 비파괴 롤백(`references/tdd-doctrine.md` 롤백 절) 뒤 사용자에게 보고한다.

## 커밋

- 게이트를 통과한 것만, 단일 논리 단위로. 경량·표준은 승인 없이, 중대와 규율 파일(`CLAUDE.md`·`.claude/`)은 커밋 전 사용자 승인.
- 형식: 영문 conventional commit(`fix(scope): …`, `feat`, `refactor`, `docs`, `chore`) + 결함 ID를 제목 끝 괄호에 — 예: `fix(db): … (D-362)`. 이유: 원장과 커밋을 ID로 서로 찾는다.
- 구조 변경과 행위 변경은 별도 커밋, 구조 먼저. 구조 변경은 `refactor` 타입으로 구분한다.
- 원장·STATUS 갱신은 그 수정과 같은 커밋 또는 바로 뒤 `docs:` 커밋.
- 커밋 전에 올릴 변경에 자격증명이 없는지 한 번 본다(`sbshop-ops-write` §9).

## 기록

- 원장(`docs/normalize/defect-ledger.md`)이 정본이다. 결함 수정·기능 작업·운영 작업은 레코드를 남긴다 — 형식과 상태 어휘는 `defect-triage`.
- 상태가 바뀌는 작업을 끝내면 `docs/normalize/STATUS.md`를 갱신해 같은 커밋에 넣는다.
- 결과서(`docs/normalize/working_history/`)는 의무가 아니다 — 사용자 결정이 여럿 얽힌 작업을 묶어 남길 때만 쓴다. 이유: 결과서는 쓰이다 끊겼고 원장 레코드는 빠짐없이 쓰였다.
- 영속(커밋): `docs/normalize/`(원장·STATUS·plans), `backend/docs/ddl/`. 휘발(gitignore): `_workspace/fixes/`·`verify/`·`ops/`. 판정 요지·미해결·진행 중 운영 작업은 원장과 STATUS에 옮긴 뒤 세션을 끝낸다 — 휘발 산출물에만 있는 정보로 다음 세션이 판단하게 두지 않는다.
