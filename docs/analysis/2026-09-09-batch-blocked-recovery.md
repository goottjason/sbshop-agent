## 실제 복구와 확인 기준

- 스마트스토어: 원상품 번호·판매자 SB코드, SELF 계정, 무옵션, 현재 연결·상품 버전, 원래 배치 목표를 검증한다. `SALE_PRICE`·`STOCK` 수정 후 GET으로 두 값이 일치해야 `PRODUCT_STATUS_SALE`을 요청한다. 마지막 GET에서 가격·재고·판매 상태까지 확인한 항목만 성공으로 기록한다. `PROHIBITION` 등은 대상이 아니다.
- 스마트스토어 선행 검증에서 `SUSPENSION` 상태 변경 요청에 재고를 같이 넣으면 HTTP 400이 발생했다. 재고 변경과 판매 재개를 분리해 성공을 확인했고 이후 복구에 적용했다. 거절된 요청도 전송 이력에 보존했다.
- 11번가: 상품별·필드별 새 검토를 만든 뒤 기존 API로 commit했다. 새 작업 ID를 원래 배치 단계에 연결하고 기존 실패 이력을 보존했다. 변경 전 검토·연결·계정·목표를 다시 비교했으며, 원래 SB 저장 버전을 덮어쓰지 않았다. 정상 작업 큐의 속도 제한·429 처리를 유지한다.
- 쿠팡: 승인완료와 판매자·등록상품·옵션·SB코드를 확인하고 옵션별 가격·재고 수정 → GET 일치 → 판매 재개 → 마지막 GET 순서로 실행했다.
- 두 쿠팡 상품 `210106IHB003`, `220522IHB002`는 쿠팡 자체 판매중지로 재개가 거절됐다. 응답은 대표 이메일에 전달된 사유 확인과 해당 이메일 회신을 통한 재개 요청을 안내했다. 가격은 실제 GET 일치로 성공 처리하고 재고 단계는 ‘수량 적용됨 / 판매 재개 보류’로 남겼다. 영구 금지라고 단정하거나 강제로 재등록하지 않았다.

## 버전 변경 원인 관련 코드 근거

`ProductSyncScheduler.syncIherbProductStock()`은 매일 04:00 KST에 모든 IHB 상품의 소싱 재고를 갱신한다. `ProductSyncService.syncProductStock()`은 성공 수집 시 `recordCrawlSuccess()`와 `saveAndFlush()`를 실행하므로 실제 가격·수량이 같아도 상품 버전이 바뀔 수 있다. 조사 표본의 버전 2→3, 마지막 수집 시각과 일치하는 유력 경로다. 모든 대상의 변경 원인이 이 스케줄러 하나였다고 단정하지 않는다. 오래 실행되는 마켓 큐가 이러한 갱신과 겹칠 때 목표가 같은 항목까지 오래된 검토로 중단되는 구조를 개선해야 한다.
