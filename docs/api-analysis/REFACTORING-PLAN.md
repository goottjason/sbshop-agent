## R1 — 오류·HTTP 시맨틱 일관화 (★★★, 리스크 중)

**목표:** 미존재→404, 부분/전건 실패→적절 상태, 비동기/래핑으로 실패가 성공으로 안 보이게. 응답 계약을 일관되게.

**대상**
- **404 도입**: `ResourceNotFoundException`(신규) → GlobalExceptionHandler 404 매핑. 미존재 리소스 조회/수정을 404로. — F-PROD-5·26·29, F-BATCH-S2·SM1, F-MREG-2
- **예외 유형 보존**: F-ORD-8(마켓 접수 실패 RuntimeException 뭉갬 → 전용 예외/사유 보존), F-CAFE-2(/status 모든 실패 200 → HTTP 구분)
- **부분/전건 실패 표면화**: F-MISC-20(email/fetch 항상 ok:true → 실제 결과 반영), F-ORD-12(일괄 발주확인 부분실패 200 → 상태/헤더), F-ORD-33(발송 orderIds null 서비스 NPE — 이미 BulkShipResult가 방어? 확인)
- **애드혹 응답 정리**: F-MISC-11(ResponseEntity<?>+Map.of), F-BATCH-B2(0건 vs 진행 스키마 비대칭)

**접근:** 공용 예외 계층(NotFound/Conflict) + GlobalExceptionHandler 확장. 각 엔드포인트 재현 테스트로 실제 상태코드 확정 후 교정(P1처럼 오탐 주의).
**리스크:** 프론트가 상태코드/바디에 의존하면 계약 변경 → 프론트 병행 확인 필요.

## R2 — 관측성·활동로그 일관화 (★★★, 리스크 낮)

**목표:** 활동로그가 실제 결과를 정확히 반영하고, 조회/실패 경로도 일관 기록.

**대상**
- **비동기 sync 결과 로그**: F-SYNC-3(SUCCESS/FAILED 미기록 — P4a에서 SyncStatus는 자기기록化됨, ActionLog도 동일하게)
- **실패 경로 marketType**: F-ORD-5·15(발주확인/취소 실패 로그 marketType null — 조회로 채우기)
- **조회계열 로그 정책**: F-PROD-3·F-ORD-4(조회 API 로그 미기록 — 정책 확정: 기록할지 명시)
- **마스터데이터 로그**: F-SUP-3·F-SUP-CS-5·UC-5(supplier/currency 변경 로그), F-CRED-3(자격증명 조회 로그)
- **수동/자동 일관**: F-MISC-19(수동 email 트리거가 SyncStatus 미기록), F-BATCH-7(STARTED/완료 이원화·marketType null)

**접근:** ActionLog 기록 규약을 한 곳(공통 헬퍼/AOP)으로 정리하면 반복 제거 + 일관화. 대부분 저위험.

## R3 — 트랜잭션·멱등성·동시성 (★★★, 리스크 높)

**목표:** 외부 부수효과와 DB 저장의 정합, 재실행 안전(멱등), 동시 실행 가드.

**대상**
- **긴 트랜잭션 내 외부 I/O**: F-PSRC-8(이미지 다운로드·R2 업로드가 트랜잭션 안 → 장시간 tx·고아 이미지). F-PSRC-14/F-SYNC-19 패턴(외부호출 tx 밖·PENDING 선저장) 재사용.
- **부분성공 롤백**: F-ORD-31(발송 단일 tx 부분성공 후 예외 전체 롤백 — 건별 tx), F-SYNC-20(customs 마지막 배치 예외 전체 롤백 — F-SYNC-19에서 일부 개선, 잔여 확인)
- **멱등성**: F-PSRC-13(게시 재호출 시 MarketRegistration 중복 — unique 제약/upsert), F-PSRC-9(SB코드 결번/중복 — 시퀀스 전략)
- **동시 실행 가드**: F-BATCH-1(동시 배치 advisory lock — `[[deployment-two-jvm-topology]]`), F-SYNC-17(정산 중복 실행 가드), F-CAFE-6(재인증 동시성 락)
- **하드삭제 정합**: F-PROD-27·28(마켓 등록 있는 상품 하드삭제 고아·멱등성 — 주문삭제 폐지처럼 정책 재검토)

**접근:** 공통 패턴(선저장→외부호출→갱신, advisory lock, unique 제약)으로. **각 건 재현·정합 테스트 필수.** 분산 정합이라 리스크 높음 → 건별 신중.

## R4 — 동기화 정확성(마켓 엣지케이스) (★★, 리스크 높)

**목표:** 마켓별 sync의 취소감지·상태매핑·페이징·통관 정확도.

**대상**
- **취소감지**: F-SYNC-6(스마트스토어·Cafe24 부재), F-SYNC-10(11번가 30일 창)
- **상태/필드 매핑**: F-SYNC-11(Cafe24 items 개수 불일치 일괄적용), F-SYNC-12(Cafe24 PCCC 필드), F-SYNC-8(송장병합 가드 비대칭), F-SYNC-9(resolveProductId sbCode만), F-SYNC-18(정산 누락 신호)
- **페이징/기간**: F-SYNC-7(offset 15000 절단·30일 하드코딩)
- **마켓등록 sync**: F-MREG-1(POST /sync가 DB 미갱신·이름 불일치), F-MREG-5(vendorItemId 폴백 오조회), F-MREG-7(ESM 어댑터 부재)
- **이메일 수집**: F-MISC-21(200건 제목 contains 의존), F-MISC-22(N×M 연결)

**접근:** 마켓별로 실제 API 응답 샘플 기반 검증 필요 → **라이브 데이터 확인 동반**. 도메인 깊고 마켓 계약 의존 → 신중, 우선순위는 실제 오작동 관측 시 상향.

## R5 — 구조 정리·죽은코드·중복·상수화 (★★, 리스크 낮 — 먼저 하기 좋음)

**목표:** 유지보수성. 동작 불변, 회귀 게이트로 보증.

**대상**
- **죽은코드 제거**: F-ORD-10/19(batch 컨트롤러 catch 도달불가), F-ORD-21(toCustomsData 미사용), F-H5(markSentIfSucceeded isFailed 도달불가), F-BATCH-6(couponRate 미사용), getAllBatches(호출처 0)
- **중복 제거(잔여)**: F-S3(sourcing 분기 중복), F-H3(shipping 분기 중복), F-MISC-15(SSE 두 리스너 중복)
- **매직넘버 상수화**: F-ORD-32·F-SYNC-4(정산 0.89 — 마켓별 수수료율 설정화), F-SYNC-21(customs 배치30·1000ms), F-BATCH-M2/M3/A3(배치 정책 매직넘버·비대칭)
- **위치기반 커맨드**: F-PROD-10/14(26필드 커맨드 1~2칸 — 빌더/명시 매핑), F-PSRC-16(identifiers "{}" 삼킴)·17(productId=sbProductId 혼용)
- **요청 DTO화**: F-ORD-11/20(confirm/cancel-batch Map 직접 바인딩 → record), F-SYNC-16(원시 JsonNode 응답), F-PSRC-10(FQCN 인라인)
- **레코드/불변**: F-MISC-5(EnumMapperValue record화)

**접근:** 각 항목 독립·소규모, 병렬 처리 적합. 동작 불변 리팩토링 → 기존 테스트로 보증. **정산 수수료율 설정화(0.89)는 값 검증 필요**(마켓별 실제 요율 확인).

## R6 — 조회 품질(정렬·페이징·필터) (★★, 리스크 낮)

**목표:** 목록 API 정렬/페이징/필터 일관, 조용한 무시 제거.

**대상**
- **정렬/페이징**: F-SUP-4·LC-2(공급사/통화 정렬), F-BATCH-S3·ST2(배치 status 정렬·페이징), F-MISC-1·2(action-logs 페이징·상한 계약)
- **필터 정확성**: F-ORD-2(기간필터 — 이미 R? 완료됨), F-ORD-3(shippingStatuses EXISTS 부분매칭), F-PROD-1(marketFilter·keyword 배타)
- **입력검증(조회계 잔여)**: F-PROD-18·22(크롤 URL 검증·상한), F-PSRC-5(iHerb URL 검증), F-S4(소싱 금액)

## R7 — 보안 강화(전체 SP-10) (★ 보안 비중요 방침, 리스크 중)

> 사용자 방침상 **선택**. 최소분(시크릿 마스킹·internal 가드)은 P5b에서 완료. 아래는 전체 강화 시.

**대상**
- **OAuth CSRF**: F-CAFE-5·10(state 발급/검증), F-CAFE-11(콜백 error 처리), F-CAFE-7·9(인가코드 재사용·파싱)
- **시크릿 저장 암호화**: F-CRED-2(DB 평문 → 암호화), F-CRED-9(검증), F-CRED-10(예외 로그 마스킹)
- **로그 노출**: F-CAFE-8·13(인가코드 URL/access.log)
- **접근·PII**: F-SYNC-13(preview 무인증 PII), F-MISC-13(SSE 인증/상한), F-MISC-3·F-CAFE-14(CORS 전역)

**접근:** 실 인증 프레임워크(Spring Security) 도입 여부가 선결. 도입 없이는 부분적. 사용자 결정 필요.

## R8 — 순수 NOTE(관찰·의도) (☆, 대개 무액션)

**성격:** 대부분 의도된 동작·모범사례·경미 관찰. 코드변경보다 **문서로 명시**가 적절.

**조치:** 각 §7에 "의도/유지" 확정 표기 또는 소소 개선. 별도 배치 불필요.

## 실행 방식 제안

1. **R5(구조 정리)부터** — 리스크 낮고 병렬화 쉬움, 코드베이스가 깔끔해져 이후 작업 수월. 동작 불변이라 회귀 게이트로 안전.
2. **R2(로그) → R1(시맨틱)** — 관측성·계약 일관화. R1은 프론트 계약 영향 있어 도메인별 승인.
3. **R6(조회 품질)** — 소규모 다수, 병렬.
4. **R3(정합) → R4(sync)** — 어렵고 도메인 깊음. 건별 재현·라이브 확인. 실제 오작동 관측 시 우선.
5. **R7(보안)** — 사용자 방침 확인 후 선택. Spring Security 도입 결정 동반.
6. **R8** — 문서 확정.

각 R묶음은 기존 정상화 워크플로우(재현 테스트 우선 TDD → 단독 회귀 게이트 → 관심사별 커밋 → 문서 반영)로 진행. 진척은 `FINDINGS-CHECKLIST.md` 체크박스로 추적.
