# 마켓플러스 선택 재전송: 실행 전 계약 보완

2026-09-08. [기존 선택 필드 계약](2026-09-08-marketplus-selected-final-contract.md)을 애플리케이션 코드와 다시 대조하고, 운영 Chrome에서 옥션 상세 화면과 관리자 검색 화면의 DOM·함수 원문만 읽었다. 가격·HTML·옵션 입력을 변경하거나 저장·전송 함수를 실행하지 않았다. 이 문서는 구현 제안이며 실제 전송 기능의 완료 보고가 아니다.

[추가 관측 근거](evidence/2026-09-08-marketplus-selected-execution-followup.json)에 식별자, 함수 해시, 옵션 필드, 조회 한계와 복원 결과를 기록했다. 원문은 `/private/tmp/sbshop-mp-selected-followup-read-2.json`, `/private/tmp/sbshop-mp-selected-stock-read.json`에 있다. 수집 플래그를 복원했고 기존 MP 전송이력 탭은 ready·20행으로 확인했다. 마지막 상태는 collect/upload=true, collectEnabled=true, error=null이다.

## 현재 구현과 빠진 부분

| 단계 | 현재 구현 | 남은 구현 |
| --- | --- | --- |
| DB 변경 → 카페24 | 동일 변경 이력·revision·전송 대상의 가격/수량/일반 필드 작업을 조회 | G/A 목표와 카페24 목표 사이의 상속 계약을 검토에 고정 |
| MP 선택 재전송 검토 | `MarketPlusFieldProgressService`의 준비 안내와 비활성 버튼 | 실제 상품·계정·entity·필드·상속·정규화 값의 영속 검토 |
| MP 실행 | 없음. 일반 필드 엔진의 SUPPORTED는 G/A를 제외하고 worker는 읽기 전용 | 명시적 실행 접수, 쓰기 의도 기록, UI 실행 및 응답 분류 |
| MP 결과 관측 | 분 단위 성공/실패 이력 수집 | 새 쓰기 작업과 정확히 연결 가능한 식별자 확보. 시간 근접만으로 연결하지 않음 |
| G/A 최종값 | 공개가격과 제한된 옥션 무옵션 수량 관측 | 검토 목표와의 비교, HTML 최종 영역/정규화 계약. 403·오류는 미확인 유지 |

`ProductEditPolicy.nativeCafe24`는 G/A 활성 연결이 있는 상품의 일반 필드 편집을 허용하지 않는다. 따라서 HTML 재전송만 추가해도 DB 상세정보 수정부터 이어지는 전체 흐름은 열리지 않는다. 필드 지원·최종 재조회 계약을 확보한 뒤 별도로 정책을 보완해야 한다. 이번 조사에서는 잠금을 변경하지 않았다.

Q26은 쿠팡·11번가·카페24가 각각 현재 한 계정의 상품이라는 사용자 확인으로 정리됐다. 이를 계정 귀속 미확인이라는 일반적인 차단 사유로 다시 남기지 않는다. 단일 계정 검사 구현은 별도 작업에서 담당한다. MP 실행 직전 현재 로그인된 mall/shop·G/A 판매 계정과 해당 상품 연결의 일치 검사는 계속 필요하다.

## 저장 응답과 후속 동작

현재 옥션 `auction|shouldbe2480`, 카페24 10186/P0000PBU, 외부 상품 D888859044, entity `65b25bf7dbece`에서 다음 함수 원문을 확인했다.

1. `saveProduct('P')`는 폼·편집기를 정규화하고 `is_modify_partial=T`로 관리자 내부 `/mp/product/rest/save`에 POST한다. 호출 제한 시간은 500,000ms다. 검토용 조회가 아니다.
2. 응답 handler는 `error/message/menu_no`, `validation`, `valid_success/valid_message`를 검사한다. 입력 검증·권한·서버 거절은 각각 기록해야 한다. HTTP 200만으로 접수 성공을 확정하면 안 된다.
3. 이어 `send_count`, `send_list`, `valid_success_count`, `valid_success_ids`를 읽는다. 이 필드들의 실제 응답 형태와 항목별 의미는 아직 관측하지 않았다. 숫자 합계만으로 현재 상품·계정 한 건의 접수를 확정하면 안 된다.
4. 정상 경로의 `showOriginAlert`는 안내·부모 새로고침·현재 창 닫기이며 추가 전송 요청은 없다. `showProductGuide`도 가이드 표시 후 종료 경로다. 따라서 기존 정상 흐름에서 save 다음에 send를 무조건 호출하는 구현은 잘못된 중복 전송을 만들 수 있다.
5. 별도 `sendProduct()`는 `/mp/product/rest/send`를 호출한다. 실패/부분 가능 레이어의 후속 동작과 연결돼 있으므로 정상 저장 뒤 자동 호출 대상에서 제외한다. 실제 경로를 사용해야 할 경우 대상과 추가 쓰기 의도를 다시 검토해야 한다.

실제 save/send 응답은 이번 조사에서 만들지 않았다. 응답 유실·브라우저 종료를 실패 확정으로 보고 자동 재전송하면 안 된다. 쓰기 의도 기록 이후 결과가 불명확하면 `UNKNOWN`으로 보존하고 결과 조회만 먼저 진행한다.

## 재고관리 전환에서 구분해야 할 값

사용자는 옵션/재고관리 미사용 상품에 대해 관리 사용과 SB 판매용 수량의 변경안을 비교 검토에 포함하도록 승인했다. 이 승인은 숨김 수량이나 내부 토글의 의미를 확정하는 근거는 아니다.

현재 옥션 화면은 `is_default_option_stock=T`이며, 로컬 `is_option_stock=F`, `current_stock=500`, `market_current_stock=500`이다. 현재 폼에는 실제 `item_no`/`item_current_stock` 입력이 없다. 두 500을 품목별 전송 수량 또는 소싱 실재고로 확정하지 않는다.

| 값/함수 | 확인한 동작 | 구현상 의미 |
| --- | --- | --- |
| `is_default_option_stock=T` | 카페24 원본 옵션/재고 정보를 상속 | 별도 설정 전환과 원본 설정 변경을 구분해 검토 |
| `setIsOptionStock('T')` | 카테고리 옵션 메타를 읽고 `initLoadOption('T','F','F')`로 옵션을 초기화 | 단순 재고 추적 토글로 사용하면 안 됨. 구매 옵션 구성이 달라질 수 있음 |
| `checkMarketCurrentStock` | `item_current_stock`들을 합산해 `market_current_stock`에 기록 | 총수량만 입력하는 것과 품목 수량 배분은 다른 작업 |
| `setItemCurrentStock` | 0이면 `use_soldout=T`, 양의 정수이면 F로 바꾸고 합계를 갱신 | 수량 변경에 품절 상태 변경도 동반. 재개 금지 상태와 별도 대조 필요 |
| `initBaseProductOption` | 읽기 경로 `getCapiProductData`의 `sMarketOptionType` N/X/S/O를 구분 | N=옵션재고 사용 안 함, X=지원 불가, S=재고 사용, O=옵션 사용. 현재 상품의 실제 응답은 추가 확인 필요 |
| `checkStockOption` | 현재 함수 첫 줄에서 `return true` | 이 함수 통과를 유효성 검증 근거로 사용할 수 없음 |

후속 검토에는 최소한 카페24 재고 사용 방식, MP 기본/별도 설정, 기존·변경 옵션명과 품목 식별자, 품목별 수량, 합계, `use_soldout`, 선택전송 확대 항목을 나란히 표시해야 한다. 새 구매 옵션 생성이나 기존 옵션 초기화가 수반되면 수량만 바꾸는 작업으로 축약하지 않는다.

## G마켓 추가 조사 결과

관리목록의 `search_word_type=C`(마켓상품코드), `search_word_text`, 기간 필드를 확인했다. 코드 3490115053을 입력해 조사했고, 기간 입력은 2000-01-01~2026-09-08까지 표시됐다. 그러나 확장된 화면에 총 2,992건의 넓은 목록이 나왔으므로 코드 조건이 조회 상태에 반영되었다는 근거는 확보하지 못했다. 특정 상품이 검색되지 않았다거나 삭제됐다는 결론을 내릴 수 없다. G마켓 entity와 상세 페이지의 동일 계약은 아직 확보되지 않았다.

다음 읽기는 관리자 검색 handler/실제 조회 조건을 먼저 확인하거나, 이미 화면에 보이는 G마켓 행의 상품번호·계정·카페24 코드와 상세 진입 식별자를 함께 읽어 시작한다. 정확한 상세 화면에서 가격/HTML/옵션 선택 가능 여부, 편집기 정규화, 상속 모드, 상품 버전을 다시 확보한다. 옥션의 숫자 schema ID나 entity를 G마켓에 복사하지 않는다.

## 구현할 최소 실행 단위 제안

첫 단위는 검증한 계정의 기존 상품에 대한 가격·HTML 선택 재전송이다. 이미지·상품명·신규 등록·옵션 구성 변경은 이 실행 범위와 구분한다. stock 전환은 위의 옵션/품목 계약을 확보할 때까지 비교 검토 단계에만 포함한다.

- **준비:** 최대 50개 상품을 순차 조회하되 각 상품·마켓별로 독립 검토한다. actor, requestId, SB revision, 연결 revision, mall/shop, 카페24 번호/코드, MP entity, 외부 번호, 계정, 현재 상속 모드, 선택·연관 필드, 정규화 전후 값/해시, handler 계약 버전과 만료를 고정한다. 일부 미지원은 사유와 함께 제외한다.
- **목표값:** 카페24 상속 T를 유지하려면 같은 revision의 카페24 쓰기·재조회와 현재 상속 원본을 대조한다. MP 폼의 hidden 값만 목표로 삼지 않는다. 별도 설정 F로 전환하는 안은 그 변경과 향후 상속 해제 효과를 검토에 표시한다. 조용히 설정을 바꾸지 않는다.
- **실행:** 검토 승인 후 영속 작업을 생성하고, 실행 직전 상품·계정·상속·정규화·최종 체크 집합을 다시 대조한다. 차이가 나면 `STALE`로 종료한다. 신규 쓰기 의도를 DB에 기록한 뒤 자신의 임시 탭에서 공급자의 검증된 선택전송 경로를 한 번 실행한다. handler가 생성한 선택 범위가 검토를 넘으면 요청 전에 중단한다. 관리자 POST를 공개 API처럼 임의 재현하지 않는다.
- **접수:** 응답 원문의 필요한 항목을 제한적으로 보존하고 명시 거절·접수·불명을 구분한다. 동일 commit/report는 중복 접수하지 않는다. 외부 쓰기 응답이 유실된 작업은 자동 반복하지 않고 조회로 복구한다. 실제 429만 공유 대기를 연장한다.
- **결과:** `MP 접수`, `전송이력 관측`, `공개가격 관측`, `최종 필드 일치/미확인`을 별도로 표시한다. 분 단위 이력을 쓰기 ID처럼 사용하지 않는다. 공개가격이 확인돼도 HTML까지 성공으로 올리지 않는다. 오류 페이지는 최종 확인 불가로 남긴다.

이를 구현하기 전에 필요한 마지막 계약은 G마켓 상세 식별/동등 handler, 현재 상속 원본과 목표의 대응, 새 HTML을 넣었을 때의 실제 정규화·자동 선택 범위, save 응답의 항목별 식별 형태, 최종 HTML 조회 영역이다. 준비·상태 모델과 실패 보존은 현재 근거로 설계할 수 있지만, 이 자료 없이 양 마켓 전체 실행과 최종 성공을 지원했다고 표시할 수는 없다.

계약 보완 뒤 최초 실검증은 사용자와 확정한 기존 상품 한 건·마켓 한 개·필드 한 개에서 시작한다. 검토한 값과 선택 범위의 재대조, 쓰기 한 번의 접수, 동일 commit/report 복구, 별도 마켓 조회의 결과를 남긴다. 그다음 가격+HTML 조합과 선택 다건의 부분 실패를 확인한다. 수량은 카페24 재고만 사용(S)과 구매 옵션 사용(O)의 실제 차이를 확정하고 전환 검토가 승인된 품목에 한해 별도 검증한다. 이 문서 작성 단계에서는 어떤 실전송도 수행하지 않았다.

이번 변경은 문서·정제된 증거만 추가했다. 애플리케이션 소스, 운영 상품 DB, 외부마켓 쓰기, 배포에는 변경이 없다. helper의 Python 문법 검사와 라이브 읽기를 수행했으며 전체 앱 테스트를 다시 실행하지 않았다.
