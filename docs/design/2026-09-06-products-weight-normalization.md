# 상품 무게 kg 표준 전환 — Q19

2026-09-06. 사용자 확정: kg 저장, 출처로 단위가 확인된 기존 값만 변환, 불명확한 값은 미확인 표시. Q18의 가격 끝자리·정수 수량 처리 질문과는 별개다.

## 확인한 경로와 수정

| 경로 | 확인 내용 | 조치 |
| --- | --- | --- |
| `ProductDraft.weightG` | DB `weight_g` 소수 2자리, 소싱 응답 `shippingWeightGrams`에서 입력 | 원본 g 유지 |
| `DraftPublishUseCase` → `ProductCreateCommand` | g 값을 그대로 전달하던 오류 | 생성 경계에서 정확히 1000으로 나눔 |
| `LogisticsInfo.weight` | 기존 소수 2자리로는 125g의 kg 표현을 보존할 수 없음 | 소수 5자리·전체 13자리로 확장, 2026-09-06 운영 반영 |
| 상품 생성·수정 입력 | `weight` 단위가 화면에 없었고 DB 반올림 위험 | kg 계약 명시, 범위·초과 정밀도 검사, 신규 화면 kg 표시·상세 입력 안내 |
| `LandedCostCalculator` | kg로 받은 값을 배송비 정책의 g로 변환 | 소비 경로는 유지. 초안 1200g가 1.2kg로 전달되어 올바른 배송비 구간을 사용하는 회귀 검사 |
| `Cafe24MarketClient.formatWeight` | kg를 소수 2자리로 변환하는 기존 외부 전송 경로 | 이번 변경 범위에 포함하지 않음. 내부 저장 정밀도와 외부 API 표현의 차이는 필드 반영 설계에서 별도 검토 |

`ProductWeight`는 단위 변환과 저장 가능한 정밀도 검사를 담당한다. 화면 표시를 맞추기 위한 반올림은 하지 않는다. 125g→0.125kg, 125.01g→0.12501kg가 DB 저장·재조회 후에도 동일해야 한다. 정수 8자리 범위는 그대로 유지하므로 기존 큰 값이 열 확장 때문에 잘리지 않는다.

초안 무게를 변환할 때 빈 값을 임의 수량으로 대체하지 않는다. 다만 기존 `Product.create`가 무게 미입력 시 0을 저장하는 동작은 남아 있다. 기존 0이나 누락을 확인된 실제 중량으로 취급하지 않는다.

## 기존 상품의 출처 조사

[읽기 전용 SQL](../../backend/docs/ddl/2026-09-06-product-weight-review.sql)은 상품별 현재 값, 연결된 초안 ID·g 값·kg 환산값, 양쪽 소싱 URL·수정 시각을 나열한다. 초안이 여러 개면 여러 행으로 표시하여 임의로 한 개를 선택하지 않는다.

상품의 `weight`와 초안의 `weight_g`가 같아도 g 단위를 확정하지 않는다. 초안이 게시 이후 수정됐거나 상품의 무게가 별도로 보정됐을 수 있다. 원본 소싱 자료와 게시 경로·당시 버전·상품 수정 기록을 대조하고, 근거가 부족하면 재수집 또는 수동 확인 대상으로 남긴다. 값의 크기, 브랜드, 용량의 `measureUnit`, 단순 생성일만으로 추정하지 않는다.

기존 값의 실제 변환 기능은 다음 자료와 처리가 준비된 후 연결한다.

- 상품 ID·검토 시점의 값/버전, 확인한 원본 단위, 근거 자료와 확인자.
- 이전 값·단위→kg 결과의 미리보기 및 변경 이력. 이미 kg인 값의 재변환 방지.
- 적용 직전 상품의 값/버전 재검사. 검토 후 변경된 상품은 충돌로 제외.
- 단위 미확인·확인 완료 상태의 영속 저장과 API/UI 표시. 현재 새 미리보기는 기존 단위 확인 안내를 제공하며 상품별 확인 완료 판정은 아직 제공하지 않는다.
- 무게에 의존하는 가격·마켓 필드의 파생 변경 검토 및 기존 편집/동기화 정책 적용.

현재 조사 SQL에는 UPDATE가 없으며 단위 확인 이력을 만들어내지도 않는다. 배포 시 운영 열 정의와 무게 집계는 확인했으나 상품별 단위 조사·값 변환은 수행하지 않았다.

## 배포 시 순서

1. 기존 DB 열 정의를 확인하고 [정밀도 확장 DDL](../../backend/docs/ddl/2026-09-06-product-weight-precision.sql)을 검토한다. 기존 데이터 변환과 구분한다.
2. `numeric(13,5)` 확장과 실제 DB 저장/조회 검증 후 새 백엔드·프론트를 배포한다. 기존 `ddl-auto=update`가 형식 변경을 정확히 수행할 것으로 가정하지 않는다.
3. 기존 상품은 조사 결과로 변환 대상을 검토하고, 이력·충돌 검사 기능을 통해 확인된 값만 반영한다.

2026-09-06 DB 백업 후 정밀도 확장과 새 코드의 운영 배포를 완료했다. 기존 값은 변환하지 않았으며 상품 수·무게 합계·최솟값·최댓값이 보존됐다. [운영 배포 기록](2026-09-06-products-deployment.md)을 참고한다. 코드 롤백 시에도 확장한 열의 정밀도는 축소하지 않는다. 이전 코드의 자동 DDL도 비활성화하여 새 kg 값의 소수 부분을 보존한다.
