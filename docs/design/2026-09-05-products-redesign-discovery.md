# 상품 관리 전면 개편 — 1차 점검 및 Q&A 기록

작성일: 2026-09-05. 갱신일: 2026-09-06. 상태: Q1~Q6, Q8~Q17 확정 / Q7의 자동 생성 운영 방식 확인.

사용자는 기존 화면을 대폭 교체하되, 여러 차례 Q&A를 통해 화면과 백엔드 정책을 결정하기를 명시했다. 이 문서에서 ‘확정’으로 기록한 요구사항만 사용자 합의 사항이며 나머지는 검토안이다. 미결정 제안은 답변 없이 확정하거나 구현하지 않는다. 이전 설계 문서는 참고 자료이며 이번 요청보다 우선하지 않는다.

## 1. 이번에 확인한 범위

- 크롬 제어 전용 도구가 제공되지 않아 사용자가 허용한 코드 점검으로 진행했다. 브라우저 렌더링·클릭 동작을 직접 검증한 것은 아니다.
- 운영 `/sbshop-agent/products`: HTTP 200, 프론트 정적 자산 경로 확인.
- 제공된 계정으로 운영 `GET /sbshop-agent/api/v1/products?page=0&size=2`: HTTP 200. 총 2,854건, 표본 2건의 목록 응답 확인. 전 상품·외부마켓 실물을 대조한 결과가 아니다.
- 로컬 React 화면, Spring API·도메인·마켓 어댑터·일부 스케줄러 코드 확인. 배포 코드가 로컬 코드와 완전히 동일한지는 검증하지 않았다.
- 프로젝트와 macOS 다운로드 폴더에서 관련 API PDF 존재 확인. 핵심 수정 문서를 텍스트 추출하여 일부 필드 대조. 전체 필드 조사는 아직 완료되지 않았다.
- 운영 상품 변경·외부마켓 등록·동기화·크롤 실행은 하지 않았다. 작업물은 설계 논의 문서이며 인증정보는 저장하지 않는다.

## 2. 사용자 요구사항 — 유지할 범위

| 영역 | 요구사항 |
| --- | --- |
| 화면 | 기존 UI에 얽매이지 않는 전면 개편. 복잡한 작업을 직관적으로 수행 |
| 검색·정렬·필터 | 빠른 검색, 필드 조합과 정렬은 Q&A로 결정 |
| 목록 | 썸네일, SB코드, 브랜드, 상품명 링크, 카테고리, 소싱처, 판매가, 재고, 묶음수량, 각 마켓 현황 |

| 수정 제한 | 외부마켓이 변경을 허용하지 않는 연동 필드는 시스템상품에서도 수정 불가. 마켓별 API 근거 조사 필수 |

| 불일치 | 시스템상품과 마켓 정보의 불일치를 눈에 띄게 표시하고 즉시 반영 가능 |
| 자동화 | 429를 고려한 스케줄 동기화. 빈도·범위·심사 대상 취급은 추가 협의 |
| 연결 해제 | 외부 삭제·판매중단 감지 시 요구된 연결 해제 정책 수립. 삭제와 판매중단의 판정·후속 처리 상세는 추가 Q&A |
| 신규 등록 | 단건/여러 상품에서 미등록 마켓 선택 등록. 등록과 수정 동기화의 처리 구분 |
| 자료 | 프로젝트·다운로드 API 자료를 우선 조사. 근거 미확보 사항은 추측하지 않고 필요한 자료를 특정하여 요청 |
| 진행 | 조사 → 여러 차례 Q&A → 화면 검토 → 백엔드 상세 설계 → 구현·검증 순으로 구체화 |

## 3. 코드 및 운영 응답에서 확인한 설계 문제

| 확인 사항 | 근거 | 개편 시 해결할 문제 |
| --- | --- | --- |
| 통합 검색은 상품명·SB코드·브랜드의 부분 일치 | `ProductSpecifications.addKeyword` | 검색 대상·여러 코드 붙여넣기·성능 기준 결정 |
| 프론트 정렬 상태와 정렬 파라미터가 없음 | `ProductGrid`, `ProductQuery` | 서버 전체 결과 기준 정렬과 안정적인 보조 정렬 필요 |
| 마켓 필터는 선택 마켓의 등록행 존재를 OR로 검사 | `ProductSpecifications.addMarkets` | ‘쿠팡 등록 AND 11번가 미등록’ 또는 정보 불일치 조합 표현 필요. 등록행 존재와 실제 활성 등록 구분 |
| 상품명 클릭은 상세 모달 열기 | `ProductGrid`의 `productInfo` 열 | 요구된 상품 URL 링크와 정보 편집 진입점을 구분. URL 목적지 확인 필요 |
| 묶음수량은 DB에 있으나 목록 DTO·운영 응답에 없음 | `LogisticsInfo`, `ProductListResponse`, 운영 표본 | 목록 응답 확장 |
| 재고는 그리드에서 수량 대신 ‘있음/품절’로 표시 | `ProductGrid`의 `priceStock` 열 | 재고 수량·소싱처 재고 상태·마켓 판매 상태 의미 구분 |
| `SYNCED` 배지가 정보 일치를 증명하지 않음 | `MarketBadgeState.of`: 삭제/오류 외에는 식별자 유무로 `SYNCED` 반환 | 등록 여부·판매 상태·최신 정보 일치·확인 시각을 분리 |
| G마켓·옥션은 카페24 연결정보에서 URL이 만들어지면 `SYNCED`로 표시 | `ProductController.buildMarketMap` | 각 하위 마켓의 독립적인 판매·반영 확인 필요. 카페24 성공을 하위 마켓 성공으로 취급할 수 없음 |
| 일반 저장은 DB만 수정, 가격·재고와 이미지 저장은 마켓 호출까지 수행 | `ProductManageUseCase.updateProduct/updatePriceStock/updateImagesAndHtml` | 저장과 외부 반영을 일관된 두 단계로 정리 |
| 카테고리 등 일반 수정 경로에 등록 마켓 기반 필드 잠금이 없음 | `ProductUpdateRequest`, `ProductManageUseCase.updateProduct`, `Product.update` | 화면과 서버 양쪽에서 동일한 수정 규칙 적용. 일괄·크롤 경로도 동일 |
| 일반 필드 반영 목록은 브랜드·상품명·제조사뿐이며 쿠팡 제외 | `MarketEditField`, `ProductFieldSyncUseCase`, `productFieldSync.ts` | 실제 수정 범위 전체의 필드별 지원 조사 및 확장 |
| 카페24 필드 반영은 제조사를 제외하고 나머지 필드를 성공 처리 가능 | `Cafe24MarketClient.syncProductFields` | 일부 필드 미반영을 마켓 전체 완료로 감추지 않도록 필드별 결과 필요 |
| 이미지 업로드·크롤 UI는 반환된 마켓 실패 결과를 충분히 표시하지 않음 | `ProductDetailModal.handleFilesSelected/handleUploadByUrl/handleCrawl` | 업로드 성공과 외부 반영 성공의 구분 |
| 소싱 이미지 크롤 UI는 IHB만 허용 | `ProductDetailModal.handleCrawl` | 가격·재고 크롤 지원과 콘텐츠 크롤 지원을 소싱처별로 별도 조사 |
| `lastCrawlAt`은 시도/성공 시각으로 사용되며 콘텐츠별 성공 반영일이 아님 | `Product.markCrawlFailed/markCrawlSucceeded`, 목록 응답 | 가격·재고·이미지·HTML별 확인/변경/적용/실패 시각 구분 |
| 마켓별 판매가는 원가·묶음·수수료·마진 정책으로 별도 계산 가능 | `MarketSalePriceResolver` | 그리드 판매가가 기준가인지 실제 마켓가인지 Q&A 필요. 정상 가격 차이를 불일치로 오판하지 않도록 설계 |
| 확인한 상품 스케줄러는 IHB 재고 정기 처리이며 `BatchScheduler` 메서드에는 `@Scheduled`가 없음 | `ProductSyncScheduler`, `BatchScheduler` | 전체 필드 불일치 처리·존재 확인·재시도 스케줄의 별도 설계 필요. 운영 외부 스케줄러 유무는 미확인 |

### 전제 수정이 필요한 부분

1. **상품명과 카테고리를 모두 ‘대부분 수정 불가’로 묶어 잠그면 안 된다.** 쿠팡의 승인필요 수정 API에는 상품명 관련 필드가 있고 승인 후 반영되며, 노출카테고리는 등록 후 판매자 직접 변경 불가로 명시된다. 등록상품명·노출상품명·제품명을 구분하여 확인해야 한다. [쿠팡 공식 수정 문서](https://developers-v1.coupangcorp.com/hc/ko/articles/360034156073-%EC%83%81%ED%92%88-%EC%88%98%EC%A0%95-%EC%8A%B9%EC%9D%B8%ED%95%84%EC%9A%94)
2. **스마트스토어 카테고리 변경 무시 조건을 모든 상품에 일반화하면 안 된다.** 확보 PDF 2쪽은 표준형 옵션 카테고리 상품에서 변경 요청이 무시되며 렌탈은 예외라고 설명한다. 기존 `D-294` 문서의 전체 불가 표기는 근거보다 범위가 넓다. 현재 공식 엔드포인트와 버전 표기는 확인했지만 웹 추출 본문은 요청 스키마 설명을 충분히 포함하지 않아, PDF의 상세 조건을 최신 전체 스키마와 추가 대조해야 한다. [현재 원상품 수정 문서](https://apicenter.commerce.naver.com/docs/commerce-api/current/update-origin-product-product)
3. **11번가도 상품 유형 구분이 필요하다.** 확보 수정 PDF는 소/세 카테고리 변경 범위와 함께 신규상품의 카테고리 수정 불가를 기재한다. ‘신규상품’의 API 상품 유형 정의와 현재 상품들의 유형을 확인해야 한다. 신규 등록일이 최근이라는 뜻으로 추측하지 않는다.
4. **기존 조사 문서의 미구현 표시는 현재 코드와 다를 수 있다.** 예를 들어 카페24 브랜드 수정은 현재 `brand_code`와 코드 해석기를 사용한다. 이전 문서의 문자열 `brand` 전송 의심을 현재 결함으로 그대로 보고하지 않는다.
5. **카페24 → G마켓·옥션은 별도 연동 경로다.** 현재 UI는 마켓플러스 수동 전송 안내를 포함한다. 과거 스파이크 문서만으로 공개 API 부재 또는 완전 자동화 가능을 현재 사실로 확정하지 않는다. 계약/권한/사용 가능한 인터페이스와 하위 마켓 결과 확인 방법을 추가 조사한다.

### 전체 필드 조사표에 기록할 항목

각 업무 필드별로 DB 경로, 마켓 요청 경로, 상품 유형, 수정 가능 상태, 즉시/심사 필요/불가/미지원/미확인, 빈 값 처리, 파생 필드, 근거 문서와 버전, 반영 검증 방법을 기록한다. ‘미지원’과 ‘불변’은 구별한다. 마켓에 대응 필드가 없는 내부 업무 필드의 편집 정책도 Q&A 대상으로 남긴다.

대상은 상품명·기본명·원문명·브랜드·카테고리·제조사·원산지·HS코드, 원가·환율·배송비·마진·쿠폰·최소마진·판매가, 재고 수량/상태·입고예정일·무게·묶음수량, 바코드·용량·단위, 소싱처·URL, 원본/호스팅 이미지·대표/부가 이미지·상세 HTML·검색어·메모를 포함하여 엔티티와 대조한다. SB코드·내부 PK·감사 시각·연동 상태 등 시스템 관리 필드는 업무 편집 대상과 구분한다.

## 5. Q&A 후 구체화할 설계 방향 — 미확정

### 화면

- 상단 빠른 검색과 저장한 필터, 필요한 조건만 펼치는 필터 영역.
- ‘전체 / 정보 반영 필요 / 반영 실패 / 콘텐츠 오래됨 / 미등록 마켓 있음’ 작업용 보기 후보. 기본 정렬은 ‘조치 필요 우선 → 정보 갱신 오래된 순’으로 확정. 조치 필요의 세부 판정과 갱신일의 기준은 검토 중.
- 상품 식별 열을 고정한 그리드. 요구된 열을 모두 포함하고 가격·수량·마켓 상태가 구분되도록 검토.
- 상품명은 확인된 상품 URL, 별도 편집 진입점은 상세 패널 또는 상세 화면. 레이아웃은 시안으로 비교 후 결정.
- 선택 시 일괄 편집·소싱처 갱신·마켓 반영·미등록 마켓 등록 액션 제공. 현재 페이지 선택과 검색 결과 전체 선택의 의미를 명시.
- 상세 편집에 잠금 사유와 해당 마켓을 표시. 마켓별 변경 전후·실패 원인·재시도 및 작업 진행 이력 제공.

### 백엔드

- 시스템상품 저장 시 변경 필드와 버전을 남기고, 외부 반영 작업을 분리하는 구조 검토.
- 마켓별 필드 지원/잠금 정책을 서버에서 판정하여 프론트에 제공. 등록된 마켓 중 수정 불가능한 대상이 있으면 연동 필드의 DB 수정도 차단한다는 요구사항 적용. Q5로 심사 후 수정 가능한 필드는 편집을 허용하고 심사 대상·변경 내용을 확인한 뒤 반영하기로 확정. 내부 전용·지원 여부 미확인의 상세 취급은 검토 중.
- 마켓의 존재, 판매 가능 여부, 정보 일치, 작업 상태, 마지막 검증 시각을 구분. 예상 마켓 데이터는 상품 데이터와 마켓별 변환·가격 정책을 함께 기준으로 생성.

- 단건·일괄·스케줄러가 같은 영속 작업 경로를 사용하도록 검토. 상품×마켓×버전/작업종류 단위 중복 방지, 작업별 결과, 실패 항목 재시도, 재시작 복구, 오래된 작업의 최신 변경 덮어쓰기 방지.
- 마켓·계정별 호출 제한을 조사한 뒤 대기열과 재시도 적용. 429·일시 오류와 데이터 거절·심사·정책 차단을 구분하며 수치와 재시도 횟수는 임의 확정하지 않음.

- Q8 확정: 일시 품절은 정상 연결 유지. 규칙 위반 등에 따른 영구 판매금지와 삭제 확정은 활성 연결 해제. 원인 미확인·조회 실패를 영구금지/삭제로 추측하지 않는다. 과거 식별자·주문 이력은 유지하는 설계.

### Q18 확정 — 2026-09-06

사용자 최종 답변: 판매가는 **100원 단위 반올림**, 12,345원→12,300원 / 12,650원→12,700원. 300원·900원은 끝자리 제한이 아닌 예시였다. 재고·묶음수량은 **비율 계산 결과의 소수 부분을 버리고 미리보기에 표시**한다. 무게·용량은 단위에 따라 가능하면 정수 또는 소수 첫째 자리까지 표시하는 방향이다.

| 대상 | 확정 방향 | 구현과 검토 범위 |
| --- | --- | --- |
| 판매가 | 100원 단위 반올림 | 미리보기의 값 지정·증감·비율 연산 결과에 HALF_UP을 한 번 적용. 이미 100원 단위인 값은 추가로 올리지 않음 |
| 재고·묶음수량 | 비율 계산 후 소수 부분 버림 | 3개에서 50% 증가 시 4.5→4개. 직접 지정·증감은 정수 입력. 묶음수량 1개 미만·음수·범위 초과는 제외 |
| 무게·용량 | 단위에 따라 정수 또는 소수 첫째 자리 선호 | Q19의 무게 단위와 함께 적용 범위 확정. 0.05kg를 0.1kg로 바꾸는 등 표시 편의를 이유로 실제 규격을 임의 변경하지 않음. 단위가 확인되면 50g 등 정확한 값으로 읽기 쉽게 표시하는 안 검토 |

미리보기는 기존 값·계산 원값·소수 처리 후 값을 구분한다. 표시에 천 단위 구분을 넣되 문자열의 소수 정밀도를 유지한다. 화면 표시 자릿수와 DB 저장 정밀도는 별개이며, 현재 DB 소수 2자리 제한 자체가 사용자 승인 정책은 아니다. 원가·환율·배송비 등 다른 수치 필드에 판매가 반올림 규칙을 확대 적용하지 않는다.

API 기본값과 프론트 요청은 `APPLY_FIELD_RULES`이며 위 필드별 규칙을 적용한다. 무게·용량 등 다른 필드의 저장 정밀도 초과는 임의 반올림하지 않고 제외한다. 변경 예정값이 없는 제외 항목에는 계산 원값을 성공 결과처럼 표시하지 않는다.

### Q19 확정 — 2026-09-06

사용자가 추천안을 수락했다. **시스템상품 무게 저장 단위는 kg로 통일하고, 기존 값은 출처로 단위가 확인된 경우에만 변환한다. 불명확한 값은 미확인으로 표시한다.** 용량 단위와 배송 무게 단위는 별개다.

신규 초안의 `weightG`를 `ProductCreateCommand.weight`에 그대로 넘기던 경로를 g→kg로 수정했다. 초안의 소수 2자리 g를 보존하려면 kg 소수 5자리가 필요하므로 DB 저장 정밀도를 확장하는 코드·DDL을 준비했다. 이는 Q18의 화면 표시 선호와 별개이며 소수 첫째 자리로 실제 무게를 변경하지 않는다. 신규 상품 입력 화면은 kg 단위를 명시한다.

기존 상품·초안의 연결과 값 일치는 조사 단서일 뿐이다. 초안이나 상품이 이후 수정될 수 있으므로 단위 확정이나 자동 변환의 증거로 단독 사용하지 않는다. [무게 단위 전환 기록](2026-09-06-products-weight-normalization.md)에 코드 경로, 조사 SQL, 검토·이력 요건, 남은 작업을 정리했다. 운영 데이터 변환은 아직 수행하지 않았다.

### Q20 확정 — 자동 계산의 최소마진과 반올림 충돌

조사 당시 `MarginCalculator`는 계산 가격을 다음 100원으로 올린 뒤 최소마진 부족분을 더하고, `MarketSalePriceResolver`는 스마트스토어만 10원 단위 올림했다. 이 두 규칙을 공통 100원 반올림·최소마진 보정으로 대체했다.

사용자가 추천안을 수락했다. **최소마진을 우선 보장하고, 하한을 충족하는 100원 단위로 보정하며 사유를 표시한다.** 반올림가 12,300원 / 최소마진 하한 12,340원 → 최종가 12,400원이다. 이미 하한을 충족하거나 100원 단위인 값에 100원을 더하지 않는다.

자동 계산·마켓별 등록가·배치 계산에 공통 규칙을 연결했고, 배치 결과 메시지와 상품 상세의 ‘마켓별 가격 계산 근거’에서 보정 내역을 확인하도록 구현했다. 원가·마진 자료가 없는 기준가 대체 계산은 최소마진 미검증으로 표시한다. 운영 배포는 하지 않았으며 실제 구현 범위·남은 가격 경로는 [구현 기록](2026-09-06-products-implementation-progress.md)의 Q20 항목을 따른다.

- 그리드·상세 패널의 시각적 배치. 행 간격은 촘촘하게 기본, 필요 시 넓게 전환으로 사용자 확정.
- 상품명 조합 규칙과 필드별 확정 매핑. 잠금은 현재 활성 연결 기준(Q15 확정).
- 소싱처별 콘텐츠 갱신 지원 범위, 오래됨 기준 일수.최신 공통 템플릿 적용은 Q11 확정 사항.
- 확정된 Q8 상태별 처리의 API 판정 근거와 재등록 필수 정보. 삭제 사유를 마켓이 제공하지 않을 때의 표시와 처리.
- 일괄 편집의 값 지정/증감/비율 변경, 부분 적용·사전 검토, 페이지 간 선택 및 전체 결과 선택.
- 자동 반영 시점·주기·실패 알림과 재시도 한도. 심사 대상 수동 시작 정책은 Q6 확정 사항.
- 필요한 API 자료가 남으면 ‘마켓 / 업무 / 엔드포인트 또는 필드 / 현재 자료의 누락점’을 특정해 요청.
