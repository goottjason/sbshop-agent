# 카페24 재고·GTIN 실제 조회와 반영 확인 보완

2026-09-06. [API 버전 업그레이드](2026-09-06-cafe24-api-version-upgrade.md) 이후 사용자의 계속 진행 지시에 따라 운영 상품을 읽기 전용으로 대조하고, 기존 카페24 재고·바코드 전송 경로를 보완했다. 이번 코드는 로컬 구현·검증 상태이며 운영에 배포하지 않았다.

## 실제 운영 조회

2026-09-06 16:39 KST, 운영 DB의 카페24 인증과 상품번호를 읽기 전용 트랜잭션으로 읽었다. 앱 ID가 사용자가 업그레이드한 `younzara` 앱과 같은지 확인하고, 서버 메모리에서 기존 액세스 토큰을 사용했다. 토큰·비밀번호를 출력하거나 파일에 저장하지 않았다.

상품 3개에 대해 상품 상세 → 품목 목록 → 품목 상세 → 품목 재고의 **GET 12회**를 수행했다. 호출 사이에 0.7초 간격을 두었으며 모두 HTTP 200, 응답 헤더 `X-Cafe24-Api-Version: 2026-09-01`이었다. 관측한 `X-Api-Call-Limit`는 `0/40`이었다. 버전관리 화면뿐 아니라 실제 API 응답 버전도 확인했다.

| SB코드 | 카페24 상품번호 | 품목 코드 | 조회 재고 |
| --- | --- | --- | ---: |
| 200630WA013 | 7034 | P0000KKO000A | 500 |
| 210909FM017 | 14972 | P0000WDW000A | 333 |
| 210909FM023 | 14978 | P0000WEC000A | 333 |

세 상품 모두 `shop_no=1`, `has_option=F`, 단일 품목, 상품·품목 판매 중, `use_inventory=T`, `display_soldout=T`, `inventory_control_type=A`였다. `market_sync=T`이며 세금 계산은 `M`이었다. GTIN 값은 이번 조회 결과에서 확인되지 않았다. 자체 품목 코드는 첫 상품에서 SB코드와 같았고 다른 두 상품은 빈 문자열이었다.

따라서 무옵션이어도 품목과 재고 **조회**가 가능한 것은 확인했다. 무옵션 GTIN **수정**이 가능한지, 재고 변경이 G마켓·옥션으로 어떻게 전달되는지는 이 GET 결과로 확정하지 않는다. 기존 재고 500·333을 300으로 바꾸거나 외부 상품을 수정하지 않았다.

## 구현한 보완

문서 계약은 [라이브 API 대조 기록](2026-09-06-cafe24-live-api-contracts.md)과 [품목 재고 수정](https://apidocs.cafe24.com/docs/admin/put-products-by-product-no-variants-by-variant-code-inventories), [품목 수정](https://apidocs.cafe24.com/docs/admin/put-products-by-product-no-variants-by-variant-code)을 따른다.

- `Cafe24VerifiedProductAccess`: 계정, 상품번호, 쇼핑몰, 상품코드와 품목 코드의 대응을 검사한다. 품목이 여러 개이면 첫 품목을 선택하지 않고 보류한다. 빈 응답, 업무 오류, 다른 쇼핑몰·품목, 잘못된 수량을 성공 증거로 사용하지 않는다.
- 재고 변경에서 상품 수준 `supply_quantity`를 제거했다. 현재 품목 재고를 읽고 변경이 필요할 때 `/products/{product_no}/variants/{variant_code}/inventories`에 최상위 `shop_no=1`, `request.quantity`를 전송한다. 재고 사용·품절표시 설정은 임의로 변경하지 않는다.
- 가격과 재고를 함께 처리할 때 세금 계산 조건을 쓰기 전에 검사한다. 재고를 먼저 재조회하여 일치를 확인한 뒤 필요한 가격·판매 상태를 전송한다. 최종 상품과 재고가 일치하지 않으면 일부 반영 가능성을 표시하고 실패로 반환한다.
- 소싱처 품절의 판매 중지는 기존 판매용 수량을 지우지 않고 `selling=F`로 처리한다. 판매 중지 원인이 확인되지 않는 상품의 자동 판매 재개는 보류한다. Q10의 자동 복구를 완성하려면 시스템이 중지시킨 이력에 근거한 별도 복구 흐름이 필요하다.
- 시스템상품을 받는 재고 호출은 SB코드도 대조한다. 재조회 중 상품코드·SB코드가 바뀌거나 계정이 바뀌면 결과를 확정하지 않는다.
- GTIN은 숫자 문자열과 선행 0을 보존한다. 실제 품목의 현재 값이 같으면 재전송하지 않는다. 전송 본문의 `shop_no` 위치를 바로잡고, 별도 GET에서 목표 GTIN이 일치한 경우에만 캐시를 갱신한다. 타임아웃 뒤 재시도도 먼저 조회하므로 이미 적용된 GTIN은 다시 쓰지 않는다.
- 무옵션 GTIN 수정은 최신 버전의 쓰기 검증이 남아 있어 계속 보류한다. 과거 422를 모든 최신 버전에서 영구 미지원이라는 단정으로 표시하지 않는다.
- 성공 결과에는 확인한 필드·시각·상품/품목·`CAFE24_NATIVE_ONLY` 범위를 기록한다. 카페24 재고·바코드 일부 성공이 전체 `isSynced`나 전체 동기화 시각을 갱신하고 기존 HTML 등 다른 오류를 지우던 경로를 제거했다.
- 기존 `isSynced` 캐시가 참이라는 이유만으로 카페24 재고 재조회를 생략하지 않는다. 실제 값이 같으면 어댑터가 쓰기를 생략한다. 바코드의 기존 진입점에도 연결 해제·하위 마켓 영구 금지·진행 중 등록의 쓰기 차단을 추가했다.

## 지원 범위와 확인 대기

이 전송 경로는 **카페24 본상품이며 `market_sync=F`인 경우**에 한정한다. 마켓플러스 연결 여부가 T이거나 확인되지 않으면 전달 범위·결과 확인이 필요하다는 사유를 반환한다. 이번에 읽은 운영 샘플 3개는 모두 T이므로 새 경로에서 전송을 보류하는 대상이다. 운영 전체 상품이 같은 설정이라고 추정하지 않는다.

당시 별도 마켓플러스 수정·결과 조회 API 자료를 요청했으나, 이후 [자동 전송 재조사](2026-09-06-marketplus-auto-forwarding-recheck.md)에서 그 자료를 필수로 요구한 전제를 정정했다. 카페24 수정 → 마켓플러스 → G마켓·옥션 자동 반영이 공식 안내의 기본 경로다. 남은 확인은 현재 자동 전송 설정·필드별 기본/별도 설정·API별 전송 발생과 상품관리이력의 결과 근거다. 위 `market_sync=F` 제한은 검증 전의 임시 구현 제한이며 연동 상품의 영구적인 수정 불가 정책이 아니다. 카페24 본상품의 반영 성공을 G마켓·옥션의 성공으로 확대하지 않는다.

재고·GTIN의 새 DB 작업 큐, 스케줄러와 전체 기존 호출의 429 속도 통합, 시스템 품절 중지 이력에 따른 자동 복구, 무옵션 GTIN 쓰기 파일럿, 다중 품목의 SB코드 매핑, 소싱 이미지·HTML 비교 적용과 성공 시각 필터는 후속 범위다. 현재 재고·바코드 코드는 기존 전송 진입점을 보완한 것이며 가격용 영속 작업 큐의 전체 필드 확장이 아니다. 429 정보는 전파하고 일부 성공을 전체 성공으로 기록하지 않지만, 이번 코드만으로 모든 재고 재시도가 자동 실행되는 것은 아니다.

## 검증

- Infrastructure **139건**, Core **41건**, 총 **180건 통과**. 마지막 변경에 영향을 받지 않은 Core 검사는 직전 실행 결과가 유지되었고 마지막 명령에서 up-to-date였다. 이전 531건·38건과 중복 합산하지 않는다.
- 무옵션 단일 품목의 재고 계약, 전송 후 별도 조회, 수량·가격 일부 실패, HTTP 200 업무 오류, GTIN 선행 0·재전송 생략·응답 유실 후 재시도, 다중 품목 제외, 계정·상품·품목·쇼핑몰 불일치, 429 대기 전달, 마켓플러스·판매중단·재고 설정 차단을 검사했다.
- Core에서 필드 일부 성공이 기존 HTML 오류와 전체 동기화 시각을 지우지 않는지, 하위 마켓 영구 금지와 진행 중 등록이 기존 바코드 경로에서도 차단되는지 확인했다.
- 변경 Java 11개 파일에 한정한 Spotless 검사 통과. 프론트 수정은 없다. 실제 외부 API 검증은 앞의 GET 12회이며, PUT은 테스트 대역으로 검증했다.
