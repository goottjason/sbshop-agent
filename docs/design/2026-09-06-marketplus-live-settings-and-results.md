# 마켓플러스 실제 설정·전송 이력 확인과 배지 보완

2026-09-06 17:16~17:33 KST. 사용자가 열어 둔 Chrome의 마켓상품관리에서 공통설정·계정 설정·상품관리이력·표본 상품 수정 화면을 읽었다. 운영 DB와 서버 로그는 읽기 전용으로 대조했다. 외부 상품 전송, 설정 저장, 운영 DB 변경·배포는 실행하지 않았다.

## 현재 계정의 설정

| 항목 | 실제 선택값 |
| --- | --- |
| 마켓상품 자동전송 | 사용함 (`is_send_rtq=T`) |
| 전체 재고 0일 때 | 품절 또는 판매중지로 전송 (`use_sold_out=T`) |
| 상품명 길이 | 마켓 최대 길이로 자르기 (`is_split_prd_name=T`) |
| 연동 계정 | 옥션 `shouldbe2480`, G마켓 `younzara`; 한국어 쇼핑몰 1 |
| 두 계정의 연동 범위 | 상품정보 + 주문정보 |
| 두 계정의 카페24 진열/판매상태 연동 | 사용함 (`use_auto_selling=T`) |
| 두 계정의 판매기간 자동연장 | 무제한 (`selling_period_day=F`, 화면 문구로 확인) |

현재 마켓플러스의 연동완료 계정은 위 두 개였다. 스마트스토어·쿠팡·11번가는 연동가능 상태였다. 이는 SB의 직접 API 연결과 별개다.

첫 공통설정 로딩 중에는 라디오가 전부 선택 해제되어 있었다. 로딩 후 실제 `checked` 값으로 다시 확인했다. `F`를 항상 ‘사용안함’으로 해석하지 않는다. 판매기간의 `F`는 이 화면에서 ‘무제한’이었다.

## 실제 성공·실패와 SB 배치 대조

| SB코드 / 카페24 상품 | 운영 SB 로그와 카페24 재조회 | 마켓플러스 이력 |
| --- | --- | --- |
| `201005IHB002` / `10186` / `P0000PBU` | 배치 로그 16:00:06.568, 96,800원·`soldOut=false`. GET의 수정 시각도 16:00:06, `selling=T`, `display=T`, 가격 96,800원 | 16:02 옥션 `D888859044`, G마켓 `3490115053` 상품수정 전송 성공 |
| `210810IHB025` / `14086` / `P0000UVU` | 배치 로그 16:00:41.513, 179,100원·`soldOut=true`. GET의 수정 시각도 16:00:41, `selling=F`, `display=T`, 가격 179,100원 | 16:02 옥션 `D889144957`, G마켓 `3490363781` 모두 상품수정 전송 실패 |

실패 문구:

> 연동된 쇼핑몰상품이 '진열/판매'상태일 때만 판매중지를 해제할 수 있습니다. (관련 설정: 기본 > 마켓계정관리 > 마켓수정 > 카페24 진열/판매 연동 설정)

실패 상품의 운영 카페24 등록행은 `is_synced=true`, 마지막 동기화 시각은 UTC 07:00:41이었다. **카페24 품절 저장 성공과 하위 마켓 전송 결과가 다를 수 있음을 실상품에서 확인했다.** 이 문구는 429 재시도로 풀리는 오류나 영구 판매금지·삭제 근거가 아니다. 품절 요청과 마켓플러스가 판매중지 해제를 검사한 경로의 차이를 조사해야 한다. 오류를 없애기 위해 카페24 `selling`을 T로 바꾸지 않았다.

상품번호·가격·수정 시각과 배치 기록이 일치하므로 기존 SB 배치 이후 마켓플러스 전송이 발생한 정황을 확보했다. 별도 수동 전송이 섞였는지 질문했고, 사용자는 “너가 아까 테스트하면서 수정한 거 아니야? 그게 아니라면 기억은 안 나”라고 답했다. 수동 실행 여부는 **미확인**으로 기록하며, 실행하지 않았다는 확답으로 간주하지 않는다. 에이전트 작업 기록에는 승인받은 API 버전 설정 변경과 상품 GET·화면 읽기만 있으며 해당 상품 전송/중지해제 테스트는 없다. 서버 로그를 다시 읽어 16:00:41의 `product-batch-1`에서 카페24 상품 `14086`의 `soldOut=true` 처리를 재확인했다. 이 사실만으로 배치의 최초 실행자나 16:02 마켓플러스 작업의 단독 원인까지 확정하지 않는다. API 버전 변경의 간접 영향 역시 별도 검증 없이 배제하지 않는다. 새 품목 재고 API·GTIN·이미지·HTML의 각 수정 경로까지 동일하게 자동 전송된다고 일반화하지 않는다. 이번 상품 GET 두 건은 모두 200, 실제 응답 API 버전은 `2026-09-01`이었다.

이력 기간은 **2026-08-06~2026-09-06**이었다. 당시 성공 이력 30,447건, 실패 이력 5,847건, 상단 처리필요 전송실패 589가 표시되었다. 서로 다른 집계이며 이력 건수를 고유 상품 수로 취급하지 않는다. 최신 실패 20행은 위 진열/판매상태 사유였지만 전체 5,847건이 같은 원인이라고 단정하지 않는다. 목록 `No`는 탭별 순번으로 보여 영구 작업 ID로 사용하지 않는다.

## 같은 상품의 마켓별 상속 차이

표본 `201005IHB002`의 체크박스 값과 화면에 실제 렌더링된 ‘기본/별도’를 함께 읽었다. 설정을 바꾸지 않았다.

| 상품명 | 별도 | 별도 |
| 판매가 | 기본 | 기본 |

| 옵션/재고 | 기본 | 기본 |

카페24 이미지만 바꾼 뒤 이 표본의 옥션 이미지까지 자동 갱신했다고 표시하면 안 된다. 이미지 비교에는 마켓별 ‘별도 관리 중’과 전환 후 변경값을 보여 주는 설계가 필요하다. 원래 설정을 일괄 덮어쓰지 않는다. 상품명 ‘별도’는 상속 설정이며 그 자체로 마켓 정책상 변경 불가를 뜻하지 않는다.

두 마켓의 표본 수정 화면은 가격 96,800원, 재고 500을 표시했다. 기존 SB 로그의 `qty=999`는 메서드 인자이며 실제 품목 재고 반영 근거가 아니다. 이 화면 값도 마켓에서 직접 새로 조회한 최종 판매값으로 간주하지 않는다. [재고 전송 보완](2026-09-06-cafe24-inventory-and-gtin-verification.md)의 별도 품목 재고 GET 검증이 필요한 이유다.

## 이번 코드 보완

- 카페24에 보관한 G마켓·옥션 상품번호를 곧바로 `SYNCED`로 반환하던 코드를 **`UNVERIFIED` / `MARKETPLUS_RESULT_UNVERIFIED`**로 변경했다. 상품 링크는 보존한다.
- 실제 React 배지는 ‘G마켓 미확인’, ‘옥션 미확인’과 설명을 표시한다. 클릭은 상품 페이지를 열며 등록·재전송을 실행하지 않는다. 카페24 성공·실패를 하위 마켓 결과로 복사하지 않는다.
- 영구 판매금지·연결 해제는 미확인보다 우선한다. 미확인을 미등록이나 신규 등록 대기로 바꾸지 않는다.
- 신규 등록 안내에서 API 부재를 단정하던 문구를 제거하고 마켓플러스에서 대상·내용을 확인하는 실제 절차를 설명한다.

**로컬 구현이며 운영 미배포다.** 이번 실패 이력을 DB에 자동 수집하거나 재시도까지 연결한 것은 아니다. 수집 기능 연결 전 기존 G마켓·옥션 연결은 ‘미확인’으로 표시된다. 카페24 연동 T에 대한 기존 쓰기 제한도 아직 해제하지 않았다.

## 가격 설정 조회의 403

동일 운영 자격증명의 `GET /admin/products/setting?shop_no=1`은 **403**을 반환했다. 상품 두 건 조회는 200이었다. 문서상 상품 설정 조회 권한은 `mall.read_store`이며 현재 `Cafe24TokenManager.generateAuthorizationUrl`에는 이 scope가 없다. 실제 앱 허용 권한과 재인증 범위를 확인해야 한다. API 버전 업그레이드와 OAuth 권한 추가는 별개다. 이번에는 재인증·외부 앱 권한 변경을 실행하지 않았다.
