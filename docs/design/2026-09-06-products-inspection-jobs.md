# 선택 상품 상태 확인 작업·429 재시도 — 2026-09-06

**로컬 구현·검증 완료, 운영 미배포.** [연결 해제 단계](2026-09-06-products-connection-lifecycle.md)에 이어 선택 상품의 스마트스토어 조회를 DB 작업으로 처리한다. 이번에 운영 API·DB·외부마켓을 호출하거나 배포하지 않았다.

## 화면에서 제공하는 기능

상품 관리의 `마켓 상태 확인·작업`에서 선택 상품을 접수한다. 선택이 없어도 최근 작업은 열 수 있다. 현재 자동 판정이 검증된 스마트스토어만 대상이며, 연결 없음·상품번호 없음·이미 해제·다른 확인 작업 진행 중인 상품은 이유와 함께 제외한다.

- 작업별 대기·진행, 상태 확인, 연결 해제, 확인 필요, 제외 건수를 구분한다. 처리율 100%는 전부 판매 정상 또는 동기화 완료라는 뜻이 아니다.
- SB코드·외부 상품번호·시도 횟수·관측 상태·결과 코드·사유·다음 재시도 예정 시각을 표시한다.
- 확인 필요 상품만 보거나, 실패·미확인·연결 변경·계정 확인 필요 상품을 현재 연결 기준으로 다시 확인한다. 재확인은 새 작업으로 남기므로 원래 실패 이력은 유지한다.
- 접수 응답 유실 후 같은 버튼은 같은 요청 ID를 사용한다. 같은 요청이 이미 접수되었으면 기존 작업을 반환한다. 접수가 확인되면 해당 선택의 접수 버튼을 잠근다. 새 선택 작업은 창을 다시 열어 접수한다.
- 진행 조회가 실패하면 이전 상세 결과를 숨기고 확인 불가를 표시한다. 새로고침 후 최근 20개 작업을 다시 조회할 수 있다. 닫기·페이지 새로고침으로 서버 작업을 취소하지 않는다.

## 작업·재시도 계약

`sb_market_inspection_batch`, `sb_market_inspection_task`, `sb_market_inspection_gate` 세 테이블을 추가했다. 접수 시 상품·마켓 상품번호·등록 버전·전체 식별자·조회 앱 참조를 고정한다. 시스템상품 변경값을 외부에 쓰는 큐는 아니다.

요청당 최대 5,000개, 전체 대기/진행 항목은 최대 20,000개다. 상품·등록 정보와 이미 실행 중인 상품은 일괄 조회한다. 중복 요청 ID는 인증 작업자와 정규화된 선택 목록까지 동일할 때만 기존 결과를 반환한다. 다른 작업자의 키나 다른 선택에 재사용하면 409다. 같은 상품의 겹치는 작업도 접수 시 제외한다.

조회 작업자는 DB 잠금으로 한 항목을 선점하고, 180초 임대 토큰을 기록한 후 잠금을 풀고 외부 조회를 한다. 여러 앱 인스턴스가 동시에 같은 작업을 가져갈 수 없다. 시각은 DB의 `CURRENT_TIMESTAMP`를 사용한다. 완료 시 토큰과 임대 만료, 원래 연결 버전·식별자를 다시 확인한다. 임대가 만료되었거나 새 작업자가 인계받았다면 이전 결과를 적용하지 않는다.

작업 결과, 판정 근거, 연결 해제, 해당 연결의 변경 대기 취소를 한 트랜잭션에서 저장한다. 저장 실패 시 전부 되돌리며, 실행 중 상태를 성공으로 바꾸지 않는다. 서버 중단이나 저장 실패로 남은 실행 중 작업은 임대 만료 후 재시도한다. 반복 중단도 5회에서 실패로 종료한다.

| 상황 | 처리 |
| --- | --- |
| 정상 존재·품절·일반 정지 | 상태 확인 기록, 연결 유지. 필드 동기화 성공 표시 없음 |
| 명시적 삭제 상태·영구 판매금지 | 근거와 연결 해제 저장 |
| 정확한 상품 조회의 404 `NOT_FOUND` | 아래 계정 귀속 조건 충족 시만 해제 |
| 429 | 연결 유지, 해당 조회 큐 전체의 다음 호출을 지연 |
| 5xx·네트워크 접근 오류 | 연결 유지, 항목별 자동 재시도 |
| 권한·인증·잘못된 응답·미검증 상태 | 미확인으로 종료, 사유 확인 후 수동 재시도 |
| 조회 도중 연결 변경 | `STALE`, 이전 상품번호 판정을 새 연결에 적용하지 않음 |
| 대기·조회 도중 계정 변경 | `ACCOUNT_CHANGED`, 미확인으로 종료 |

자동 재시도는 최초 실행 포함 최대 5회다. 기본 대기는 30→60→120→240초에 0~5초의 작은 무작위 지연을 더한다. 서버가 `Retry-After`를 제공하면 로컬 대기와 비교해 더 늦은 시각을 따른다. 마지막 429에서도 다른 대기 작업에 공유 지연을 유지한다. 헤더의 초 단위/HTTP 날짜 형식은 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)에 따라 해석한다.

일반 성공 후 다음 작업은 최소 2초 뒤 시작한다. 이 값은 우리 조회 큐의 보수적인 초기 간격이며 마켓의 공식 허용량을 뜻하지 않는다. 네이버는 [요청 제한이 유동적이라고 안내](https://apicenter.commerce.naver.com/docs/restriction)한다. **이번 공유 제한은 새 일괄 조회 큐에만 적용**되며, 기존 단건 조회·가격/재고·주문 API 전체의 제한 통합은 아니다.

스마트스토어 HTTP 클라이언트에 연결 10초·응답 30초 제한을 설정했다. 같은 클라이언트를 쓰는 기존 요청에도 적용된다. 시간 초과는 조회/응답 실패이며 외부 작업이 수행되지 않았다는 증거로 취급하지 않는다. 새 작업 스케줄러는 기존 주문·재고 스케줄러와 별도 스레드로 실행한다.

## 계정 귀속 보호와 Q&A

현재 데이터 모델에는 마켓당 하나의 연동 앱이 있고, 과거 각 상품번호의 판매 계정 귀속은 별도 저장하지 않았다. 다른 계정의 상품번호를 현재 계정으로 조회한 404를 삭제로 오인하지 않도록 보호를 추가했다.

Q23은 **전체 상품 하루 1회 + 선택 즉시 확인**, Q24는 **현재 연동된 한 계정의 상품**으로 확정했다. 이후 [정기 확인 단계](2026-09-06-products-daily-inspection.md)에서 매일 오전 3시 접수와 계정 확인 근거의 DB 저장을 구현했다. 운영 미배포다.

최초 초기화 시 현재 SELF 앱 참조를 한 번 고정한다. 저장값과 현재 앱 참조가 일치해야 정확한 상품 조회의 404 `NOT_FOUND`로 연결을 해제할 수 있다. 앱이 바뀌면 정기 접수는 보류하고, 부재 응답은 `ACCOUNT_REVIEW_REQUIRED`로 연결을 유지한다. 기존 상세 단건 확인에도 같은 보호가 적용된다. 명시적인 `DELETE`·`PROHIBITION`과 판매자 직접 확인은 별도 근거다. 수동 환경 설정 `MARKET_INSPECTION_VERIFIED_ACCOUNT_REFERENCE`는 DB 고정값이 없을 때만 사용한다. 비밀키·토큰은 참조값에 저장하지 않는다.

PostgreSQL DDL 실행·부하 검증은 아직 하지 않았다. 운영에서는 기존 쓰기를 멈추고 진행 중 작업을 마친 뒤 스키마와 앱을 함께 전환한다. 구버전으로 되돌리면 연결 보호가 유지되지 않으므로 기존 연결 단계의 롤백 조건을 따른다. 새 작업 테이블·이력은 삭제하지 않는다.

남은 범위는 다른 마켓의 계정별 판정 계약, 모든 API의 제한 공유, 외부 **쓰기** 작업의 버전별 동기화·성공 검증·선택 재등록이다. 작업 목록의 서버 페이지 처리, 오래된 작업 정리와 취소 UI도 아직 없다. 이번 조회 임대로 기존 외부 쓰기 요청의 경쟁 구간까지 해결한 것으로 보지 않는다.
