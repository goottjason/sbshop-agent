# 상품 편집 검토·실제 저장·변경 이력 — 2026-09-06

**로컬 구현·검증 단계이며 운영 미배포다.** 기존 운영 배포는 `02142157`이고, 이번 변경을 운영 DB나 외부마켓에 적용하지 않았다. 이 문서는 전체 개편 중 시스템상품 저장 단계의 구현 범위를 기록한다.

## 사용자에게 제공하는 흐름

1. 상품 상세에서 수정 가능한 필드를 편집하거나, 목록에서 상품을 선택해 숫자 필드의 값 지정·증감·비율 변경을 입력한다.
2. 변경 검토에서 실제 저장할 값, 반올림·수량 버림, 최소마진 보정, 파생 변경, 제외 사유, 연결 마켓과 계산 가격을 확인한다.
3. 검토한 상품을 저장한다. 한 상품의 변경값은 전부 함께 저장하거나 전부 제외한다. 여러 상품 중 다른 상품의 실패는 나머지 상품의 저장을 되돌리지 않는다.
4. 상세 화면에서 작업자·저장 시각·변경 전후 값과 마켓 미반영 기록을 조회한다. 목록에는 미반영 기록 수를 표시한다.

새 화면은 판매가만 먼저 저장하던 기존 분리 요청을 사용하지 않는다. 요청 응답을 받지 못한 경우 같은 검토 ID로 재시도하며, 서버에 이미 저장된 변경은 중복 적용하지 않는다. DB 저장 완료를 마켓 반영 완료로 표시하지 않는다. **자동 마켓 전송은 아직 제공하지 않는다.**

## 이번에 적용한 편집 조건

후속 [연결 모델](2026-09-06-products-connection-lifecycle.md)의 활성 연결만 편집 조건에 반영한다. 아직 확정 해제하지 않은 기존 등록 기록은 보수적으로 해석한다. `RECORDED`는 등록 기록이 있다는 뜻이며 현재 판매 정상·정보 일치를 보증하지 않는다. `REVIEW_REQUIRED`는 기존 오류·삭제 표시 등의 확인이 필요하다는 뜻이다. `REGISTRATION_UNCONFIRMED`는 외부 상품번호가 없어 생성 결과를 확인해야 한다는 뜻이다.

| 조건/필드 | 현재 처리 | 후속 작업 |
| --- | --- | --- |
| 내부 메모 | 연결 유무와 관계없이 허용. 마켓 미반영 대상은 만들지 않음 | 없음 |
| 활성 연결이 없는 상품 | 검증을 통과한 필드 편집 허용. 상품명 조합 필드 변경 시 이름 함께 재조합 | Q21 확정·활성화, Q15 모든 연결 해제와 연계 완료 |
| 외부 상품번호가 없는 등록 기록 | 메모 외 변경 보류 | 생성 여부 확인 및 등록 중 상태 분리 |
| 외부 상품번호가 있는 상품의 가격 7개 필드 | 판매가·원가·마진율·쿠폰율·최소마진·환율·배송비 변경 검토 및 저장 | 마켓별 가격 반영 작업과 결과 확인 연결 |

| 연결 상품의 재고 | 판매용 설정 수량 계약 전까지 확인 필요 | 기본 300개 판매 수량과 소싱 품절·재입고 분리 |

카페24 GTIN을 바코드 수정 지원으로 간주하지 않으며, 11번가 `makerNm`도 지원 근거로 사용하지 않는다. 기존 `DELETED_ON_MARKET`나 오류 문자열만으로 연결을 해제하거나 카테고리를 열지 않는다. Q15의 “모든 활성 연결 해제 후 편집 허용”은 후속 연결 모델에 구현했으며, 해제 후에도 식별자와 근거 이력을 보존한다.

## 저장 및 API 계약

| API | 역할 |
| --- | --- |
| `GET /api/v1/products/{id}/edit-workspace` | 상품 버전, 필드별 편집 조건·사유, 기존 연결 기록 해석 |
| `POST /api/v1/products/{id}/changes/preview` | `{expectedRevision, values}`를 검토하고 저장 가능한 값 확정 |
| `POST /api/v1/products/changes/preview` | 기존 숫자 일괄 변경 요청을 상품별로 검토 |
| `POST /api/v1/products/changes/commit` | `{reviewId}`만 받아 서버에 보관한 값 저장 |
| `GET /api/v1/products/{id}/change-history` | 새 경로에서 저장한 최근 50건의 변경 이력과 미반영 대상 |

- `sb_product.revision`을 JPA 버전으로 관리한다. 검토 후 상품 버전, 등록 기록의 식별자·상태·오류, 가격 계산 결과 또는 편집 조건이 달라지면 다시 검토해야 한다.
- 검토는 인증된 요청자에 귀속되며 유효 시간은 30분이다. 본문의 작업자 필드는 신뢰하지 않는다. 저장 시 클라이언트가 변경값을 다시 보내지 않는다.
- 상품별 잠금과 트랜잭션으로 상품 수정·변경 이력·미반영 대상을 함께 저장한다. 대상 기록 저장에 실패하면 상품과 이력도 되돌린다.
- 검토 ID와 상품 ID의 유일성 및 상품 잠금으로 동시·순차 재시도 중복 저장을 막는다. 이미 성공한 상품은 검토 만료 후 재시도에도 기존 결과를 반환한다.
- 신규 마켓 등록 준비는 읽었던 상품 버전을 확인하고 상품 잠금 아래 등록 대기 기록을 만든다. 기존 강제 재등록·등록정보 가져오기 전체가 새 연결 계약으로 전환된 것은 아니다.
- `SAVED`, `CONFLICT`, `FAILED`, `EXCLUDED`, `UNCHANGED`, `NOT_FOUND`를 상품별로 반환한다. 실패 상품은 같은 검토 ID 재시도, 충돌 상품은 새 검토가 필요하다.
- 가격 검토는 현재 4개 직접 연동 마켓의 계산과 최소마진 하한을 확인한다. 자료가 없어 하한을 검증할 수 없으면 저장 제외한다. 반올림가가 하한보다 작으면 하한을 충족하는 100원 단위로 보정한다.
- 가격 및 파생 결과와 반올림·버림 사유를 검토 원문에 보관한다. 바코드의 선행 0과 무게·용량의 저장 정밀도를 화면 편의를 위해 변경하지 않는다.
- 미반영 대상은 `PENDING_DISPATCH`로 기록한다. 카페24와 기록이 있는 G마켓·옥션은 별도 대상이다. 아직 전송·재시도 작업자가 없으며, 기록 수는 미반영 변경 건수이지 서로 다른 마켓 개수가 아니다.

## 기존 경로와 남아 있는 제약

기존 전체 필드 수정, 수동 일괄 전체 필드 수정, 브랜드·바코드 보완, 이미지 저장은 공통 편집 조건과 이력 저장 경로로 연결했다. 잠긴 필드가 요청에 포함되더라도 값이 변하지 않으면 허용된 다른 필드의 저장을 막지 않는다. 이미지 업로드는 외부 저장소 업로드 전에 편집 조건을 확인하고 DB 저장 직전에 다시 검토한다.

다음은 이번 범위에 포함되지 않았다.

- 기존 가격·재고 직접 수정 및 소싱 배치 경로 전체의 새 검토·이력·미반영 계약 전환. 기존 직접 쓰기·반영 동작이 남아 있으므로 전체 쓰기 경로 통일 완료로 볼 수 없다.
- 판매용 재고 기본 300개 저장, 품절 중 설정 보존과 재입고 복구.
- 비숫자 필드의 일괄 편집 UI, 이미지·HTML 최신 콘텐츠 비교 후 선택 적용, 성공 갱신 시각.
- 마켓별 필드 변경 가능 조건의 전체 조사·확정. 현재 잠금은 임시 확인 필요 상태를 포함한다.
- 마켓별 등록·미등록 AND 필터, 실패·오래된 콘텐츠 필터, 조치 필요 순 정렬.
- 변경 버전별 외부 동기화·429 제어·실패 사유·재시도·외부 반영 확인.
- 단건 상태 확인·판매자 확인을 넘어선 전체 마켓 자동 판정과 일괄 스케줄러, 선택 재등록. 단건 연결 해제·과거 이력 보존은 후속 연결 모델에 구현했다.
- 과거 편집 이력 소급 복원, NULL로 값을 지우는 별도 계약, 검토 기록 보존 기간/정리 작업.

기존 전체 수정의 작업자는 `system:legacy-product-edit`, 수동 배치는 `system:batch-full-edit`처럼 호출 출처로 남긴다. 새 화면의 저장은 실제 인증 사용자로 남긴다. 기존 경로도 실제 작업자를 전달하도록 통일하는 일은 후속 작업이다.

## 스키마 및 운영 반영 전 조건

[DDL](../../backend/docs/ddl/2026-09-06-product-edit-review.sql)에 상품 버전과 검토·이력·미반영 대상 3개 테이블을 정의했다. 기존 상품값·등록 식별자를 변경하지 않는다. 운영 백업 후 DDL을 먼저 적용하고 프론트·백엔드를 함께 배포해야 한다. 이번 작업에서는 운영 SQL·배포를 실행하지 않았다.

H2 통합 테스트는 실제 트랜잭션을 사용하지만 운영 PostgreSQL 마이그레이션 검증은 아직 하지 않았다. 새 이력의 FK는 이력이 있는 상품·등록 행의 물리 삭제를 막는다. 기존 정상 상품 삭제는 소프트 삭제이므로 이력을 보존하지만, 별도 물리 삭제 경로는 이력 보존 정책에 맞게 확인해야 한다. 롤백 시 이력 테이블과 버전 열을 삭제하지 않는다. 후속 연결 모델 적용 시 구버전은 해제 상태를 무시하므로, API/worker 혼합 운영 및 롤백 시 마켓 쓰기 중지가 필요하다. 상세 조건은 연결 구현 기록을 따른다.
