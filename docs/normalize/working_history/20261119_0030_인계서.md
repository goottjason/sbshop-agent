## 4. 통합 시험 — 서버 임시 DB (D1 ①)
운영 쓰기 등급 W1(가역 — 임시 DB를 지우면 끝). **승인 요청에 아래 명령을 그대로 보여 준다.** 이 절차 자체도 실행된 적이 없다.

- 사전 확인(읽기): 진행 중인 배포(`gh run list`), 도는 소싱처 배치(`sb_supplier_batch_run`의 `RUNNING`·`PAUSING`), 디스크 여유. 시험 부하는 작다(행 100개짜리 테이블 몇 개, 1~2분).
- 접속: 주 세션만 한다. 하위 에이전트에게 서버를 맡기지 않는다.

```bash
# 1) 임시 DB — 관리 계정으로. 이름을 눈으로 확인한다
docker exec projects-postgres-1 psql -X -U goottjason -d postgres -v ON_ERROR_STOP=1 \
  -c "CREATE DATABASE sbshop_dbwrite_test OWNER sbshop"
docker exec projects-postgres-1 psql -X -U goottjason -d sbshop_dbwrite_test -v ON_ERROR_STOP=1 \
  -c "GRANT CONNECT ON DATABASE sbshop_dbwrite_test TO sbshop_ro" \
  -c "ALTER DEFAULT PRIVILEGES FOR ROLE sbshop IN SCHEMA public GRANT SELECT ON TABLES TO sbshop_ro"

# 2) 파일 두 개를 저장소 밖 임시 폴더로 (PC에서 scp)
#    tools/dbwrite/sbshop_db_write.py, tools/dbwrite/test_integration_pg.py → ~/ops-write-test/ (700)

# 3) 실행
cd ~/ops-write-test
BASE='"/usr/bin/docker","--context","default","exec","-i","projects-postgres-1","psql","-X","-U"'
TAIL='"-d","sbshop_dbwrite_test","-v","ON_ERROR_STOP=1","-f","-"'
SBSHOP_DBWRITE_TEST_PSQL="[$BASE,\"sbshop\",$TAIL]" \
SBSHOP_DBWRITE_TEST_PSQL_RO="[$BASE,\"sbshop_ro\",$TAIL]" \
python3 -m unittest test_integration_pg -v

# 4) 정리 — 이름을 눈으로 확인한다. sbshop 이 아니다
docker exec projects-postgres-1 psql -X -U goottjason -d postgres -v ON_ERROR_STOP=1 \
  -c "DROP DATABASE sbshop_dbwrite_test"
rm -r ~/ops-write-test
docker exec projects-postgres-1 psql -X -U sbshop_ro -d sbshop -Atc "SELECT datname FROM pg_database ORDER BY 1"
```

- **기대:** 18개 전부 통과. 시험은 시작할 때 두 접속의 DB 이름이 `_test`로 끝나지 않으면 전부 중단한다.
- **알아둘 것:** 시험의 쓰기 역할 `sbshop`은 앱이 쓰는 역할과 같다. 그래서 잠금 시험의 `pg_terminate_backend`는 `datname = current_database()`로 임시 DB 안의 접속만 겨눈다. 임시 DB 밖에는 아무것도 쓰지 않는다.
- **이 절차의 미확인 가정:** 새 DB에서 `sbshop`(소유자)이 public에 테이블을 만들 수 있다, `sbshop_ro`의 역할 설정(`default_transaction_read_only`)이 임시 DB에서도 적용된다. 1)에서 오류가 나면 멈추고 보고한다.

### 시험이 깨질 때
| 무엇이 다른가 | 할 일 |
|--------------|------|
| 오류 **문구**·출력 모양(예: `duplicate key …`, `lock timeout`, 표의 정규식) | 시험의 기대값을 실제에 맞춘다. 도구는 그대로. 표준 등급 |
| 표지·태그의 **형식**(psql이 `NOTICE:`·`ERROR:`·`COMMIT`·`SBW|END|…`를 다르게 낸다) | 도구의 파싱이 틀린 것이다. 고치면 단위 게이트 + 검증자 재확인. 설계 §4-4의 판정 전제에 닿으면 멈춘다 |
| **동작**(롤백돼야 하는데 값이 바뀜, 흔적이 남음, 백업한 행 ≠ 바꾼 행, PL/pgSQL 구문이 거부됨) | **멈춘다.** 고쳐 쓰지 않는다. 설계서 §9 — 고정 결정에 닿는 설계 변경이다(페이블) |

도구 파일을 고치면 `--version` 해시가 바뀐다. 이 문서 §2와 설치 대조값을 새 값으로 쓴다.

### 실 DB에서 확인해야 할 것 (검증자 목록 — 통합 시험이 대부분 덮는다)
1. `DO` 본문의 `#variable_conflict use_column`이 받아들여지는가.
2. `psql -f -`의 NOTICE/ERROR 줄, 표준 출력의 명령 태그 `COMMIT`/`ROLLBACK`, `\echo SBW|END|…`가 줄 그대로 나오는가 — "끝까지 실행됨" 판정이 이 셋에 기댄다.
3. PL/pgSQL 변수 `_sbw_tids`(`tid[]`)가 `CREATE TABLE … AS`·`UPDATE`·`DELETE`의 `ctid = ANY`에서 동작하는가.
4. `CREATE TABLE … AS` 직후 같은 `DO`에서 그 테이블을 셀 수 있는가.
5. `WITH … INSERT … RETURNING *` 뒤의 `ROW_COUNT`.
6. `lock_timeout`이 행 잠금 대기에 걸리는가.
7. `sbshop`이 만든 테이블을 `sbshop_ro`가 읽는가.
8. 컨테이너 psql에서 한글 조각이 그대로 저장되는가.
9. 비결정 조건(`ORDER BY random() LIMIT`)에서 백업한 행 = 바꾼 행인가, K14의 각 거부 경로.
10. `DO` 안의 오류가 종료코드 3이 되고 `COMMIT` 태그·끝 표지가 나오지 않는가.
11. *(시험이 덮지 않음)* `docker exec` 클라이언트가 죽어도 컨테이너 안 psql이 계속 돌아 커밋하는가 — `committed=unknown` 규칙의 근거. 임시 DB에서 `pg_sleep`이 든 스크립트로 한 번 확인하면 좋다. 확인하지 못해도 규칙은 안전한 쪽이다.
12. *(시험이 덮지 않음)* 운영 `pre` 덤프가 10분 안에 끝나는가 — 백업 로그의 `secs=`(지금 45초).
