## 진단 — 한 달간 불명이던 사유를 어떻게 잡았나

`sb_action_log`에는 `Cafe24 API POST 호출 실패`만 남아 있었다(컨테이너 재생성으로 원본 로그는 소실).
원인은 **D-152** — `enrich()`가 `get()`에만 적용돼 다른 동사의 상태코드·본문이 최상위 메시지에서 사라졌다.
액션로그·화면은 최상위 메시지만 보므로 원인 체인에 남아도 사람에게 닿지 못한다.

재전송을 1회 유발해 원문을 확보했다:

```
422 {"error":{"code":422,"message":"You cannot change to that order state.",
     "more_info":{"status":"shipping","order_id":"20260630-0000017", ...}}}
```

Cafe24 읽기 조회로 상태를 확인했다 — 두 주문 모두 **이미 배송중(N1)이고 배송건이 하나 등록돼 있었다**
(`shipping_code=D-...-00`, `tracking_no=00000000` 더미). 배송중 주문에는 배송건을 새로 만들 수 없다.

## 반전 — 두 번의 교정 (이 사이클의 핵심 교훈)

### 1차 가설과 그 한계

`PUT /admin/orders/{order_no}/shipments/{shipping_code}` 라우트 존재를 라이브로 확인하고
(없는 코드로 PUT → `404 parameter.shipping_code` / 대조군 없는 경로 → `No API found`),
"Cafe24에는 수정 경로가 있다 — 11번가·네이버와 정반대"라고 판단해 D-151을 배포했다.

### 배포 직후 라이브가 뒤집은 것

PUT은 정상 동작했지만 Cafe24가 **다른 사유**로 거부했다 — 그리고 D-152 덕에 그 사유가 보였다:

```
422 Shipping information (tracking number, shipping carrier code)
    cannot be edited for marketplace orders.
```

**G마켓·옥션처럼 마켓에서 연동된 주문은 Cafe24 API로 송장을 고칠 수 없다.** 결국 11번가·네이버와
같은 결론이고, 사람의 조치 경로는 Cafe24 관리자가 아니라 **G마켓·옥션 판매자센터(ESM+)**다.
게다가 문구가 바뀌며 기존 Cafe24 조건에 걸리지 않아 **영구 거부가 재시도 대상으로 샜다**(D-154).

### 하마터면 — 최초 전송을 깨뜨릴 뻔한 것

배포 후 점검에서 발견: **Cafe24는 발송 전에도 배송건 `D-...-00`을 미리 만들어 둔다.**

```
20260807-0000011 (아직 우리 송장 없음) → 배송건 1건 존재, tracking 없음
20260723-0000018                       → 배송건 0건
```

"배송건이 있으면 수정"은 너무 넓은 기준이었다 — 최초 전송까지 수정 경로로 새고, 위 제약 탓에
**송장이 영영 마켓에 못 들어갔을 것이다.** 판정 기준을 "배송건 존재"에서
**"마켓이 실송장을 들고 있는가"(`ShippingData.isMeaningfulTracking`)**로 좁혔고,
모호 실패도 *수정 대상이 여럿일 때*로 한정했다(다건 주문의 첫 전송을 막지 않기 위해).

> **교훈 2가지**
> 1. **동사를 바꾸면 거부 문구도 바뀐다** — 마켓 호출 방식을 바꿀 때는 영구 거부 분류 목록을 함께 봐야 한다.
> 2. **"있으면 수정"은 마켓이 자리표시자를 미리 만들어 두는 곳에서 위험하다** — 존재가 아니라 *의미 있는 값의 존재*로 판정할 것.
