# 2026-09-19 20:40 결과서 — 마켓별 품절 표현 통일(안 A)과 카페24 예외 확정

## 이 사이클에서 정해진 것

사용자와 문서·운영 데이터를 대조해 **품절 처리 방식**을 확정했다.

- **쿠팡·스마트스토어·11번가: "품절 = 재고 0"** (정석 루트, 세 마켓 모두 이미 그렇게 동작 — **코드 무변경**)
- **카페24: 예외.** 재고관리(`use_inventory`)는 항상 T, 수량은 **300 고정**, 품절·판매는 본상품 `selling` T/F로만 표현한다. **재고 0을 보내면 마켓플러스가 G마켓·옥션으로 전송할 때 연동 오류가 난다**(사용자 확정).

근거가 된 공식 문서(사용자 제공):
- 스마트스토어 `(v2) 원상품 수정`: 수정 시 입력 가능한 `statusType`은 **SALE·SUSPENSION뿐**이고, **`StockQuantity`가 0이면 상태가 자동으로 `OUTOFSTOCK`(품절)**이 된다. 즉 품절은 지정하는 상태가 아니라 재고 0의 결과다. 품절→판매중 복귀 시에는 `StockQuantity`와 `statusType=SALE`을 함께 보내야 한다.
- 11번가 `판매중지처리`/`판매중지해제처리`: `stopdisplay`는 "전시를 **일시적으로** 중지"(→105), `restartdisplay`는 →103. 상태표에 **104 품절이 별도로 존재**한다.
- 쿠팡 `판매 중지`/`판매 재개`/`수량 변경`: 셋 다 승인완료·`vendorItemId` 필요. 재개 실패 사유에 **"쿠팡의 모니터링에 의해 '판매중지'된 상품"**이 있어, 쿠팡이 내린 중지는 API로 재개되지 않는다.

**안 1(판매중지 + 수량 보존으로 전 마켓 통일)은 기각**했다. API로는 4마켓 모두 가능하지만, 네이버는 품절 대신 판매중지로 보이고(노출에서 빠짐), 배치의 완료 판정 체계를 전면 개편해야 하며, "우리가 내린 중지"를 구분할 표식이 없어 사람이 내려둔 상품을 배치가 되살릴 위험이 있다.

## 발견한 결함 (원장 D-308~D-312)

경로가 둘로 갈려 있다는 것이 모든 문제의 뿌리였다.

| 경로 | 누가 쓰나 | 카페24 품절 처리 |
|---|---|---|
| **reviewed** (`MarketStockSyncService`·`MarketPriceSyncService`) | **소싱처별 배치**(운영에서 실제 도는 배치), 상품관리 "마켓 판매용 수량 반영" | 규칙 위반 — `selling=F` 뒤 **`{"quantity":0}` 무조건 PUT** |
| **legacy** (`syncPriceAndStock`) | 상품관리 가격/재고 수정, 수동 일괄 업데이트 | 규칙 준수 — `!soldOut` 조건이라 수량 미전송 |

- **D-308(중대)**: 소싱처 배치가 카페24에 재고 0을 전송. **운영 실측 — 카페24 최종 관측 기준 수량 0 + 판매안함 272건, 그중 235건이 G마켓·옥션 연동 상품.** 목표수량 0 작업 592건에 쓰기 333회 기록.
- **D-309(중대)**: reviewed 경로에 마켓플러스 연동 차단이 없다(레거시는 `requireNativeWrite`로 차단). D-308의 재고 0이 연동 상품에 나간 경로.
- **D-310(중대)**: 가격 경로가 재고 상태를 보지 않는다. 카페24 `readSalePrice`는 `selling=F`여도 `writable=true`라, **어제도 오늘도 품절인 상품의 가격이 환율로 바뀌면 매번 PUT이 나갔다** — [[D-262]]가 막으려던 전송이 reviewed 가격 경로에는 적용된 적이 없다.
- **D-311(경량, 미수정)**: D-262의 `changed` 스킵이 무력화됐다. 플래그가 `syncInternal`까지 전달되지만 **본문에서 한 번도 쓰이지 않고**, 회귀 테스트도 "전달 여부"만 단언한다.
- **D-312(기록)**: 같은 날 오전 D-304에 "품절 = `use_inventory=F`"를 사용자 확정 사실로 적었으나 오후에 "재고관리는 항상 T"로 정정됐다. D-304가 추가한 `use_inventory=F` 분기는 실전에서 걸리지 않는 안전망으로 남는다.

## 수정 내용 (D-308·309·310, 커밋 `5d5d3517`)

본코드는 2개 파일만 바뀌었다.

- `Cafe24MarketClient.writeStockQuantity` — 보낼 필드를 4개 불리언으로 먼저 확정하고 **하나도 없으면 `beforeWrite`(내구 가드)조차 호출하지 않고 즉시 반환**. 무조건 나가던 `inventories {"quantity":N}` PUT을 제거하고, 수량 복구는 `quantity > 0 && 현재수량 <= 0`일 때만. `readSalePrice`에 `selling=F` → `writable=false` 분기 추가.
- `MarketStockSyncService.matchesTarget` — 무조건 수량 비교를 **카페24 분기 뒤로** 이동. 카페24는 품절 목표면 `saleState=F` 하나로, 재입고 목표면 `saleState=T · stockState=T · 수량>0`으로 판정한다.

| 목표 | 카페24로 나가는 PUT |
|---|---|
| 품절 · 이미 `selling=F` | **0회** |
| 품절 · `selling=T` | 본상품 `selling=F` **1회뿐**, `inventories` 0회 |
| 재입고 | 품목 `selling=T` → 본상품 `selling=T` → (마켓 수량 0 이하일 때만) 수량 |
| 가격 · `selling=F` | **0회(BLOCKED)** |

**완료 판정을 함께 바꾸지 않으면 의미가 없다** — 목표 300과 현재 0이 달라 매 배치마다 재전송되고, 그 반복이 곧 연동 오류다. 이번 수정의 급소가 여기였다.

## 남은 리스크와 라이브 확인 항목

- **"판매중 + 재고 0" 잔여 상태**: 재입고 순서를 `selling=T` → 수량으로 바꾼 대가. 수량 PUT이 3회 연속 실패하면(`beginWrite`의 `writes >= 3`) `FAILED_MISMATCH`로 종결되어 사람 개입 전까지 남는다. 구 순서라면 "판매안함 + 재고 0"(안전)이었을 상태다. `selling` 먼저를 택한 근거는 D-262의 거부 문구 *"연동된 쇼핑몰상품이 '진열/판매'상태일 때만 판매중지를 해제할 수 있습니다"* 다.
- **기존 272건(연동 235건)의 재고 0**: **자연 교정**을 택했다. 일괄 교정은 235건 × 2마켓 전송을 새로 만들어 D-262 증상을 재현한다.
- **미검증(코드로 확증 불가)**: 마켓플러스가 ESM으로 전송할 때의 수용·거부 규칙 전반, "판매중 + 재고 0" 중간 상태의 실제 영향, 기존 272건이 재입고 시 실제로 복구되는지.
- **범위 밖 관찰**: 레거시 `syncVerifiedPriceStock`은 `soldOut`과 무관하게 price를 보낼 수 있다. `market_sync=T`는 `requireNativeWrite`로 막히므로 연동 오류로는 이어지지 않으나, "품절 중 가격 미전송" 규칙이 그 경로에선 충족되지 않는다(연동 미사용 카페24 상품 한정).
