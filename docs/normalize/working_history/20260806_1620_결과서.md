## 이번 사이클의 성격 — 실측이 계획을 지웠다

착수 순서를 **① 실측 → ② 이전계획(승인) → ③ 5단계**로 잡았고, ①에서 ②가 사라졌다.

`product-orders/query`로 **기존 22건을 전수 조회**해(서버에서 실행, 자격정보 미반출) 확인한 것:

| 항목 | 결과 |
|------|------|
| `order.orderId` 존재 | **22/22** |
| `productOrder.packageNumber` | **22/22**, 전부 상이 |
| **22건 중 orderId 공유** | **0건** (distinct orderId 22 = 주문 수) |
| `expectedSettlementAmount` | **22/22** (취소·미결제는 0) |
| 새 키 ↔ 기존 `market_order_no` 충돌 | **0건** |
| 마켓 주문번호를 문자열로 든 다른 테이블 | **없음** |

orderId 공유가 0이므로 이전은 **행 병합이 아니라 키 재작성**이다 → 별건 계획 없이 5단계에 흡수.
사용자 승인은 화면 주문번호가 바뀌는 것에 대해 받았다.

**교훈: 계획의 크기를 데이터가 정한다.** 실측 없이 설계했으면 병합 전략·승인 절차를 먼저 짜느라
한 사이클을 더 썼을 것이다. 라이브 응답 한 번이 그 계획을 통째로 지웠다 — 4단계에서 배운 것과 같다.

## 수정 내용

- **어댑터**: 응답 원소(= 상품주문 1건)를 `orderId`로 묶어 3계층 DTO를 낸다. 배송은
  `packageNumber`로 가르고(없으면 상품주문번호 폴백), 상품주문 키는 `productOrderId`,
  정산액은 `expectedSettlementAmount` 실측값.
- **청크 경계를 넘어 누적한다.** 30일 창을 1일 단위로 훑으므로 같은 주문의 상품주문이 다른 날
  바뀌면 다른 청크에 온다. 같은 상품주문이 두 청크에 나오면 **나중 것이 이긴다**(최신이 진실) —
  그대로 두면 라인아이템 키 중복으로 `uk_line_item_order_market_no` 위반, 동기화 전면 실패.
- **동기화**: 공통 골격(D-138)에 위임. 기존/신규 판정만 공통 헬퍼에서 뺐다 —
  **새 키로 못 찾으면 옛 키로 찾아 갈아 끼우는** 마켓 고유 규칙이 생겼기 때문이다.
- **발송·발주확인·취소**는 전부 상품주문 단위다. 라인아이템 키 / 주문의 `productOrderIds`를 쓰고,
  특정 불가 시 주문번호로 추측하지 않고 즉시 실패한다(D-127).

## 설계 판단 하나 — 테스트가 잡았다

처음에는 **재키잉 선(先)패스 + 공통 헬퍼가 재조회**하는 구조로 짰다. 테스트가
"재조회가 방금 바꾼 키를 못 보면 새 주문을 만든다"를 잡았다(실제로 두 행이 저장됐다).
JPA의 flush 타이밍에 기대는 구조였다 — 조회 자체를 마켓 규칙으로 끌어올려 없앴다.

**이전이 곧 동기화다.** 배포 시점과 데이터 이전 시점이 어긋나도 중복 행이 생기지 않는다.
이 성질 덕분에 "배포 먼저 → 이전 나중" 순서를 안전하게 쓸 수 있었다.

## 미완 — 사용자 조작이 필요한 것

1. **창 밖 11건의 키 이전(SQL)**: 30일 창 안 11건은 동기화가 스스로 이전했다. 5~6월 11건은
   마켓이 더는 변경으로 내려주지 않아 동기화가 만나지 못한다. 스크립트를 서버
   `/tmp/ss_migrate.sql`에 올려 뒀으나 **실행이 권한 정책에 막혔다** — 사용자가 직접 실행해야 한다:
   ```
   ssh -i ssh-key-2026-06-25.key ubuntu@168.107.31.154 \
     "docker exec -i projects-postgres-1 psql -U canagent -d sbshop -v ON_ERROR_STOP=1 < /tmp/ss_migrate.sql"
   ```
   스크립트는 ① 옛 키·새 키가 동시에 있으면(중복 행) 전체 중단 ② 이미 이전된 건은 대상에서 제외
   ③ 라인아이템 키·`productOrderIds`를 먼저 채우고 주문 키를 바꾼다. 미실행이어도 **동작에는
   지장이 없다** — 그 11건은 전환 전 의미(주문번호 = 상품주문번호)대로 폴백 경로가 처리한다.
2. **기존 행의 정산액은 추정값 그대로다.** 실측값(`expectedSettlementAmount`)은 **신규 라인아이템
   생성 경로에만** 반영된다(11번가 D-134와 같은 규율). 예: `2026073137353041` 실측 49,998 vs
   DB 48,392. 교정은 **과거 정산 수치를 바꾸는 일**이라 사용자 판단이 필요하다 — 백로그 유지.
3. **N스토어 다품목 실사례가 0건**이다(22건 전부 상품주문 1건). 묶음·다품목 경로는 테스트로만
   증명됐다 — 쿠팡과 같은 상황이다.
