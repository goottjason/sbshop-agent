## 진단 — 실측이 먼저였다

세 건 다 코드만 읽어서는 심각도를 판정할 수 없어 운영 DB를 먼저 봤다.

```

COUPANG        |    192 |        192 |               0 |      192 |               0
SMART_STORE    |     22 |         22 |               0 |       22 |               0
```

**240행 전부가 `market_line_item_no` NULL, `shipment_id` NULL, 배송 0행.** 이 한 장이 세 건의
심각도와 안전성을 동시에 정했다 — 결함은 전부 실재하고(백필 대상이 240행), 수정은 전부
행위 불변이다(배송이 없으니 새 경로가 발동하지 않는다).

1단계 산출물이 정말 미배선인지도 확인했다 — `MarketOrderNormalizer`·`OrderShipmentUpsertService`·
`ShipmentRepository` 모두 비테스트 호출부가 0건이었다.

## 핵심 결정과 이유

### 1. 모르는 값에 대체값을 넣지 않는다 (D-131)

정규화기가 `marketLineItemNo`에 배송 식별자(주문번호 또는 `shipmentBoxId`)를 넣고 있었다.
`market_line_item_no`는 **마켓 상품주문번호**를 뜻하므로 이것은 거짓이고, 1단계가 적용한
`uk_line_item_order_market_no` 하에서 **주문당 라인아이템이 2건이 되는 순간 유니크 위반으로
동기화가 통째로 실패**한다. Cafe24는 이미 `items[]` 순회로 주문당 N건을 만든다.

D-127에서 얻은 교훈이 그대로 적용된다 — *폴백은 실패를 없애지 않고 실패의 원인을 감춘다.*
여기서는 감추는 것을 넘어 **새 실패를 만들** 수 있었다. null(= 아직 모름)로 두면
PostgreSQL이 NULL끼리 충돌로 보지 않으므로 레거시·미전환 행이 공존한다.

**배송 계층 폴백은 유지했다.** 설계 §3.3이 명시적으로 허용하고(배송이 항상 존재해야 상위 로직에
null 분기가 안 생긴다), 전환 전 마켓은 주문당 배송 1건이라 충돌하지 않는다. 두 폴백은 같아 보이지만
제약 조건이 다르다 — 하나는 충돌하고 하나는 안 한다.

### 2. 채택이 곧 백필이다 (D-132)

별도 백필 배치를 두지 않았다. 동기화가 30일 창을 매 사이클 다시 훑으므로, 매칭 시점에 레거시 행을
채택해 키를 부여하면 그것이 백필이다(설계 §5.4). 30일 이전 주문은 자연히 손대지 않는다.

매칭 순서: **정확키 → 상품 ID → 카디널리티**.

가장 어려웠던 판단은 카디널리티 규칙의 범위다. 처음에는 "남은 것이 1:1이면 채택"으로 두었는데,
그러면 레거시 2행 : 상품주문 2건에서 상품 ID가 명백히 어긋나는 마지막 둘을 억지로 짝짓는다.
**"주문 전체가 1:1일 때"로 좁혔다** — 상품 정보가 양쪽에 있는데 일치하지 않으면 그것은
"모르겠다"가 아니라 "다르다"다. 현재 240행 전부가 주문 전체 1:1이므로 실효는 그대로다.

반대로 1:1일 때는 상품 ID가 달라도 채택한다. 종전 `updateLineItemFromDto`가 상품 ID 불일치 시
그냥 재할당했기 때문에(마켓 sbCode 재매핑 등) **채택이 곧 동작 보존**이고, 거부하면 중복 행이 생겨
오히려 퇴행한다.

**기존 행은 최대 1회만 소비한다.** 두 상품주문이 한 행을 함께 채택하면 서로 덮어써 D-130이
그대로 재발한다.

설계 §5.4-3의 "섞인 흔적" 경고도 넣었다 — 쪼개짐이 일어났고 채택한 행이 이미 송장을 갖고 있으면
다른 상품주문의 송장일 수 있으므로 **지우지 않고** ⚠ 확인 필요로 남긴다. 정나영 건의 실제 형태다
(한 행이 순번1의 상품·정산액과 순번2의 송장을 함께 갖고 있었다).

### 3. 표방한 전제를 실제로 만족시킨다 (D-133)

설계 §4.4는 *"쓰기는 배송이 단일 원본이고, 라인아이템 컬럼에 직접 쓰는 코드는 남기지 않는다"*고
정했다. **그 전제가 거짓인 채로 1단계 미러링이 들어갔다** — 이메일 파이프라인·수동 송장 입력·
발송 처리기가 각자 라인아이템에 직접 쓰고 있었다.

2단계에서 발송처리 호출 단위가 배송으로 바뀌면(§6.1) 배송이 모르는 송장은 마켓에 나가지 않는다.
즉 **iHerb 발송메일 → 쿠팡·11번가 송장 자동반영이라는 지금 라이브인 파이프라인이 조용히 멈춘다.**
이 사이클에서 가장 값어치 있는 발견이다 — 2단계를 켠 뒤에 알아차렸다면 원인 추적이 훨씬 어려웠다.

`LineItemShippingWriter`를 단 하나의 통로로 두고 9개 지점을 이관했다. 판단이 필요했던 세 가지:

- **형제 미러 O** — 한 배송 = 한 송장이다(§3.1). 11번가는 묶음배송번호가 같으면 한 번의
  발송처리로 나머지 주문번호까지 발송된다(`-3308` 문서). 형제가 같은 송장을 갖는 것이 실제다.
  사용자 승인 시 두 안(포함/제외)을 제시해 **포함**으로 확정했다.
- **진행상태 X** — 같은 배송에서도 상품마다 갈린다(§3.2). 정나영 건이 근거다.
- **미러 실패가 사실을 지우지 않는다** — 배송을 못 찾으면 경고만 남기고 라인아이템 기록은 유지한다.
  D-125의 교훈 그대로: 송장은 부수 경로의 성공 여부와 무관하게 실재하는 사실이다.

**남긴 필자와 그 이유**를 명시해 뒀다. `OrderService:120,174`는 상태 전용(NEW→PREPARING, →CANCELED)이라
라인아이템이 맞다. 4개 마켓 동기화 서비스와 `CoupangOrderAdapter`는 각 마켓 단계(3~5)에서
자기 배송 upsert로 전환된다 — 그 마켓 라인아이템은 해당 단계까지 `shipment_id`가 NULL이라 갈릴 수 없다.

### 4. 기존 테스트에 목이 아니라 진짜 통로를 끼웠다

D-133은 16개 테스트 파일의 생성자를 깼다. 새 의존성을 목으로 채우면 컴파일은 통과하지만
**라인아이템 쓰기 자체가 사라져 기존 검증이 통과해도 아무것도 증명하지 못한다.** 진짜
`LineItemShippingWriter`를 같은 목 리포지토리로 조립해 끼웠다. `shipment_id`가 null인 이
테스트들에서는 통로가 배송을 건드리지 않으므로 종전과 동작이 같고, **그 사실이 곧 회귀 증거**다.

   설계 §6.2가 유력한 가설을 제시한다: 다품목 주문에서 `ordPrdSeq=1`만 발주확인하고 순번 2는
   안 했다면 주문은 결제완료 목록에 계속 남는다. **2단계에서 자연히 검증된다** (`plcodrCnfDt` 확인).
2. **쿠팡 어댑터가 요청 status를 상태로 사용** — 응답의 실제 status를 읽고도 쓰지 않는다. 3단계 범위.

4. **D-127 미검증** — 11번가 발송처리 성공 로그를 아직 확인하지 못했다.

  **주문 1개 = DTO 1개, 그 안에 배송 N개, 배송마다 라인아이템 N개**가 되어야 한다.
- **배포는 아직 하지 않았다.** 두 커밋(`97b815f`·`093724c`)은 로컬에만 있다. 행위 불변이므로 2단계와
  함께 내보내도 되고, 먼저 내보내 회귀를 분리 확인해도 된다. 배포 시 도는 배치를 중단시키므로
  배치 중 push는 피한다.
- **구조 관찰(백로그)**: 이번 세 건 모두 *"기반을 놓을 때 표방한 전제가 실제로 성립하는지 확인하지

  이번엔 직전 사이클의 리뷰 루프가 그 목록을 남겨 줘서 건졌다.
