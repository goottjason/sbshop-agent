## 핵심 결정
- **자유 SQL을 받지 않는다.** 작업 파일(update·delete·insert)에서 도구가 문장을 조립한다.
- **조건은 단계마다 한 번만 평가한다.** 대상 행의 ctid 배열을 얻어 그것으로 백업하고 그것으로 바꾼다. 검증 1차가 "같은 조건을 두 번 평가하면 `LIMIT`(ORDER BY 없음)·`random()`에서 백업한 행과 바꾼 행이 갈린다"를 잡았다.
- **앱 역할 `sbshop`으로 실행**(superuser 아님). 확인은 `sbshop_ro`.
- apply의 선행 조건 넷: 같은 파일의 dry-run 성공 기록, `--confirm <해시>`, 30분 이내 전체 덤프, 사전 확인(백업 테이블 없음). 건너뛰는 옵션 없음.
- 연쇄 쓰기가 가능한 테이블(사용자 트리거·규칙·상속, CASCADE류 참조 FK)은 거부. 지금 운영 스키마에는 해당 없음.
- 환경 변수로 대상·판정이 바뀌지 않게: 홈은 계정 DB에서, 하위 프로세스는 고정 환경, 덤프 나이는 파일 수정 시각, `docker --context default`, `python3 -I` 강제.
- 커밋 여부(`committed`)는 근거가 있을 때만 yes/no, 아니면 unknown. 시간 초과·클라이언트 강제 종료는 unknown(컨테이너 안 psql이 나중에 커밋할 수 있다).

## 검증
- qa-verifier 3회. 1차 부분(반려, 높음 1·중 3) → 설계 개정·수정 → 2차 보류(낮음 2) → 수정 → 3차 **정적·단위 범위 PASS**(변이 40종 전부 잡힘).
- **운영 설치는 조건부다.** 실 DB 통합 시험 18항목 통과가 전제다. PL/pgSQL·psql 동작(변수 치환이 `CREATE TABLE … AS`에서 되는지, 메시지 형식, 종료코드 전달 등)은 그때까지 추정이다.
