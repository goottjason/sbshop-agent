## 5. 다음 할 일 — D-369 설계(페이블)
계획서 §3의 여섯 가지를 정하고 같은 파일에 설계를 덧붙입니다(`handoff.md` §1 양식). 확인할 것과 실마리는 다음과 같습니다.

1. **판매 이력 상품의 소프트 삭제 영향**
   - 주문 그리드, 대시보드 집계, 클레임·반품 매칭, 정산이 `deleted_at`이 찍힌 상품의 주문을 어떻게 다루는지 봅니다.
   - 1차 grep에서는 주문 쪽에 삭제 상품을 거르는 조건이 없었습니다. 삭제 상품을 거르는 곳은 상품·마켓 쓰기 경로와 `MarketRegistrationRepository.java:30` 하나뿐입니다.
   - 등록 행은 남습니다.
   - 아직 화면·쿼리 단위로는 보지 않았습니다.
2. **미종결 주문 294(주문 670)·1376(주문 705)**
   - 둘 다 쿠팡 주문이고 10월부터 SHIPPED/DISPATCHED입니다.
   - 실제로 배송 완료됐는지 사용자에게 물어 두었고, 답은 아직 없습니다.
   - 가드는 바꾸지 않습니다.
3. **`advance` 범위**
   - 상품 지정이 없고 `last_attempt_at` 오름차순(NULL 먼저)으로 처리합니다.
   - 두 번째 회차부터는 D-361 잔여 10개(11-07)가 먼저 처리됩니다.

## 6. 함정
- **`/internal/retirement/start`·`advance`의 `dryRun` 기본값은 `true`입니다.** 실제 실행은 `dryRun=false`를 명시해야 합니다.
- 호출은 api 컨테이너 안에서 합니다. 예: `docker exec projects-sbshop-api-1 curl -s -X POST 'localhost:8080/internal/retirement/start?dryRun=true' -H 'Content-Type: application/json' -d '[1375]'`. D-361 방식이고, 이 세션에서는 실행하지 않았습니다. 첫 사용 때 형식을 확인합니다.
- **`esm-confirm`을 `advance`와 동시에 돌리지 않습니다.** 낙관락 충돌로 전체가 거부됩니다. 20개 단위로 넣습니다(D-361).
- ESM 삭제는 판매중지 상태에서만 됩니다. 크롬으로 판매중지 → 삭제 → 검색으로 부재 확인 순서입니다(D-361).
- 11번가는 삭제 API로 지워지지 않고 판매중지(STOPPED)로 완료됩니다. 리스팅은 11번가에 남습니다.
- `start`만 해도 그 상품에는 가격·재고·필드 쓰기가 차단되고 소싱처 배치에서도 빠집니다. 마켓 판매는 멈추지 않습니다.
- 시스템에는 쿠팡 판매중지·재개 경로가 없습니다. 쿠팡 판매 상태는 사용자가 Wing에서 바꿉니다.
- Wing 일괄변경 엑셀 교훈:
  - 대상 행만 남깁니다.
  - 판매가격·재고 입력 칸도 비우지 않습니다(현재 값과 같게).
  - openpyxl로 다시 저장한 파일은 거부됩니다.
  - 승인반려 상품은 바뀌지 않습니다.
- 운영 DB 조회는 `sbshop_ro`라 `CREATE TEMP VIEW`가 거부됩니다. CTE로 씁니다.
- 새벽 시간대(00:55, 02:00~04:30)를 피합니다. 04:00 아이허브 동기화가 같은 상품에 씁니다.
- D-367: 새 IHB 소싱 초안 등록은 고치기 전까지 피합니다(국내 6,000원이 이중으로 붙습니다).
