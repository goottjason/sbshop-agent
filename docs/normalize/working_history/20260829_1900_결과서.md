## 스키마 변경 (중대 등급)

```sql
ALTER TABLE sb_market_registration ADD COLUMN IF NOT EXISTS unsync_reason VARCHAR(32);
```

추가·nullable 이라 가역적이다. `ddl-auto: update` 이므로 배포 시 자동 생성도 되지만, 결정성을 위해 **수동 선행**했다.

백필은 확실히 판별 가능한 행만 했다.

| 구분 | 건수 |
|------|------|
| `is_synced=false` 전체 | 2,024 |
| ↳ `NEVER_SYNCED` 백필(식별자 없음 + 동기화 이력 없음) | 3 |
| ↳ **미분류(NULL) 유지** | **2,021** |

2,021건을 추측으로 채우지 않았다. **틀린 사유는 사유 없음보다 나쁘다** — `DELETED_ON_MARKET` 으로 오판하면 D-223 가드가 그 상품의 중복 등록을 허용해 정확히 막으려던 사고를 부른다.

## 핵심 결정과 이유

**1. 사유 미분류 행에 게시 가드를 적용하지 않았다.**
막는 쪽이 안전해 보이지만 2,021건의 재등록이 전부 불가능해진다. 통과시키되 경고 로그를 남긴다. 실피해가 큰 `is_synced=true` 는 확실히 막히므로 D-223 의 목적은 달성된다.

**2. 분류 실패를 `TRANSIENT_ERROR` 로 떨어뜨렸다.**
마켓이 에러 문구를 바꾸면 삭제 감지를 **놓치는** 방향으로 새고, 살아있는 상품을 삭제로 **오판하는** 방향으로는 새지 않는다. 오판 비용이 비대칭이라 안전한 쪽으로 기울였다.

**3. 식별자를 지우지 않고 보존했다.**
`replaceIdentifiersArchivingPrevious` 가 이전 값을 `previousIdentifiers` 배열에 쌓는다. 원장 D-222 의 원칙("식별자는 지우지 않는다 — 지우면 해결이 아니라 안 보이게 되는 것")을 게시 경로에도 적용했다.

**4. `MarketRegistrationResponse` 에 필드를 추가했다.**
계약 테스트(`ResponseDtoContractTest`)가 엔티티↔DTO 바이트 동일성을 검사해 정확히 이 누락을 잡았다. 결과적으로 D-222(배지 분리)의 재료가 프론트까지 이미 내려간다.
