# 2026-08-09 09:00 결과서 — 송장 출처 표시 (📧 이메일 / ✍ 진위 불명)

기능 요청(사용자): "지금 기입한 송장이 가송장인지 이메일 동기화로 들어온 진짜 송장인지 구분하기 어렵다.
배지를 하나 더 추가해 보여달라."

설계: `docs/superpowers/specs/2026-08-09-tracking-source-badge-design.md`
계획: `docs/superpowers/plans/2026-08-09-tracking-source-badge.md`

## 무엇을 만들었나

송장은 세 경로로 들어오는데 모두 같은 칸에 쓰이고 **출처를 기록하지 않았다.** 그래서 화면의 송장이
iHerb 메일이 준 진짜인지, 마감을 맞추려 넣은 가송장인지 알 수 없었다.

`sb_shipment.tracking_source`(EMAIL / MANUAL / MARKET)를 신설하고, 화면은 **두 아이콘으로 접어**
송장 입력칸 왼쪽 고정폭 슬롯에 표시한다.

| 표시 | 조건 | 뜻 |
|---|---|---|
| 📧 | `EMAIL` | iHerb 메일이 확인해 준 진짜 송장 |
| ✍ | `MANUAL`·`MARKET` | 사람·마켓이 넣은 값 — 진위 불명 |
| (없음) | `null` | 이 기능 이전의 과거 데이터. 소급 판정하지 않는다 |

## 설계에서 갈린 지점 두 가지

**1. 가송장 체크박스를 없앴다.** 처음엔 관리자가 입력할 때 가송장 여부를 체크받는 안이었으나,
사용자가 더 단순한 길을 지적했다 — 관리자 입력은 어차피 ✍로 뜨고 iHerb 메일이 오면 자동으로 📧가 된다.
입력 단계를 늘릴 이유가 없다. **그 전제(자동 교정)가 실제로 성립하는지 코드로 확인하고 진행했다**:
이메일 처리 대상은 `PREPARING`·`DISPATCHED`·`SHIPPED`이고 매 사이클 메일함을 다시 검색하며,
송장이 다르면 *"취소 방지용 가짜 송장을 진짜 송장으로 교정"* 분기를 탄다.
한계는 `DELIVERED` 이후 — 큐에서 빠져 더는 복구되지 않는다.

**2. 출처의 뜻이 "누가 처음 썼나"에서 "무엇이 이 값을 확인했나"로 바뀌었다.**
사용자 지적: 마켓 유래 값이 이메일이 준 진짜 송장과 같다면 📧로 보여야 한다.
실제로 구멍이 있었다 — 마켓이 진짜 송장을 갖고 있으면 동기화가 채택해 `MARKET`으로 기록되는데,
이후 메일이 와도 **값이 같으면** 이메일 경로가 `sameTracking` 분기로 빠져 출처가 굳는다.
그래서 이메일은 **값을 바꾸지 않는 경우에도 출처를 `EMAIL`로 승격**시킨다.

## 실행 방식

서브에이전트 방식(SDD) — 태스크마다 새 구현자, 태스크별 리뷰, 마지막 전체 리뷰.

| 커밋 | 내용 | 리뷰 |
|---|---|---|
| `824c978` | 도메인 `TrackingSource` + `Shipment.trackingSource` | 통과 |
| `0bbfdd2` | 세 쓰기 경로가 출처 기록 | 통과 |
| `bcb9311` | 이메일 승격(값이 같아도 EMAIL) | 통과 |
| `559f353` | 화면 아이콘 + 고정폭 슬롯 | 지적 1건 |
| `e07c1dd` | 지적 수정 — 택배사 select도 같은 x에서 시작 | 재확인 |

**리뷰가 잡은 실제 문제**: 아이콘 슬롯 때문에 송장 입력칸이 위 택배사 select보다 17px 좁아지고
오른쪽으로 밀렸다. 사용자가 "여백이 틀어져 보기 안 좋은 것만 아니면 된다"고 한 조건에 정확히 걸려
수정 라운드를 돌렸다(select에도 같은 스페이서).

## 게이트

- 백엔드 회귀 **1026건 · 실패 0** (기능 착수 전 1017 → 신규 9건)
- 프론트 `tsc -p tsconfig.app.json --noEmit` + `npm run build` 통과
- 운영 DDL을 **배포보다 먼저** 실행(`ALTER TABLE sb_shipment ADD COLUMN tracking_source VARCHAR(20)`) —
  컬럼 없이 새 엔티티가 뜨면 기동에 실패한다(Flyway 없는 수동 스키마 관리)

## 라이브 검증 — 통과

- 배포 확인: 서버 커밋 `e07c1dd` + 컨테이너 재생성 + **주문조회 200**
- 이메일 페치 1회 → **`EMAIL` 11건 기록**, 과거 데이터 245건은 설계대로 `null` 유지
- API 응답의 `lineItems[].shipment.trackingSource`에 `EMAIL`이 실제로 실려 나가는 것 확인

## 최종 점검 — 쓰기 경로 전수

| 경로 | 기록 | 판정 |
|---|---|---|
| `EmailFetcherService` 2곳 + 승격 분기 | `EMAIL` | 정상 |
| `OrderService` 3곳 · `OrderShipProcessor` | `MANUAL` | 정상 |
| `OrderShipmentUpsertService` | `MARKET` | 정상 — 실제 채택 + 실값일 때만 |
| `markTrackingAsSent` | 없음 | 정상 — 송장 값을 바꾸지 않는다 |
| `LegacyShipmentBackfillService` | 없음 | 정상 — 과거 값의 출처를 모르니 `null`이 정직하다 |

값과 출처가 어긋나는 경로 없음, 과거 데이터에 출처를 추론해 넣는 곳 없음.

  코드로는 검증했으나 실제 렌더링은 미확인이다.

  승격이 분기 맨 앞이라 현재는 안전하지만, 위치가 바뀌면 조용히 깨진다.

  대신했고 리뷰 게이트는 모두 정상적으로 거쳤다(원장에 사실대로 기록).
