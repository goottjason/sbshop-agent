## 핵심 결정과 이유

1. **빈 위치 = 소비자 모듈(core)**: @Async 한정자는 실행 컨텍스트에서 해소된다. 호출자가 api·worker 양쪽이므로 빈은 core에 있어야 함. api AsyncConfig는 껍데기로 존치(D-009 빈 이름·회귀 테스트 보존) — 정리 후보로 원장 기록.
2. **D-013 동결**: testcontainers(신규 의존성) + D-005 병합이 필요해 중대 등급 — 자율 마커로도 생략 불가한 사용자 승인 대상.
3. **D-014 리더 직접 처리**: 기계적 포맷터 실행에 팀 스폰은 과잉(게이트 강도는 리스크에 비례 원칙).

## D-013 분석 결론 (fixer-c3 실측 + 리더 config 확인)

- 순환 depends-on(flyway↔entityManagerFactory)의 트리거 = `spring.jpa.defer-datasource-initialization: true` + Flyway. **DB와 무관(빈 정의 시점)**.
- **운영 기동 차단 개연 (P0-후보)**: 운영 api application.yml에 defer:true + flyway:enabled + sql.init.mode:always 그대로, 프로파일 오버라이드 없음 — 리더 실측. D-001/D-009 빈 충돌이 기동을 먼저 막고 있었으므로 이 순환은 관측된 적 없었을 개연. 실기동 재현 전이라 P0 확정은 아님.
- H2 불가 실측: PG호환 모드에서도 Flyway V2에서 실패. R2Config S3Client 즉시생성도 테스트 기동 차단.
- 결론: 정도(正道) = testcontainers-Postgres + defer 제거 + after-migrate.sql↔Flyway 단일화(D-005) — 분리 불가한 하나의 중대 배치.
