## D-138 — Tidy First로 먼저 합쳤다

11번가(D-134)·쿠팡(D-137)을 전환하며 골격이 거의 그대로 두 번 복제됐고, 차이는 **로그 태그·상품
해석·정산액 산출 셋뿐**이었다. Cafe24·N스토어가 남아 있어 그대로 두면 복제가 넷이 된다.

`MarketLineItemSyncDispatcher`(골격) + `MarketLineItemSyncPolicy`(마켓별 3가지)로 분리해
두 서비스에서 **232줄 제거 / 52줄 추가**했다.

**골격이 소유하게 된 규율** — 마켓과 무관하게 같아야 하므로 한 곳에 모았다:
매칭은 주문 전체에서 한 번 · 상품 해석은 상품주문당 한 번 · 송장은 배송 미러가 내려씀 ·
`UNKNOWN`은 덮지 않음 · 분할 보류(D-136) · 기존 행 미삭제.

**행위 불변의 증거는 기존 테스트다.** 리팩토링 전 906개가 **하나도 바뀌지 않고** 통과했고,
신규는 골격 계약 테스트 9건뿐이다(915). 앞으로 마켓별 테스트는 **정책만** 검증하면 되고,
공통 규율의 정본은 `MarketLineItemSyncDispatcherTest`다.

## D-139 — Cafe24: 인덱스 짝짓기는 원래 필요가 없었다

**실물 확인이 결정적이었다.** 주문 `items[]` 원소가 배송 식별자를 **직접** 갖는다:

```
order_item_code = 20260805-0000011-01     ← 상품주문 식별자
shipping_code   = D-20260805-0000011-00   ← 배송 식별자 (item에 들어 있다)
order_status    = N20                     ← 상품별 진행상태
tracking_no · shipping_company_code       ← 상품별 송장·택배사
custom_product_code = 220622IHB002        ← sbCode
```

`shipments` 리소스도 매핑을 명시한다: `items = [{"status":"shipready","order_item_code":"…"}]`.

종전 `applyItemShipping`은 `items.size() == lineItems.size()`일 때 **배열 인덱스로** 짝짓고,
개수가 다르면 **첫 아이템 상태를 전체에 씌웠다.** 마켓이 순서를 바꾸면 엉뚱한 상품에 송장·상태가
붙는다. **기존 코드 주석도 *"sbshop 라인아이템은 order_item_code 미보존"*이라 인정하고 있었다** —
응답에 있는 식별자를 저장하지 않고 인덱스로 추측하고 있었던 것이다.

**Cafe24가 네 마켓 중 매핑이 가장 깔끔하다.** 그룹핑에 `shipments` 리소스를 호출할 필요조차 없다.

### 핵심 결정

**1. 미매핑 `order_status` 폴백을 `NEW` → `UNKNOWN`으로 바꿨다.** 종전 폴백은 새 코드가 등장하면
배송중 주문을 신규로 되돌린다 — 가장 나쁜 실패다. 11번가·쿠팡은 이미 정리했고 Cafe24만 남아
있었다. 골격이 `UNKNOWN`으로 기존 상태를 덮지 않으므로 안전하게 보존된다.

**2. D-124 실송장 탐색은 배송이 하나뿐일 때만** 적용한다. 여러 배송 중 아무 곳에나 붙이면 엉뚱한
송장이 들어간다. (ESM+ 자체배송은 Cafe24에 `'00000000'` 더미만 등록된다는 라이브 확증이 근거다.)

**3. 순수 변환을 `Cafe24LineItemMapper`로 분리했다.** 서비스가 `JsonNode`를 직접 읽는 구조라
DTO 경로가 없었는데, 변환만 떼어내니 서비스는 "DTO 조립 → 골격 위임"으로 얇아졌다.

## 정정 — 앞선 판단이 틀렸다

3단계 결과서에 `Cafe24Gmarket/AuctionOrderAdapter`를 *"소비처 없는 죽은 코드"*라고 적었는데
**틀렸다.** `MarketplaceShippingService`가 `List<MarketOrderPort>`를 주입받아 `getMarketType()`으로
찾으므로 **Spring이 타입으로 해석**한다 — 클래스명 직접 참조가 없어 grep에 걸리지 않았을 뿐이다.
실제로는 **G마켓·옥션의 발주확인·취소·송장 전송**을 담당한다. 지웠다면 기능 세 개를 잃었다.

D-136에서 *"죽은 코드가 기능 상실을 가린다"*고 적었는데 이번엔 **반대 방향으로 틀렸다** —
살아 있는 코드를 죽었다고 판정했다. **DI가 타입으로 해석하는 빈은 클래스명 grep으로 사용처를
판정할 수 없다.**

## 작업 중 사고 — 정규식 수술로 파일을 손상시켰다

`mapStatus` 등 메서드 4개를 정규식으로 제거하려다 `createOrder`·`updateOrder`·`persistOrder`·
`fetchAndPersist`가 함께 지워졌다. **컴파일은 통과했다** — 호출부도 같이 사라졌으므로.
즉 컴파일러가 잡아 주지 않는 기능 상실이었다.

파일 단위로 되돌리고(디렉터리 단위 checkout은 오전에 이미 한 번 다른 작업물을 지웠으므로)
`Edit`로 정확히 다시 했고, 핵심 메서드 존재를 **대조군으로 명시 확인**했다.

**교훈: 여러 메서드를 지우는 편집을 정규식으로 하지 말 것.** 중괄호 균형을 세는 스크립트도
javadoc·주석 경계에서 어긋난다. 지운 뒤에는 핵심 메서드 존재를 명시적으로 확인해야 한다.
