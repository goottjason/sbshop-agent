# 아이허브 축소 → 영국 소싱(포트넘·오카도) 전환 단계별 계획 (D-360)

- 작성: 2026-10-31 · 요청: 사용자(2026-10-30)
- 배경: iHerb KR 결제에 구매자 본인인증이 필요해졌다. 통관부호만으로는 결제가 안 되고 주문마다 고객 연락·인증이 필요하다. 감당할 인력이 없어 iHerb 상품을 점진적으로 내린다.
- 사용자 지정 순서: ① 몇 개월 내 팔린 적 없는 것부터 ② 연동된 마켓에서 삭제 ③ 삭제가 확인되면 시스템에서 삭제. 그 뒤 포트넘앤메이슨(FTN)·오카도(OCD) 상품 등록을 늘린다.

### 계획에 영향을 주는 사실 4가지
1. **"몇 개월"은 최대 5개월까지만 판정할 수 있다.** 주문 기록이 5/21부터라 그 전에 팔린 상품은 "안 팔림"으로 보인다. 한 번도 안 팔린 2,000개가 곧 "5개월 이상 판매 없음"이다.
2. **지금 삭제 기능을 그대로 쓰면 D-358(툴시 잎차) 같은 유령 리스팅이 대량으로 생긴다.** 현행 `ProductManageUseCase.deleteProduct`의 문제는 세 가지다.
   - 카페24 상품을 지우면서 G마켓·옥션 자식 리스팅은 "수동"으로만 기록하고 남겨 둔다. 카페24 상품이 사라지면 G마켓·옥션 리스팅은 판매중인 채로 연결이 끊긴다.
   - 외부 삭제가 실패해도 SB 상품을 **즉시** 소프트 삭제한다(`disposed = true` 고정). 사용자 방식("삭제 확인 후 시스템 삭제")과 순서가 반대다.
   - 11번가는 자동 삭제가 미지원(수동)이고, 쿠팡은 심사중이면 삭제가 거부된다.
3. **아이허브가 매출의 거의 전부다.** 판매 이력이 있는 146개를 언제 어떻게 내릴지가 매출에 직결된다.
4. **영국 상품은 이미 800개가 올라가 있는데 거의 안 팔리고(FTN 3개월 5건), 가격·재고가 7주째 갱신되지 않았다.** 신규 등록보다 기존 800개 정상화가 먼저다.

## 2. 단계별 계획

### 0단계 — 결정 (코드 작업 없음, 사용자 결정)
| # | 결정할 것 | 추천 |
|---|---|---|
| 0-1 | 1차 삭제 기준 | 판매 이력 없음(2,000개). 주문 기록이 5개월뿐이라 "5개월 이상 판매 없음"과 같다 |
| 0-2 | 판매 이력 있는 146개 | 1차에서 제외. 아이허브 매입이 가능한 동안 유지하고, 4단계에서 따로 결정 |
| 0-3 | 진행 중 IHB 주문 53건 | 매입 경로(본인인증)로 처리하되, 처리 불가 건은 취소 기준을 정해 둔다 |
| 0-4 | 쿠팡 IHB 브랜드 심사 소명 | 1차 삭제 대상 브랜드는 소명을 중단한다(삭제할 상품에 증빙을 쌓지 않는다) |
| 0-5 | "시스템에서 삭제"의 의미 | 소프트 삭제(행은 남기고 숨김). 과거 주문·정산이 상품을 참조하므로 하드 삭제는 하지 않는다 |
| 0-6 | 영국 소싱의 매입·배송 경로 | 5단계 전에 반드시 확인(아래 5-1) |

### 1단계 — 퇴출(retire) 도구 정비 (코드, 표준~중대)
목표: "마켓에서 지운다 → 지워졌는지 확인한다 → 확인된 것만 시스템에서 지운다"를 상품 수천 개에 안전하게 돌리는 도구.

1. **퇴출 상태 도입:** 상품에 `RETIRING`(퇴출 진행 중) 상태를 둔다. 이 상태의 상품은 가격·재고 배치와 마켓 전송에서 빠진다(카페24 재고 0 전송 금지 규칙 유지).
2. **마켓별 삭제 순서 고정:** G마켓·옥션(ESM) → 카페24 → 스마트스토어 → 쿠팡 → 11번가. **카페24 상품은 G마켓·옥션 리스팅이 지워진 게 확인된 뒤에만 지운다**(D-358 재발 방지).
3. **G마켓·옥션 삭제 경로 조사·구현:** ESM은 쓰기 API가 없다. 조사 대상은 아래 두 가지이고, 실측 후 고른다. 자동화가 불가능하면 대상 목록 엑셀을 뽑아 사람이 일괄 처리하는 반자동 경로로 간다.
   - 마켓플러스의 마켓상품 삭제(카페24가 대신 지움)
   - ESM 목록의 일괄 다이얼로그(판매중지 → 삭제)
4. **11번가:** 삭제 API 유무를 재확인한다. 없으면 판매중지(`stopdisplay`)로 대체하고, "삭제 확인" 대신 "판매중지 확인"을 퇴출 완료 조건으로 삼는다.
5. **쿠팡 심사중 상품:** 삭제가 거부되므로 퇴출 대기열에 두고 심사 결과 후 재시도한다(반려되면 삭제 가능). 판매중지 API도 승인완료 상품만 된다.
6. **삭제 확인:** 마켓 재조회(`/internal/registrations/probe` 계열)로 부재를 확인했을 때만 `DELETED_ON_MARKET`으로 기록한다. 쓰기 성공 응답만 보고 확인으로 치지 않는다.
7. **시스템 삭제 조건:** 모든 마켓이 "부재 확인(또는 11번가 판매중지 확인)"일 때만 SB 소프트 삭제. 하나라도 남으면 `RETIRING`으로 남겨 다음 회차에 재시도한다.
8. **가드:**
   - 진행 중 주문·활성 클레임이 있는 상품은 제외한다.
   - 실행 단위는 dry-run, 건수 상한, 마켓별 throttle(네이버 1200ms 이상)로 묶는다.
   - 매 회차 결과 리포트(마켓별 성공·거부·대기)를 남긴다.
9. **기존 `deleteProduct` 정리:** 수동 단건 삭제도 같은 순서·조건을 쓰게 하거나, 최소한 G마켓·옥션이 남아 있으면 카페24 삭제를 막는다.

### 2단계 — 파일럿 (20개)
- 판매 이력 없는 IHB 중, 모든 마켓에 등록된 상품 20개를 고른다. 쿠팡 심사중이 아닌 것 위주로 한다.
- 실행 → 마켓별 결과 → 각 마켓 화면에서 실제 삭제를 확인한다(크롬).
- **고아 리스팅 대조:** ESM 전체 리스팅과 우리 상품을 대조해(D-358 때 쓴 방식) 새로 생긴 유령 리스팅이 0개인지 확인한다.
- 문제가 없으면 회차 크기를 정한다(예: 하루 200개).

### 3단계 — 판매 이력 없는 2,000개 단계적 퇴출
- 하루 1회차씩 진행하고, 회차마다 대조 리포트를 확인한다.
- 소싱 배치가 도는 시간과 겹치지 않게 한다.
- 쿠팡 심사중은 대기열로 빠지니, 쿠팡 심사 결과가 나오는 대로 재시도한다.
- 완료 기준: 판매 이력 없는 IHB 중 `RETIRING`·남은 마켓 리스팅 0, 유령 리스팅 0.

### 4단계 — 판매 이력 있는 146개 처리 (사용자 결정 후)
- 0-2에서 유지하기로 한 상품은 매입 부담과 매출을 함께 보고 결정한다.
- 선택지:
  - 계속 판매
  - 품절 처리 후 일정 기간 관찰
  - 퇴출
- 선택지마다 영국 대체 상품이 있는지(같은 카테고리 수요)를 함께 본다.

### 5단계 — 영국 소싱 기반 정상화 (신규 등록 전)
1. **매입·배송 경로 검증 (가장 먼저):** 포트넘·오카도에서 실제로 1건씩 사서 한국 고객에게 보내는 경로를 확정한다.
   - 확인 항목: 배송대행지 사용 여부, 오카도의 해외배송 불가 여부, 통관(목록통관/일반통관·개인통관부호), 구매자 인증 요구 여부, 리드타임, 실제 원가.
   - **아이허브와 같은 인증 함정이 있는지 여기서 걸러낸다.** 현재 가격 정책(£10.5 + £2/500g)이 실제 배송비와 맞는지도 검증한다.
2. **기존 800개 정상화:**
   - 정기 크롤 재가동: 9/12 이후 멈춤 → 가격·재고 갱신.
   - FTN GraphQL 고속 경로 전환(백로그 ①, 상품당 20초 → 0.5초, 원가·중량·HS코드·성분까지 확보).
   - OCD 원본 소멸 136개 정리(이 역시 퇴출 도구로).
3. **수요 점검:** FTN 393개가 3개월 5건만 팔린 이유를 본다. 가격 경쟁력(마켓 최저가 대비), 노출, 카테고리 오등록 중 무엇이 원인인지 확인한다.

### 6단계 — 영국 상품 신규 등록 확대
- 상품 추천·자동등록 파이프라인(S0~S6)은 아이허브 기준으로 만들어져 있다. 발굴(S0)·통관게이트(S2)·인리치먼트(S4)를 FTN·OCD 스크레이퍼로 확장한다.
- 미완인 S6(마켓 등록 페이로드)을 마무리한다.
- 쿠팡 브랜드 심사를 고려해 새 브랜드는 **매입 증빙이 가능한 브랜드부터** 등록한다. 쿠팡이 인정하는 증빙은 주문 상세 화면 캡처다.
- 등록 속도는 4단계 퇴출 속도와 매출 추이를 보며 조절한다.

## 3. 순서와 의존 관계
```
0 결정 ─┬─ 1 퇴출 도구 → 2 파일럿 → 3 미판매 2,000 퇴출 → 4 판매이력 146
        └─ 5-1 영국 매입 경로 검증 → 5-2·5-3 기존 800 정상화 → 6 신규 등록
```
- 1~3(퇴출)과 5(영국 정상화)는 서로 독립이라 병행할 수 있다.
- 4(판매 상품 퇴출)는 5의 결과(대체 매출원)를 보고 결정한다.

## 5. 개정 입력 (2026-11-19) — 아이허브 배대지 전환, 영국 배제

이 절은 재설계(페이블)에 넘길 입력이다. 확정한 것과 결정할 것을 나눈다. 위 1~4절은 2026-10-31 기준 원안으로 남긴다.

### 5-1. 사용자 결정 (2026-11-19 19:00)
- 영국 소싱(FTN·OCD·COK·VTB)은 이 시스템에서 업데이트하지 않고 배제한다 → 원안 5·6단계 폐기.
- 아이허브만, **미국 오레곤 배송대행지(배대지) 경유**로 판매하는 체계로 전환한다. 배대지 배송비를 가격에 얹는다.
- 원안 배경(아이허브 한국 사이트 결제의 구매자 본인인증)을 배대지 경유로 푼다 — 그래서 매입은 미국 사이트에서 한다고 본다(5-4의 결정 1에서 확인).

### 5-2. 확인한 사실 (2026-11-19, 운영 DB `sbshop_ro` 읽기·코드)
- 삭제되지 않은 IHB 상품 147개, 그중 퇴출 진행 중 10개 → 소싱처 배치 대상 137개(`ProductSupplierBatchService.java:192-194`가 삭제·퇴출 진행 중 상품을 뺀다). 원안 4단계의 "판매 이력 146개"가 사실상 남은 상품군이다.
- 무게 보유 2,144/2,146(중앙값 0.3kg, 최대 3kg). 단위 kg.
- 현재 IHB 소싱처 정책(`sb_vendor_price_policy` id 1): 마진 4%, 쿠폰 0, 최소마진 0, 해외 배송비 0, 국내 배송비 6,000원(40,000원 이상 무료). 공통 정책(`sb_price_policy`): 마진 15%, 쿠폰 20%, 최소마진 5,000원 — 상품 값 → 소싱처 값 → 공통 값 순으로 덮는다(`MarketSalePriceResolver`).
- **실제 가격 배치는 요청 값이 위 정책을 덮는다**: 2026-11-19 배치(`sb_supplier_batch_run` 62bda9a5, IHB·PRICE, 137건)와 10-28 배치 모두 요청에 마진 15%·쿠폰 0·최소마진 15,000원을 실어 보냈고, 계산 기록(`sb_supplier_batch_item.calculation.policy`)도 136건 전부 그 값이다. 고정 최소마진 15,000원과 국내 배송비 때문에 원가 대비 판매가 배율이 1.30~5.95배로 벌어진다(스마트스토어 기준, 원가가 낮을수록 배율이 크다).
- **사용자 결정(2026-11-19 23:27): 배치 요청의 마진·쿠폰·최소마진은 상황에 따라 판매가를 바꾸려고 일부러 둔 수시 조정 값이다. 목표 마진 하한은 5% 또는 5,000원이고, 가격 정책은 수시로 바뀔 수 있다.** 따라서 15%·15,000원은 고정 정책이 아니라 이번 회차의 값이다. **추가 결정(23:30): 하한은 둘 중 작은 쪽을 지킨다. 이 하한(5%·5,000원) 자체도 고정이 아니고 수시로 바뀔 수 있다** — 설계는 하한을 상수로 박지 말고 조정 가능한 값으로 다룬다.
- 무게 기반 해외 배송비 계산이 이미 있다: 기본 금액(기본 무게까지) + 초과분을 단계 무게로 올림한 단계 수 × 단계 금액(`VendorShippingCalculator`). 크롤 때 매입원가에 더하고 묶음 수량으로 나눈다(`LandedCostCalculator`, 호출: `BatchPriceStockService:218`, `ProductSourceWorker:141`). 영국 소싱처가 £10.5 + £2/500g로 쓰던 것이다.
- **함정:** 정책의 `ship_currency`는 계산에 쓰이지 않는다. 배송비에는 **크롤한 상품 가격의 환율**(`result.fxRate()`)이 곱해진다. 지금 IHB는 한국 사이트에서 원화로 크롤해(`scraper/scrapers/iherb.py` `currency="KRW"`) 환율이 1이라 원화 요금표가 그대로 맞는다. **크롤을 미국 사이트(USD)로 바꾸면 원화 배송비에 달러 환율이 곱해져 약 1,400배가 된다** — 배송비를 달러로 넣거나 코드가 `ship_currency`를 쓰게 고쳐야 한다.
- 마켓 가격 전송은 소싱처 배치를 화면에서 시작해야만 돈다. 마지막 전송 2026-10-28.

### 5-4. 재설계에서 정할 것 (페이블)
1. **매입원가의 출처** — 한국 사이트 원화 가격을 계속 쓸지, 미국 사이트 달러 가격으로 바꿀지. 바꾸면 스크레이퍼 변경(가격 경로라 중대 등급 ④)과 5-2의 환율 함정 처리가 같이 온다. 미국 사이트 가격·재고·품절 표시가 한국 사이트와 다른지도 본다.
2. **아이허브 → 배대지 미국 내 배송비** — 지금 `domestic_fee`(6,000원/40,000원 이상 무료)는 한국 사이트의 한국 배송비다. 배대지 체계에서는 미국 내 배송 조건(무료 기준 금액)으로 바꿔야 한다. 배대지 요금에 한국 내 택배가 포함되는지도 확인한다.
3. **실제 배송 무게** — 상품 무게가 포장 포함 배송 무게인지, 부피무게가 걸리는 상품이 있는지. 0.5kg 경계 근처 상품은 한 단계(2,600원) 차이가 난다.
4. **주문 단위와 배송비 배분** — 한 주문에 여러 개·여러 상품일 때 배대지는 묶음으로 매기지만 가격은 상품마다 단품 기준으로 매긴다. 단품 기준(보수적)으로 둘지.
5. **통관·세금** — 건강기능식품 목록통관 한도·수량 제한, 초과 시 관부가세. 가격에 넣을지, 주문 수량을 제한할지.
6. **마진 하한** — 배치 값은 수시로 바뀌므로(위 사용자 결정) 설계가 정할 것은 특정 마진율이 아니라, 어떤 배치 값을 넣어도 **목표 하한(5% 또는 5,000원)이 배대지 배송비·수수료·환율 변동을 뺀 뒤에도 지켜지는지**다. 두 하한 중 작은 쪽을 지키고, 하한 값 자체도 수시로 바뀐다(사용자, 23:30) — 하한을 어디에 두고 누가 바꾸는지(배치 화면·정책 테이블)도 정한다. 하한 아래로 내려가는 배치 값을 막거나 경고할지도 정한다. 소싱처 정책의 4%는 배치에서 쓰이지 않는다.
7. **전환 시점과 순서** — 정책 변경 → 소싱처 배치(137개 × 마켓 넷, 대부분 가격 인상) → 재조회. 마켓 대량 쓰기라 파일럿 → 본 실행. 마켓 리스팅의 배송 기간·출고일 표시도 바뀌는지. 전환 전 주문(한국 사이트 직배송)과 전환 뒤 주문의 처리 구분.
8. 원안 4단계(판매 이력 상품 처리)는 "남길 핵심 상품군의 가격·배송 정상화"로 바뀐다.

**6-2-2. 코드**
- 판매가 식은 한 곳에 있다: `MarginCalculator.computeSalePrice`(`MarginCalculator.java:85-115`).
  - 총 매입가 = 개당 원가 × (1 − 쿠폰) × 묶음수량 + 국내 배송비(총 매입가가 기준 미만일 때).
  - 목표가 = 총 매입가 ÷ (1 − 마진율 − 수수료율), 100원 반올림.
  - 최저가 = max(총 매입가 + 최소마진, 총 매입가 ÷ (1 − 수수료율)), 100원 올림. 최소마진은 수수료를 빼기 전 금액이다.
- 상품 가격 계산은 `MarketSalePriceResolver.explainForProduct`(`MarketSalePriceResolver.java:57-83`)를 거친다: 배치 검토(`ProductEditPlanner.java:105-133`), 마켓 가격 전송 직전 재계산(`MarketPriceSyncService.java:361-372, 392`), 등록·미리보기(`MarketPublicationService`, `ProductPricePreviewUseCase`, `ProductPublishUseCase`). 같은 클래스에 `PricingInputs`를 받는 `resolve`가 따로 있고 `ProductMarketSyncService.java:66`이 부른다 — 이 경로가 살아 있는지는 확인하지 못했다(고정 결정 10).
- 소싱처 정책의 국내 배송비가 비어 있으면 코드 상수 6,000원/40,000원이 쓰인다(`MarketSalePriceResolver.java:76-79`, `MarginCalculator.java:10-11, 37-41`). 0과 빈 값은 다르다.
- 배치의 아이허브 수집은 자바의 `ProductSourceObservationClient`다(`:79-136`). `catalog.app.iherb.com`을 부르고, 가격 표기가 `₩`로 시작할 때만 받는다. 할인가가 정가보다 싸면 정가를 원가로 쓴다(`:112-116`).
- 수집 통화와 정책의 `ship_currency`가 다르면 원가를 비우고 가격을 보류한다(`ProductSourceWorker.java:137-138`).
- 수집 때 원가에 얹는 기존 배송비(`ship_*`, `LandedCostCalculator.java:11-30`)는 상품 무게를 묶음수량과 곱하지 않고, 그렇게 얹힌 배송비에는 쿠폰 할인도 적용된다(`MarginCalculator.java:46, 74-83`).
- 배치 요청 값(마진·쿠폰·최소마진)은 상품에 저장되고(`ProductSupplierBatchSource.java:70-74`), 이후 계산은 상품 값을 먼저 쓴다.
- 가격을 스스로 다시 보내는 스케줄러는 없다. `MarketPriceSyncScheduler`는 이미 만들어진 가격 작업만 처리하고, 처리 직전에 다시 계산한 값이 작업의 기대 값과 다르면 작업을 `STALE`로 멈춘다(`MarketPriceSyncService.java:361-372`).
- 소싱처 배치는 소싱처 전체가 대상이다. 일부만 고르는 기능이 없다(`ProductSupplierBatchService.java:191-195`).
- 예전 즉시 배치(`BatchPriceStockService.crawlAndUpdatePriceStock`)는 호출처가 없다(`BatchScheduler.java:19-22`, `BatchController`는 수동 갱신 두 가지만 부른다).

### 6-3. 고정 결정과 위임

**고정 결정** (구현자가 바꾸지 않는다)
1. **배대지 배송비는 판매가를 계산할 때 더한다. 상품 원가(`cost_price`)에는 넣지 않는다.** 이유: 원가에 넣으면 쿠폰 할인이 배송비에도 먹고, 정책을 바꿀 때마다 다시 수집해야 하며, 카페24 공급가 같은 원가 소비처의 값이 바뀐다.
2. **총 매입가 = 개당 원가 × (1 − 쿠폰) × 묶음수량 + 국내 배송비(기존 규칙) + 배대지 배송비.** 쿠폰과 국내 배송비 무료 기준은 배대지 배송비를 더하기 전 금액에 적용한다.
3. **배대지 배송비 = 기본 금액 + 단계 금액 × ⌈max(0, 계산 무게 − 기본 무게) ÷ 단계 무게⌉, 계산 무게(g) = 상품 무게(kg) × 1000 × 묶음수량 + 포장 가산(g).** 통화는 원화로 고정하고 환율을 곱하지 않는다.
4. 배대지 요금 값은 소싱처 정책(`sb_vendor_price_policy`)의 새 칸 다섯 개(기본 금액, 기본 무게, 단계 금액, 단계 무게, 포장 가산)에 둔다. 기존 `ship_*` 칸과 `LandedCostCalculator`는 건드리지 않는다. 이유: 영국 소싱처는 배제 대상이라 동작을 바꾸지 않는다.
5. 배대지 기본 금액이 비어 있거나 0이면 배대지 배송비는 0이다. 값이 있는데 상품 무게가 없으면 가격을 계산하지 않는다(기본 요금으로 때우지 않는다) — 계산 불가 사유를 돌려주고 기존 가격을 유지한다.
6. **하한가 = min(총 매입가 ÷ (1 − 수수료율 − 하한율), (총 매입가 + 하한액) ÷ (1 − 수수료율)), 100원 올림. 판매가 = max(목표가, 기존 최저가, 하한가).** 하한율·하한액 중 하나만 있으면 그 하나만 쓰고, 둘 다 비어 있으면 하한을 적용하지 않는다.
7. 하한 값은 공통 가격 정책(`sb_price_policy`)의 새 칸 두 개(하한율 %, 하한액 원)에 두고 설정 화면에서 바꾼다. 코드 상수로 두지 않는다. 모든 소싱처, 모든 계산 경로에 적용한다.
8. 하한에 걸리면 가격을 올리고 계속한다. 배치를 막지 않는다. 계산 근거(`Calculation.notices`, 미리보기)에 "마진 하한 적용"과 올리기 전·후 가격을 남기고, 기존 "최소마진 보장" 문구와 구분한다.
9. **새 칸이 모두 비어 있으면 계산 결과가 지금과 1원도 다르지 않아야 한다.** 이유: 배포와 가격 변경을 분리한다 — 배포 직후에는 아무 가격도 바뀌지 않고, 정책 값을 넣은 뒤에만 바뀐다.
10. 판매가를 계산하는 모든 경로가 같은 식을 쓴다. `PricingInputs`를 받는 `MarketSalePriceResolver.resolve`(`ProductMarketSyncService.java:66`)가 살아 있는 경로면 같은 식으로 맞추고, 죽은 경로면 손대지 않고 원장에 적는다.
11. 배치 요청의 마진·쿠폰·최소마진의 의미와 화면은 바꾸지 않는다.
12. 아이허브 수집(가격 출처·통화)은 이번에 바꾸지 않는다.
13. 상품의 무게 값은 이번에 고치지 않는다. 이유: 무게는 카페24·11번가로 전송되는 칸이라 고치면 마켓 쓰기가 따라온다.
14. DDL 파일은 테이블 소유자가 달라 둘로 나눈다(`sb_price_policy`는 `sbshop`, `sb_vendor_price_policy`는 `goottjason`). 추가형, nullable, 멱등.

**위임** (구현자가 정한다)
- 컬럼·필드·메서드 이름, 시그니처, 클래스 배치. 기존 시그니처를 남겨 위임 호출로 둘지 여부.
- 설정 화면의 배치와 문구, 배치 시작 화면에 현재 하한을 읽기 전용으로 보여 줄지.
- 계산 근거에 배대지 배송비와 계산 무게를 넣는 형식(예: "배대지 13,100원 · 계산 무게 800g = 300g × 2 + 200g").
- 정책을 저장할 때 도는 배치가 있으면 경고할지.

### 6-4. 구현 단계

원장에 새 레코드(다음 번호)를 열고 시작한다. 로직은 Red → Green 순서로 한다.

1. **구조 준비(동작 불변)** — 계산 함수가 추가 비용과 하한을 받을 자리를 만든다. → 검증: 기존 테스트 전체 통과. `refactor` 커밋으로 먼저.
2. **하한** — 아래 예 B·C와 "둘 다 비면 지금과 같다", "하나만 있으면 그 하나"를 테스트로 먼저 쓴다. → 검증: Red를 본 뒤 Green.
3. **배대지 배송비** — 예 A·D, 묶음수량 곱, 포장 가산, 0.5kg 경계(계산 무게 500g은 기본, 501g은 한 단계), 무게 없음(고정 결정 5), 기본 금액 없음을 테스트로 먼저 쓴다. → 검증: Red를 본 뒤 Green.
4. **스키마** — 엔티티에 칸 일곱 개, DDL 파일 두 개(`backend/docs/ddl/`), 정책 API와 서비스. → 검증: 엔티티 ↔ DDL 대조(검증자), 컨텍스트 로드 테스트.
5. **파일럿 경로 확인** — 선택한 상품만 수집·저장·전송하는 화면 경로가 배치와 같은 계산·같은 가격 작업을 거치는지 코드로 확인한다. → 검증: 호출 경로를 파일:줄로 인계서에 적는다. 다르면 멈춘다(6-6).
6. **화면** — 소싱처 정책 패널에 배대지 칸 다섯 개, 공통 정책에 하한 칸 두 개, 계산 근거 표시. → 검증: `frontend` 게이트, 빈 값과 0이 구분돼 저장되는지(국내 배송비 0 포함).

### 6-5. 등급과 운영 쓰기
- **중대**: 스키마(③)와 가격 산정에서 마켓 반영까지의 경로(④). 커밋 전 사용자 승인. 페이블 승급 사유는 마켓 대량 쓰기의 설계(①)다.
- 배포가 스케줄러 쓰기를 바꾸는가: 고정 결정 9가 지켜지면 다음 주기에 새로 쓰는 것은 0건이다. 푸시 직전에 처리 중인 가격 작업이 0건인지 다시 조회한다.

**운영 순서** (`sbshop-ops-write`, 단계마다 승인)
1. **DDL 적용**(W1, 추가형) — 파일 둘을 각 소유자 역할로. `\d`로 재조회. 배포보다 먼저.
2. **배포**(`sbshop-deploy`) — 푸시 승인. 배포 뒤 표본 5개의 가격 미리보기가 배포 전과 같은지 본다.
3. **정책 입력**(W1, DB 두 행. 마켓 쓰기 없음) — 사용자가 설정 화면에서 넣는다. 도는 배치가 없을 때만.
   - 공통 정책: 하한율 5, 하한액 5,000.
   - 아이허브 정책: 국내 배송비 0·무료 기준 0, 배대지 10,500 / 500 / 2,600 / 500 / 포장 200.
   - 재조회: 두 행의 값, 표본 5개의 미리보기 가격이 손계산과 같은지.
4. **파일럿**(W2, 가격 인상) — 선택 상품 수집 경로로 1~2개 → 재조회 → 20개 이하 → 재조회. 묶음 1·2·3개와 배송비 세 구간(10,500·13,100·15,700 이상)이 섞이게 고른다.
5. **본 실행**(대량 — 본 실행 승인 따로) — 사용자가 화면에서 아이허브·가격만·네 마켓으로 배치를 시작한다. 예상: 대상 137개 안팎, 가격 확인 약 516건(11-19 배치 기준), 전부 인상.
   - 배치 값은 사용자가 정한다. 값이 15%·0%·15,000원이면 평균 +14,000원(6-2-3)이다.
   - 대조(`sbshop_ro`): 보낸 값 = 확인 값, 하한 아래 0건, 손익분기 아래 0건, 내려간 가격 0건.
   - 백업: 배치 시작 전 `pre` 덤프. 쓰기 전 가격은 상품의 직전 `sale_price`와 11-19 배치(`62bda9a5`) 기록에 있다.
   - 원복: 정책 값을 되돌리고 같은 배치를 다시 돌린다. 이것은 가격을 내리는 쓰기(W3)라 따로 승인받는다.
6. **쓰기 뒤 확인** — `sbshop-ops-write` §7(상품 목록·주문 그리드·대시보드, api 로그, 주문 동기화 한 주기).

### 6-6. 멈춤 조건
- 새 칸이 비어 있는데 계산 결과가 지금과 다른 상품이 하나라도 있다(구현 중 테스트, 배포 뒤 표본).
- 판매가를 계산하는데 같은 식을 쓰게 만들 수 없는 경로가 있다.
- 선택 상품 수집 경로가 배치와 다른 계산·전송 경로를 탄다(파일럿 수단이 없어진다 → 설계로 돌아온다).
- 가격 표본 대조에서 미국 배송지 가격이 시스템 원가(개당 원가 × 묶음수량)보다 3% 넘게 비싼 상품이 있다.
- 무게 표본 10개 중 실제 배송 무게로 계산한 배대지 구간이 저장 무게로 계산한 구간보다 높은 상품이 3개 이상이다.
- 파일럿·본 실행에서 가격이 내려가는 상품이 나온다, 보낸 값과 확인 값이 다르다, 손계산과 다르다.
- 대상·건수가 예상과 다르다(137개 ± 그사이 퇴출 변동을 넘는다).
- `sbshop-ops-write` §4-7의 기본 중단 조건(연속 3건 실패, 회차 실패율 10% 초과).
