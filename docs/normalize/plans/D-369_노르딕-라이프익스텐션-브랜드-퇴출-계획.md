# D-369 노르딕내츄럴스·라이프익스텐션 브랜드 퇴출 — 설계 입력

이 문서는 설계(페이블)에 넘길 입력이다. 확인한 사실, 결정할 것, 실행 골격으로 나눈다. 실행 계획서(`sbshop-ops-write` §4)는 설계를 마친 뒤 이 파일에 덧붙인다.

## 1. 목적과 배경
- 2026-11-24 사용자 결정: 노르딕내츄럴스·라이프익스텐션은 앞으로 판매·업로드하지 않는다. 같은 날 "관련 브랜드는 전부 삭제 바람" — 기존 리스팅을 모든 마켓에서 지운다.
- 수단: D-361 퇴출 도구(`/internal/retirement/*`). 2026-10-31~11-01에 판매 이력이 없는 IHB 1,593개에 썼다(DONE 1,571).
- 등급: W3(마켓 상품 삭제) + 대량(마켓 삭제 약 36건 > 20) → 설계서·페이블·파일럿과 본 실행 두 번 승인.

### 2-4. 퇴출 도구 동작 (코드)
- 처리 순서는 스마트스토어 → 쿠팡 → 11번가 → G마켓·옥션 → 카페24다(`ProductRetirementService.java:58`).
- 카페24는 `esm-confirm` 전에는 지우지 않는다(`ESM_PENDING`, :271). `esm-confirm`이 G마켓·옥션 자식을 `DETACHED_DELETED`로 바꾼다(:443-478).
- 11번가는 삭제 API로 지워지지 않으면 판매중지와 재조회 STOPPED를 완료로 친다(:299-322). D-361에서는 1,508건 모두 판매중지였다.
- 쿠팡이 `BLOCKED_BY_MARKET`으로 거부하면 `COUPANG_REVIEW_PENDING`이고 다음 회차에 다시 시도한다(:350). D-361에서는 21개가 판매중지 뒤에도 끝내 지워지지 않았다.
- 모든 마켓이 끝나면 소프트 삭제하고 DONE이 된다(:253-257).
- 퇴출이 진행 중인 상품에는 생성·수정 쓰기 14종이 차단된다(D-361, `MarketClientRouter`). 소싱처 배치도 이 상품을 뺀다.
- **`advance`에는 상품 지정이 없다.** IN_PROGRESS 전체를 `last_attempt_at` 오름차순(NULL 먼저)으로 `limit`개까지 처리한다(`ProductRetirementRepository` `findDue`).
  - 지금 IN_PROGRESS는 10개다(D-361 잔여: 파라다이스허브즈 2, 솔가 2, 엔자이메디카 2, 노르딕 3194, 히말라야, 블루보넷, 재로우). 모두 마지막 시도가 11-07이다.
  - 새로 `start`한 행은 첫 회차에서 먼저 처리된다. **두 번째 회차부터는 11-07 잔여 10개가 먼저 처리된다.**
  - 이 가운데 220915IHB041(id 2270)은 ESM 판매불가(22)로 남아 `ESM_PENDING`이다.

### 2-5. 간섭
- 소싱처 배치: 도는 것 없음(2026-11-24 16:0x 조회, RUNNING·PAUSING 0).
- 서버 루프: 원장 기록상 없다. 실행 직전에 다시 본다.

## 3. 설계에서 정할 것 (페이블)
1. **판매 이력 있는 상품의 소프트 삭제 영향.** 주문 그리드·대시보드 집계·클레임과 반품 매칭·정산이 삭제 상품의 주문을 어떻게 다루는지 코드로 확인한다. 막는 것이 있으면 어떻게 할지 정한다. D-360 원안이 이 상품군을 "4단계, 따로 결정"으로 미룬 이유가 이것이다.
2. **미종결 주문 가드에 걸린 294·1376.** 다음 중 하나를 정한다. 가드는 바꾸지 않는다.
   - 주문 670·705의 실제 상태를 쿠팡에서 확인해, 동기화로 상태가 닫힌 뒤 퇴출한다.
   - 이번 대상에서 빼고 나중에 따로 한다.
3. **`advance` 범위.** 상품 지정이 없어 D-361 잔여 10개도 다시 시도된다. 다음 중 하나를 정한다.
   - (가) 잔여 10개를 이번 승인 대상에 "재시도"로 넣는다. 쿠팡 삭제를 다시 시도하는 것이고 3194는 어차피 대상이다.
   - (나) 첫 회차의 `limit`을 새 대상 수와 같게 묶고, 그다음은 (가)로 간다.
   - (다) 잔여분을 `cancel`한다. 쓰기 차단이 풀려 가격 배치가 다시 손댄다 — 권하지 않는다.
   - (라) `advance`에 상품 지정을 더한다. 코드 변경이고 배포가 따른다.
4. **ESM(G마켓·옥션).** D-361처럼 크롬으로 판매중지 → 삭제 → 검색 API로 부재를 확인한 뒤 `esm-confirm`한다. 63·294는 카페24가 이미 끊겼으니 ESM 잔존부터 확인한다.
5. **쿠팡 승인반려 6개.** 삭제 API가 승인반려 상품을 지우는지 모른다. 파일럿에 하나를 넣어 확인할지, 끝내 거부되면 사용자가 Wing에서 처리할지 정한다.
6. **파일럿 구성.** 4마켓이 모두 LINKED이고 미종결 주문이 없는 상품 1~2개(예: 1375 또는 1392)로 먼저 돌리고 재조회한다. 이어 나머지로 간다.

## 4. 실행 골격 (D-361 절차, 설계 확정 후 계획서로)
1. 간섭 확인(배치·루프·배포) → `pre` 덤프와 `OK kind=pre` 확인.
2. `POST /internal/retirement/start?dryRun=true`에 대상 id → 결과(WOULD_START·OPEN_ORDER)가 예상과 같은지 본다 → 승인 → `dryRun=false`.
3. `POST /internal/retirement/advance?dryRun=true&limit=…` → 마켓별 `WOULD_DELETE`를 확인한다 → 파일럿 1~2개 실제 실행 → 마켓마다 재조회한다.
4. ESM: `GET /internal/retirement/esm-targets` → 크롬으로 판매중지 → 삭제 → 부재 확인 → `POST /internal/retirement/esm-confirm`(20개 단위, `advance`와 동시에 돌리지 않는다).
5. `advance`로 카페24 삭제와 소프트 삭제를 한다 → DONE, `deleted_at`, 등록 행 상태를 재조회한다.
6. §7 확인(바뀐 행은 약 10개라 통계 영향은 작지만 상품 목록·주문 그리드·대시보드 화면은 본다), 주문 동기화 한 주기.
7. 원장 운영 조치 줄과 STATUS를 갱신한다.

## 5. 완료 기준 (초안)
- 대상 상품마다 다음 중 하나다.
  - DONE: 스마트스토어·쿠팡·카페24 삭제, 11번가 삭제 또는 판매중지, G마켓·옥션 부재 확인, `deleted_at` 기록.
  - 사유가 적힌 잔여: 미종결 주문, 쿠팡 거부.
- ESM 유령 리스팅 0.
- 대상 브랜드의 판매중 리스팅이 어느 마켓에도 없다(잔여는 사용자가 판매중지).

### 6-1. 추가로 확인한 사실 (2026-11-25 09:45 KST, 운영 `sbshop_ro` 읽기·`start` dry-run·코드)

- 대상·등록 상태·퇴출 행은 §2와 같다(살아 있는 두 브랜드 상품 11개, IN_PROGRESS 10·DONE 1,588). 도는 소싱처 배치 0, 대상 상품에 걸린 대기 가격 작업 0, 서버 루프 없음(`~/retire/loop.sh`는 파일만 남아 있고 프로세스 없음), api 헬스 UP.

  - 주문 동기화의 상품 매핑: 쿠팡·카페24·11번가는 등록 행의 식별자로(`MarketRegistrationLookup.findUnique` → `findIdentifierCandidates`, 연결 상태·삭제 여부 조건 없음), 스마트스토어·11번가는 `findBySbCode`로(삭제 조건 없음) 찾는다 → 퇴출 뒤 늦게 들어오는 반품·교환도 같은 상품에 붙는다.

### 6-2. 고정 결정

1. **소프트 삭제는 그대로 쓴다.** 판매 이력 상품이어도 주문·대시보드·클레임 경로를 막지 않는다(6-1). 코드 변경 없음.
2. **294·1376은 이번 실행에서 뺀다.** 가드는 바꾸지 않는다. 주문 670·705가 닫히면(배송 완료 또는 취소·반품 완료) 같은 절차로 따로 한다. 그때까지 쿠팡 밖 마켓(스마트스토어·11번가, 1376은 카페24·G마켓·옥션까지)의 판매를 멈출지는 사용자 결정(6-7).
3. **`advance`는 상품을 고를 수 없으므로 순서로 묶는다:** `start` → ESM 삭제·부재 확인 → `esm-confirm` → `advance?limit=새로 시작한 수`를 **한 번**. 새 행은 `last_attempt_at`이 NULL이라 먼저 잡히고(`findDue`), ESM 확인이 끝나 있어 한 회차에 카페24 삭제와 소프트 삭제까지 간다. D-361 잔여 10개는 이 회차에 닿지 않는다.
4. **두 번째 회차가 필요해지면**(쿠팡이 승인반려 상품의 삭제를 거부해 `COUPANG_REVIEW_PENDING`으로 남는 경우) D-361 잔여 10개가 먼저 잡힌다. 그 회차는 "잔여 10개의 쿠팡 삭제 재시도 9건 포함"이라고 적어 **따로 승인받는다.** 승인 없이 `limit`을 키워 돌리지 않는다. 코드 변경(상품 지정 추가)은 하지 않는다 — 임시 운영 중 배포를 늘리지 않는다.
5. **ESM은 사용자가 화면에서 지운다.** 이 세션에는 브라우저 조작 도구가 없다(`sbshop-ops-write` §8 마지막 줄). 세션은 대상 목록을 주고, 사용자가 "판매중지 → 삭제 → 판매자관리코드 검색 0건"을 본 코드만 `esm-confirm`에 넣는다. 확인하지 못한 코드는 넣지 않는다 — 그 상품은 `ESM_PENDING`으로 남고 카페24는 지워지지 않는다.
6. **쿠팡 승인반려는 파일럿의 1392로 확인한다.** 거부되면 실패가 아니라 예상 결과다. 그 경우 나머지 승인반려 5개는 본 실행 전에 사용자가 Wing에서 지운다(이미 4개를 그렇게 했다).
7. **파일럿 = 1375 + 1392.** 1375는 쿠팡이 이미 지워진 정상 경로, 1392는 쿠팡 승인반려 경로다. 둘 다 미종결 주문이 없고 스마트스토어·11번가·카페24·G마켓·옥션이 LINKED다.
8. 11번가는 삭제가 아니라 판매중지로 끝난다(도구 동작, D-361과 같다). 리스팅은 11번가에 판매중지로 남는다.

위임: 호출 사이 간격(`throttleMs` 기본 1,200ms 유지 권장), 원시 출력 파일 이름, 재조회 쿼리의 형태.

### 6-4. 실행 계획서 (`sbshop-ops-write` §4)

- **목적·근거:** D-369, 사용자 지시 2026-11-24 "관련 브랜드는 전부 삭제".
- **등급:** W3(마켓 상품 삭제 — 되돌릴 수 없음) + 마켓 대량(삭제·판매중지 합계 20건 초과) → 파일럿 승인, 본 실행 승인 두 번.
- **대상 기준:** `sb_product`에서 `deleted_at IS NULL`이고 브랜드가 노르딕내츄럴스 또는 라이프익스텐션인 것 가운데 6-3의 묶음. 제외: 미종결 주문 2개, 이미 퇴출 진행 중인 3194.
- **백업:** DB는 `start` 전에 `pre` 덤프(`OK kind=pre` 확인). 마켓 삭제는 백업 없음.
- **간섭 확인(단계마다 직전):** 소싱처 배치 RUNNING·PAUSING 0, 진행 중 배포 없음, 서버 루프 없음, 대상의 미종결 주문 없음(`start` dry-run이 다시 본다). 새벽 시간대(00:55, 02:00~04:30)에는 하지 않는다.
- **명령(api 컨테이너 안, 파일럿 기준 — 본 실행은 id·코드·`limit`만 바뀐다):**
  1. `~/ops-backup/sbshop-db-backup.sh pre`
  2. `docker exec projects-sbshop-api-1 curl -s -X POST 'localhost:8080/internal/retirement/start?dryRun=false' -H 'Content-Type: application/json' -d '[1375,1392]'` → 둘 다 `STARTED`
  3. 사용자: ESM에서 두 상품의 G마켓·옥션 리스팅 판매중지 → 삭제 → 판매자관리코드(`220130IHB042`, `220130IHB059`) 검색 0건 확인
  4. `docker exec projects-sbshop-api-1 curl -s -X POST 'localhost:8080/internal/retirement/esm-confirm' -H 'Content-Type: application/json' -d '["220130IHB042","220130IHB059"]'` → `confirmed` 2, `unmatched` 0 (`advance`와 동시에 돌리지 않는다)
  5. `docker exec projects-sbshop-api-1 curl -s -X POST 'localhost:8080/internal/retirement/advance?dryRun=true&limit=2'` → 대상이 1375·1392 둘뿐이고 마켓 결과가 `WOULD_DELETE`인지 본다. 다른 상품이 보이면 멈춘다
  6. 같은 명령을 `dryRun=false&limit=2`로 한 번
- **쓰기 뒤 재조회와 기대 값:**
  - `advance` 응답: 1375 = 스마트스토어 `DELETED`, 쿠팡 `DELETED`, 11번가 `ELEVENST_STOPPED`(또는 `DELETED`), 카페24 `DELETED`, `stage=DISPOSED`. 1392 = 쿠팡만 `DELETED` 또는 `COUPANG_REVIEW_PENDING`, 나머지는 1375와 같다.
  - DB(`sbshop_ro`): `DISPOSED`인 상품은 `sb_product.deleted_at` 기록, 퇴출 행 DONE, 등록 행이 스마트스토어·쿠팡·카페24 `DETACHED_DELETED`, G마켓·옥션 자식 `DETACHED_DELETED`, 11번가 LINKED(판매중지). 주문 줄은 그대로.
  - 마켓 부재는 도구가 같은 계정 재조회로 확인한 것만 `DELETED`로 적는다. 응답에 그 밖의 결과가 있으면 "미확인"으로 남긴다.
- **원복:** 마켓 삭제는 되돌릴 수 없다(다시 팔려면 새로 등록). `start`만 한 단계에서는 `/internal/retirement/cancel`로 쓰기 차단을 푼다. 소프트 삭제는 `deleted_at`을 쓰기 도구로 비울 수 있지만 마켓 리스팅은 돌아오지 않는다.
- **중단 조건:** ① `start`·dry-run 결과가 예상과 다르다 ② `advance` dry-run에 대상 밖 상품이 보인다 ③ 실제 회차에 `FAILED`·`MANUAL`·`SKIPPED_CONFLICT`·`BLOCKED_OPEN_ORDER`가 하나라도 있다 ④ `esm-confirm`의 `unmatched`가 0이 아니다 ⑤ api 로그에 새 ERROR·SQLState. 예상 결과(실패로 세지 않음): 11번가 `ELEVENST_STOPPED`, 스마트스토어 금지 2개와 63의 카페24 `ALREADY_DONE`, 승인반려 상품의 `COUPANG_REVIEW_PENDING`.
- **쓰기 뒤 확인(§7):** DB에서 바뀌는 행은 상품 8개·등록 약 40행으로 대량이 아니다. 그래도 사용자 화면 세 곳(상품 관리 목록, 통합 주문 관리, 대시보드)이 열리는지, api 로그 ERROR·SQLState, 주문 동기화 한 주기(30분)를 본다. `ANALYZE`는 하지 않는다(통계가 바뀔 규모가 아니다).

### 6-5. 단계

1. 파일럿 승인 → 6-4의 1~6 → 재조회 → 보고.
2. 1392의 쿠팡 결과에 따라: `DELETED`면 그대로 본 실행, `COUPANG_REVIEW_PENDING`이면 사용자가 Wing에서 승인반려 6개(122·1374·1384·1388·1389·1392)를 지운다.
3. 본 실행 승인 → 6개로 같은 순서(`limit=6`).
4. 쿠팡이 남은 상품이 있으면 결정 4의 회차를 따로 승인받는다(잔여 10개 재시도 포함, `limit` = 10 + 남은 수).
5. §7 확인 → 원장 운영 조치 줄·STATUS.

### 6-6. 완료 기준

- 파일럿·본 실행 8개: DONE이고 `deleted_at`이 찍혔거나, 사유가 적힌 잔여(쿠팡 삭제 거부)다.
- 8개의 G마켓·옥션 리스팅은 사용자가 검색 0건을 확인했다.
