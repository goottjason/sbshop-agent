# D-265 주문 상태·송장 단일 진실 설계

작성 2026-09-01 · 사용자와 브레인스토밍으로 확정 · 상태: **설계 확정, 미착수**

관련 결함: [[D-160]](판정 범위 가드) · [[D-262]](품절 재전송) · [[D-264]](30일 창) · D-107/108(PII 마스킹) · D-144~150(송장 진실)

---

## 왜 하는가

주문 상태와 송장을 쓰는 주체가 넷(마켓 동기화·iHerb 메일·수동 입력·레거시 백필)인데, **누가 이기는지에 대한 규칙이 없다.** 두 종류가 섞여 있다.

- 마켓 vs 우리 → **먼저 채운 쪽이 이김** (`OrderShipmentUpsertService`: `if (!shipment.hasOwnTracking())`)
- 메일 vs 수동 → **나중에 쓴 쪽이 이김** (`Shipment.applyTracking`·`applyTrackingSource` 에 순위 없음)

상태도 마찬가지다. `MarketLineItemSyncDispatcher` 는 마켓 값을 무조건 덮고, `OrderService`·`OrderShipProcessor` 는 로컬로 상태를 찍고, 클레임 감지는 `isNonTerminal` 인 것만 본다. 규칙이 네 곳에 흩어져 서로 모른다.

실제 피해:

| 증상 | 원인 |
|------|------|
| GMARKET 4462952064 가 두 달째 "배송중"(2026-06-30 주문, 마지막 갱신 08-08) | 주문일 30일 창 밖으로 나가 조회 대상에서 빠짐 |
| 배송완료된 뒤 반품된 건이 영영 반영 안 됨 | `isNonTerminal` 이 배송완료를 "끝난 것"으로 보고 추적 제외 |
| 마켓에서 송장을 고쳐도 화면이 안 바뀜 | 우리 `tracking_no` 를 메인으로 보여주는데 그건 메일 값이다 |

---

## 지배 원칙

> **마켓이 단일 진실 원본이다.** 우리는 마켓 상태를 거울처럼 비춘다. 우리가 하는 것은 명령(호출)뿐이고, 값은 언제나 마켓에서 다시 읽어와 갱신한다.

마켓 사이트에 하나하나 들어가 확인하지 않으려고 만든 시스템이다. 그러려면 화면이 마켓과 100% 같아야 한다.

**적용 범위는 두 필드로 한정한다** — `shipping_status`, `market_tracking_no`. 나머지에 적용하면 이미 고쳐둔 결함이 되살아난다.

## 1. 필드별 소유권

| 필드 | 진실의 주인 | 규칙 |
|------|-----------|------|
| `shipping_status` | **마켓** | 마켓 값 그대로. 전이 가드·단조성 없음. `UNKNOWN` 만 무시 |
| `sb_shipment.market_tracking_no` | **마켓** | 마켓에서 읽은 값 그대로. 화면의 **메인 송장** |
| `sb_shipment.tracking_no` | **iHerb 메일** | 실제 물건이 오는 송장. 화면의 **보조 송장**. 마켓 값이 덮지 않음 |
| 수취인 이름·주소·연락처 | 마켓, **단 의미 있는 값만** | `isMeaningfulPii` 가드 유지 (D-107/108). 마스킹·빈 값이 실값을 덮으면 안 된다 |
| 정산액 | 마켓, **단 확정된 값만** | `recoverSettlementIfZeroed` 유지. 확정 전 0 이 정산을 0 으로 덮으면 안 된다 |

## 2. 송장 — 경합이 아니라 대조

두 값은 **서로 다른 것을 가리킨다.**

- `market_tracking_no` = 마켓에 실제로 박혀 있는 송장 = **구매자가 조회하는 값**
- `tracking_no` = iHerb 가 알려준 송장 = **실제로 물건이 오는 값**

발송 후 송장 수정 API 는 **쿠팡만 가능**하고 11번가·스마트스토어·G마켓·옥션은 영구 불가다([[market-tracking-edit-capability]]). 그러니 마켓 값을 우리가 맞출 수 없는 게 정상 상태다. 덮어쓰기 경쟁을 붙일 게 아니라 **나란히 놓고 대조**해야 한다.

| 상태 | 의미 | 화면 |
|------|------|------|
| 마켓 = 메일 | 정상 | 마켓 송장만 표시 |
| 마켓 ≠ 메일 | **구매자가 엉뚱한 송장을 추적 중** | 마켓 송장 + 그 아래 작게 메일 송장, **빨강** |
| 마켓 없음 · 메일 있음 | 아직 전송 안 됨 또는 전송 실패 | 전송 필요 표시 |
| 둘 다 없음 | 발송 전 | — |

메인 송장은 **읽기 전용 텍스트**다. 입력창이 아니다.

**불일치 조치**

- 쿠팡: 감지 즉시 **자동 재전송**. 실패하면 빨간 표시로 남긴다
- 나머지 4마켓: 표시만. 사람이 마켓 페이지에서 처리한다

---

## 3. 송장 입력 경로

| 상태 | 수동 입력 |
|------|----------|
| `NEW`(결제완료) | **불가** — 주문확인을 거쳐야 구매준비가 된다 |
| `PREPARING`(구매준비) | **가능** — 유일한 입력 시점 |
| `DISPATCHED` 이후 | **불가. 경로 자체를 화면에서 제거** |

현행 `OrderService:394` 의 *"송장 수정은 DISPATCHED 또는 SHIPPED 상태에서만 가능합니다"* 를 **뒤집는다.** 지금은 발송 *후에만* 열려 있는데, 발송 후에는 대부분의 마켓에서 고칠 수 없으므로 그 경로는 존재할 이유가 없다.

`TrackingSource.MANUAL` 은 PREPARING 1회 입력으로 축소된다. 사후 개입 경로가 사라지면서 "메일이 수동을 덮는지, 수동이 메일을 덮는지" 문제 자체가 소멸한다.

## 4. 상태 — terminal 개념 폐기

배송완료 → 반품, 반품 → (고객 변심) 배송완료. **상태는 양방향으로 뒤집힌다.** `isNonTerminal()` 로 배송완료·취소·반품·교환을 "끝난 것"으로 보고 추적에서 빼는 현행 방식은 틀렸다.

- **추적 대상 = 주문일로부터 120일 이내의 모든 주문** (상태 무관)
- 120일: 청약철회 7일·하자반품 30일을 넘어 늦게 들어오는 클레임까지 덮는 여유

**`DISPATCHED` 의 처리**

`DISPATCHED`(배송지시)에 대응하는 마켓 상태는 쿠팡(`DEPARTURE`)·스마트스토어(`DISPATCHED`)에만 있다. 11번가·G마켓/옥션은 발송하면 곧장 배송중이다.

- `shipping_status` 는 마켓 값 그대로 둔다 → 두 마켓에서는 `DISPATCHED` 가 나타나지 않는다
- 우리가 송장을 보냈는지는 **별도 배지**로 표시한다 — 기존 `tracking_sent_to_market` · `shipped_at` 을 쓴다
- 상태를 오염시키지 않고 "보냈는데 아직 배송 시작 안 됨"을 구분할 수 있다

## 5. 동기화 파이프라인 — 3층

세 층 모두 **같은 반영 경로**(`MarketLineItemSyncDispatcher`)를 쓴다. 상태 판정 로직이 층마다 갈리지 않는다.

| 층 | 주기 | 대상 | 방식 | 목적 |
|----|------|------|------|------|
| **수집** | 30분 | 주문일 30일 창 | 마켓 **목록** 조회 | 신규 주문 발견 + 최근 주문 갱신 |
| **확증** | **1시간** | 주문일 120일 창 | 마켓 **목록** 조회 → 목록에도 없는 주문만 **단건** 조회 | 창 밖 주문의 상태 추적 |
| **즉시** | 명령 직후 | 그 주문 1건 | 마켓 **단건** 조회 | 명령↔반영 공백 제거 |

**확증층을 목록 조회로 도는 이유.** 30~120일 구간에 234건(쿠팡 188 · 스마트스토어 22 · 11번가 14 · G마켓 8 · 옥션 2)이 있다. 이걸 매 회차 단건으로 물으면 회차당 234회다. 목록으로 훑으면 회차당 100회 남짓이다.

| 마켓 | 120일 목록 조회 1회당 | 비고 |
|------|---------------------|------|
| 쿠팡 | 24회 (31일 청크 4 × 상태 6) | ordersheets 에 조회 기간 제한이 있어 청크 필요 |
| 11번가 | 72회 + sleep 36초 (7일 청크 18 × 소스 4) | 가장 무겁다 — 주기를 1시간으로 잡은 이유 |
| 카페24 | 페이징 수 회 | |
| 스마트스토어 | **불필요** | `last-changed-statuses`(변경일 기준)라 30일 창으로도 오래된 주문이 잡힌다 |

하루 호출량: 11번가 1,728회 · 쿠팡 576회. 30분으로 하면 11번가가 매 사이클 72회+36초 sleep 을 돌아 30분 주기 동기화 5개와 겹쳐 스케줄러가 밀린다.

## 6. 명령 경로 — "호출하고, 다시 읽는다"

```
주문확인 / 발송처리 / 송장수정
  → 마켓 API 호출
  → (로컬 상태를 건드리지 않는다)
  → 즉시 단건 재조회 → 마켓 값으로 갱신
  → 마켓이 아직 안 바뀌었으면 짧게 재시도
  → 그래도 그대로면 '요청함' 표식 (다음 정기 동기화가 갱신)
```

제거 대상: `OrderService` 가 로컬로 `PREPARING`·`DISPATCHED`·`CANCELED` 를 찍는 코드, `OrderShipProcessor:74` 의 `DISPATCHED` 낙관적 갱신.

## 7. 확증 조회 — 추정 폐지

```
120일 목록 조회 응답에도 없는 주문
  → 그 주문을 마켓에 단건으로 물어본다
  → 답하면 그 값으로 갱신
  → "그런 주문 없다"면 miss 카운트 +1
  → miss 10회 누적 → '확인 필요' 목록으로 넘기고 자동 조회 중단
```

miss 가 쌓이는 경우: 마켓에서 주문이 삭제·병합됨, 우리가 주문번호를 잘못 저장함(G마켓 유령 리스팅 전례), 마켓 API 조회 보관 기간 초과, 테스트 주문.

**이것으로 D-160 가드가 통째로 불필요해진다.** D-160("백필에 상태 판정 권한은 없다")은 *추정* 때문에 존재한다 — 쿠팡 `detectCancellations` 가 "API 응답에 없으면 취소된 것"이라고 추정하므로, 조회 범위가 좁으면 멀쩡한 주문을 취소로 오판한다. 추정을 없애고 전부 확증하면 판정 범위를 제한할 이유가 사라진다.

## 9. 구현 분할 — 4단계

각 단계가 독립 배포 가능하고, 뒤 단계가 앞 단계에 의존한다.

| 단계 | 내용 | 위험 |
|------|------|------|
| **1. 확증층 도입** | 마켓별 단건 조회 포트 정비 → 120일 목록 조회 + 단건 확증 → `detectCancellations` 제거 → D-160 가드 제거 → `reconcileOpenOrders` 대체 | 중 |
| **2. terminal 폐기 + 120일 추적** | `isNonTerminal` 필터 제거, 추적 대상을 주문일 기준으로 전환, miss 카운터 · '확인 필요' 목록 | 낮 |
| **3. 명령 경로 전환** | 로컬 낙관적 갱신 제거 + 즉시 단건 재조회 | **높음** — 주문확인·발송처리 전 경로가 바뀐다 |
| **4. 송장 대조 UI + 입력 경로 이전** | 마켓송장 메인 / 메일송장 보조 / 불일치 빨강, 쿠팡 자동 재전송, 입력을 PREPARING 으로 이동, DISPATCHED 이후 경로 제거 | 중 (프론트 포함) |

**1단계를 먼저 하는 이유**: 3단계(명령 후 재조회)가 단건 조회 인프라에 의존한다. 그리고 1·2단계만 끝나도 "두 달째 배송중" 같은 건이 해소된다.

## 착수 전 실측 — **완료 (2026-09-01, 운영 자격증명 실호출)**

**결론: 4개 마켓 모두 단건 확증 조회가 가능하다. 설계에 예외가 필요 없다.**

| 마켓 | 경로 | 오래된 주문 | 클레임 주문 | "없는 주문" 구분 |
|------|------|-----------|-----------|----------------|
| **쿠팡** | `GET /v2/.../vendors/{vendorId}/{orderId}/ordersheets` | ✅ 45일·41일 전 `200 status=FINAL_DELIVERY` | ✅ `400` **"해당 주문이 취소 또는 반품 되었습니다."** | ✅ `400` "유효하지 않은 주문번호 입니다." |
| **카페24**(G마켓/옥션) | `GET /api/v2/admin/orders/{order_id}` | ✅ 63일 전 조회됨 | ✅ `canceled='T'` + `return_confirmed_date` | ✅ `{"order": null}` |
| **11번가** | `GET /rest/claimservice/orderlistall/{ordNo}` | ✅ 36일 전 조회됨 | ✅ `ordPrdStatNm='취소완료'` | ✅ 빈 응답(본문 240B, 상태 필드 없음) |
| **스마트스토어** | `POST /external/v1/pay-order/seller/product-orders/query` | 불필요 — `last-changed-statuses`(변경일 기준) | — | 기존 동기화 경로가 매 30분 실사용 중 |

**가장 큰 성과 — 쿠팡이 추정을 필요 없게 만든다.** 반품된 주문은 "사라지는" 게 아니라 **명시적 메시지로 답한다.** `"해당 주문이 취소 또는 반품 되었습니다."`(종결됨)와 `"유효하지 않은 주문번호 입니다."`(진짜 없음)가 **서로 다른 문구**다. `detectCancellations` 의 추정을 이 두 문구 판별로 그대로 대체할 수 있다.

**주의 사항**

1. **쿠팡은 취소와 반품을 구분해 주지 않는다** — 한 문구다. 세부 구분은 기존 `detectReturns`(returnRequests API, 반품 접수일 기준으로 DB 전체와 대조)가 계속 담당한다.
2. **쿠팡 429(호출 제한)가 실제로 발생했다.** 연속 호출 시 간격이 필요하다. 3초 간격 5회는 문제없었다. 확증 대상이 소수라 실무상 부담은 없다.
3. **카페24 단건 조회 응답 키는 `order`(단수)** 다. 목록 조회의 `orders`(복수)와 다르다. 실측 중 이걸 혼동해 "카페24가 주문을 모른다"고 잘못 읽었다.
4. **문구 매칭은 마켓이 바꾸면 깨진다.** [[market-tracking-edit-capability]] 의 함정과 같은 성격이다. 문구가 안 맞으면 **상태를 바꾸지 말고 miss 로 처리**해야 한다 — 모르면 건드리지 않는 쪽이 안전하다.
