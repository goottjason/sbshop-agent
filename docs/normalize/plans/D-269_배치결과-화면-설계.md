# D-269 배치 결과·활동로그 화면 설계

## 무엇이 문제인가

D-266 검증 배치를 직접 돌리며 겪은 것을 근거로 쓴다. 추정이 아니다.

배치 `afc4a348` 을 돌렸다. 화면은 이것만 보여줬다:

```
5 / 5 (100%)   성공 1 · 실패 4 · 대기 0
완료 (성공 1 / 실패 4)
batchId: afc4a348
```

이 화면으로는 **아무것도 알 수 없다.** 어떤 상품이 실패했는지, 왜 실패했는지, 무엇을
해야 하는지. 나는 서버에 SSH 로 들어가 DB 를 조회해서야 답을 얻었다.

그런데 DB 를 보니 답은 처음부터 거기 있었다:

| product_code | step | status | message |
|---|---|---|---|
| 1916 | UPDATE_PRODUCT_ERROR | FAILED | 매입 원가가 없다 — 판매가를 만들 수 없다 |
| 2069 | UPDATE_PRODUCT_ERROR | FAILED | 매입 원가가 없다 — 판매가를 만들 수 없다 |
| 2096 | UPDATE_PRODUCT_ERROR | FAILED | 매입 원가가 없다 — 판매가를 만들 수 없다 |
| 2980 | UPDATE_PRODUCT_ERROR | FAILED | 매입 원가가 없다 — 판매가를 만들 수 없다 |
| 3020 | UPDATE_PRODUCT_SAVE | **SUCCESS** | 가격:20500, 재고:0 · 마켓반영 성공2/스킵1/**실패1 ([SMART_STORE])** |

**이 문서의 결론은 여기서 나온다: 데이터는 이미 충분하다. 화면이 안 보여줄 뿐이다.**
`GET /api/v1/products/batch/status/{batchId}` 는 이 행들을 그대로 돌려주는데,
`BatchUpdatePage` 는 `/summary` 만 호출하고 이 엔드포인트를 쓰지 않는다.

## 다섯 가지 결함

### 1. 완료 표시가 거짓말을 한다 (가장 심각)

위 표의 3020 을 보라. `process_status = SUCCESS` 인데 스마트스토어 전송은 **실패했다**
(`실패1 ([SMART_STORE])`). 배치 요약은 이걸 성공 1건으로 센다.

원인: 배치의 성공/실패는 **상품 저장이 됐는지**를 세지, **마켓에 전달됐는지**를 세지
않는다. 어제 "완료 (성공 3 / 실패 0)" 으로 남은 배치도 실제로는 스토어 1건이 400 이었다.

이건 표시 문제가 아니라 **집계 정의 문제**다. 화면만 고치면 안 된다.

### 2. 실패 사유가 화면에 없다

`message` 컬럼에 "매입 원가가 없다 — 판매가를 만들 수 없다" 라고 한국어로 정확히
적혀 있다. 화면에는 안 나온다.

특히 오늘 두 종류의 실패가 섞여 있었는데 화면에서는 구분되지 않았다:
- **크롤 실패** — 아이허브가 `costPrice: null` 을 줌. 마켓에 요청조차 안 감 ([[D-281]])
- **마켓 거부** — 네이버가 `판매가 10원 단위` 로 400 ([[D-280]])

이 둘은 해야 할 일이 완전히 다르다. 전자는 소싱처 문제, 후자는 우리 코드 문제.

### 3. 실행 대화상자 버튼에 라벨이 없다

상품관리 → "선택 가격/재고 업데이트" 대화상자의 확인·취소가 접근성 트리에
`button (unnamed)` 두 개로 나오고 화면에도 흰 박스로 보인다. **어느 쪽이 실행인지 알 수
없어 세 번 헛클릭했다.**

### 4. 실패 건만 다시 돌릴 방법이 없다

36건을 돌려 4건이 실패했을 때, 그 4건을 다시 돌리려면 DB 에서 product_id 를 캐내
쉼표로 이어 붙여 손으로 넣어야 한다. 오늘 내가 그렇게 했다.

### 5. 상품 선택 경로가 실용적이지 않다

상품관리 그리드에서는 "스토어 전송 실패한 것" 같은 조건으로 좁힐 수 없어 SB코드로 한
건씩 검색해야 한다. 배치 페이지의 "상품ID 지정" 탭이 훨씬 나은데 **상품 ID 를 알아야 해서
결국 DB 를 봐야 한다.**

## 설계

### A. 집계 정의를 바로잡는다 (백엔드 — 행위 변경)

`ProcessStatusType` 에 부분 성공을 들인다. 마켓 전송이 하나라도 실패하면 `SUCCESS` 가
아니다.

```
SUCCESS         모든 마켓 전송 성공 (또는 전송 대상 없음)
PARTIAL_FAILED  상품 저장은 됐으나 일부 마켓 전송 실패   ← 신설
FAILED          상품 저장 자체 실패
```

`BatchSummary` 에 `partial` 을 더한다. 화면 문구는 `성공 32 · 부분실패 3 · 실패 1`.

**주의:** enum 값 추가는 CHECK 제약을 같이 고쳐야 한다 ([[D-276]] 에서 이걸 놓쳐 한 시간
넘게 트랜잭션이 롤백됐다). `sb_process_status_process_status_check` 를 먼저 확장한다.

회귀 고정: 마켓 하나가 실패한 회차가 `PARTIAL_FAILED` 로 집계되는지, 요약의
`success` 에 안 들어가는지.

### B. 결과를 행으로 보여준다 (프론트 — 신규)

`BatchUpdatePage` 진행현황 아래에 결과 표를 붙인다. 데이터는 이미 있는
`getBatchStatus(batchId)` 를 쓴다. **백엔드 추가 없음.**

| 상품 | 결과 | 사유 |
|---|---|---|
| 231114IHB021 | 부분실패 | 스토어 — 판매가 항목은 10원 단위로 입력해 주세요 |
| 1916 | 실패 | 매입 원가가 없다 — 판매가를 만들 수 없다 |
| 2069 | 성공 | 가격 20,500 · 재고 0 |

- 진행 중에는 폴링으로 행이 차오른다 (지금도 요약을 폴링하니 같은 주기에 얹는다)
- 기본은 **실패·부분실패만** 펼친다. 성공 행은 접어 둔다 — 볼 이유가 없다
- 사유는 마켓별로 한 줄. `details` 의 병합 문자열을 그대로 뱉지 말고 갈라서 보여준다
- 실패 원인을 두 갈래로 나눠 배지를 다르게: `소싱처` (크롤 실패) / `마켓` (전송 거부)

### C. 실패 건만 재실행 (프론트 + 기존 API)

결과 표 위에 `실패 4건만 다시 실행`. 실패 행의 상품을 모아 같은 파라미터로
`crawlAndUpdate` 를 다시 부른다. 파라미터는 방금 돌린 값을 그대로 쓴다 — 다시 입력받지
않는다.

### D. 버튼 라벨 (프론트 — 결함 수정)

상품관리 일괄 대화상자의 확인·취소에 텍스트를 넣는다. `실행` / `취소`.
`aria-label` 이 아니라 **보이는 글자**로 — 흰 박스로 보이는 게 실제 문제다.

### E. 활동로그(`ProcessStatusPage`) 정리

지금은 상품 단위 행이 시간순으로 흐른다. 배치 단위로 접어서, 펼치면 B 의 결과 표와 같은
모양이 나오게 한다. B 를 컴포넌트로 만들어 두 화면이 같이 쓴다.

## 범위 밖

- 상품관리 그리드의 조건 검색(관찰 5) — 그리드 필터 작업이라 결이 다르다. 별도로 뗀다.
- [[D-280]] 10원 단위 · [[D-281]] 옛 오류 잔류 — 각자 결함으로 등재됐다. 이 화면 작업과
  독립적으로 고친다.

## 작업 순서

A(집계 정의) → B(결과 표) → C(재실행) → D(버튼) → E(활동로그).

A 가 먼저인 이유: B 가 보여줄 값의 정의가 A 에서 정해진다. A 없이 B 를 만들면 화면이
여전히 "성공"이라고 적힌 부분실패 건을 성공으로 그린다.

D 는 어디에 끼워도 되는 독립 수정이다. 급하면 먼저 빼서 해도 된다.
