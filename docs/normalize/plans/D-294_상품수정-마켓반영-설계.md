# D-294 상품 수정 → 마켓 반영 설계 (2026-09-05)

## 왜 하는가 — 두 전수조사가 확정한 사실

**우리 쪽**: 상세 모달에서 편집 가능한 필드 중 **마켓에 반영되는 것은 판매가·재고·이미지뿐이다.**
브랜드·상품명·바코드·무게·제조사 등 12개 필드는 저장하면 DB에만 박히고 마켓은 모른다.
`ProductManageUseCase.updateProduct` 에 마켓 동기화 호출이 아예 없다. 사용자는 이 차이를
화면에서 알 수 없다 — **"저장했는데 왜 마켓엔 그대로지?"가 구조적으로 예정된 함정**이다.

**마켓 쪽**: 4마켓의 "수정"은 성격이 전부 다르다.

| 마켓 | 수정 방식 | 게이트 | 함정 |
|---|---|---|---|
| 쿠팡 | 전체 JSON 재제출 | **승인필요 → 심사중 전환** | 가격·재고만 전용 API로 즉시. 카테고리는 등록 후 변경 불가 |
| 스토어 | 원상품 전체 PUT | 없음(즉시) | `leafCategoryId` 변경이 **조용히 무시**됨. 옛상품 400(consumptionDateText) |
| 11번가 | 전체 XML 덮어쓰기 | 없음(즉시) | GET→치환→PUT 필수(안 하면 데이터 소실). 바코드 필드 자체가 없음 |
| 카페24 | **부분 병합(PATCH형)** | 없음(즉시) | 바코드는 옵션상품만(단일 422). brand 는 코드값 |

## 설계 원칙 다섯

1. **저장과 반영을 분리한다.** "저장"은 DB만. "마켓 반영"은 명시적 행동이다.
   쿠팡은 반영이 곧 심사 트리거라 — 사용자가 모르고 누르게 만들면 안 된다.
2. **필드마다 어디에 반영되는지 화면이 말한다.** 반영 불가 필드(카테고리)는 그렇게 표시한다.
3. **신선 GET → 해당 필드만 치환 → PUT.** [[barcode-market-push]] 원칙. 특히 11번가는
   이걸 안 하면 데이터가 사라진다.
4. **결과는 마켓별로, 사유와 함께, 재시도 가능하게.** [[D-269]] 인프라(1행 process_status +
   details JSON + BatchResultTable) 재사용 — 조사로 재사용 가능성 확인됨.
5. **모르는 필드는 보내지 않는다.** 변경된 필드만 diff 로 골라 마켓별 지원 여부를 거른다.

## 화면 설계 (상세 모달 개편)

### ① 필드 행 — 반영 대상 마켓을 칩으로

```
기본 정보
  브랜드    [카탈리나크런치        ]   반영: 쿠①  스②  11③  카④
  카테고리  [— 선택 —             ]   반영: 없음(마켓은 등록 시에만)
  상품명    [(2팩) 카탈리나크런치…  ]   반영: 쿠 스 11 카
```
- 칩 상태: 채움=반영 가능, 회색=미등록 마켓, 빗금=마켓이 수정 불가
- 쿠팡 칩엔 항상 작은 ⚠(심사) 마크

### ② 저장 후 — "마켓 반영" 패널 (변경 필드가 있을 때만 활성)

```
┌ 변경된 필드: 브랜드, 상품명 ───────────────────────────────┐
│ 반영할 마켓                                                │
│  ☑ N스토어(즉시)  ☑ 11번가(즉시)  ☑ 카페24(즉시)           │
│  ☐ 쿠팡 ⚠ 반영하면 심사중으로 전환되어 판매가 잠시 중단됩니다 │
│                                     [ 마켓에 반영하기 ]   │
└───────────────────────────────────────────────────────────┘
```
- 즉시 마켓은 기본 ON, **쿠팡은 기본 OFF**(명시적 선택)
- 변경 필드 중 특정 마켓이 지원 안 하면 그 마켓 줄에 "바코드는 11번가 미지원 — 건너뜀" 표기

### ③ 결과 — 모달 안에서 마켓별 성공/실패/사유/재시도

```
┌ 반영 결과 ─────────────────────────────────────────────────┐
│  N스토어   ✓ 반영됨                                        │
│  11번가    ✓ 반영됨                                        │
│  카페24    ✕ 400 — brand 는 코드값이어야 합니다   [재시도]  │
└───────────────────────────────────────────────────────────┘
```
- 구현: 저장 시 1행짜리 `sb_process_status` 배치 생성 → `details` JSON → `BatchResultTable` 재사용

## 구현 단계 (각 단계가 독립 배포 가능)

| 단계 | 내용 | 비고 |
|---|---|---|
| 1 | **필드 diff + 마켓별 syncFields(신선GET→치환→PUT)** 백엔드 골격. 1차 필드: 브랜드·상품명·제조사 | 스토어·11번가·카페24 만. 쿠팡 제외(심사+gating) |
| 2 | 모달 개편: 반영 칩 + 저장/반영 분리 + 결과 패널 | D-269 컴포넌트 재사용 |
| 3 | 쿠팡 반영(옵트인 + 심사 경고) | [[D-260]] gating 해소 후 |
| 4 | 조건부 필드 확장(무게·검색키워드·원산지) + 카페24 brand_code 해소 | 문서 확보 후 |

## 선행 결함 (조사가 발견 — 별도 등재)

- 카페24 `brand`(텍스트) 전송 — 스키마는 `brand_code`(코드값). 무시되고 있을 가능성
- 카페24 `origin_place_value` 단독 전송 — 문서 조건("기타"일 때만) 위반 의심
- 카페24 `product_weight`·`product_tag` 필드가 있는데 미배선
- 11번가 상세설명 전용 부분수정 API 미사용(전체 XML 라운드트립 — 소실 위험 구조)
- 판매가 저장 시 이중 기록(updatePriceStock + updateProduct)
