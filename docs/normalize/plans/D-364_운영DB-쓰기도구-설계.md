# D-364 운영 DB 쓰기 도구 — 설계서

- 작성: 2026-11-18 (설계 세션) · 구현: 별도(오푸스) · 등급: **중대**(운영 쓰기 도구 — 검증자 PASS + 커밋 전 사용자 승인)
- 근거: D-363 결과서 "다음 작업 후보 ①", 운영 DB 보호 설계의 계층 2("스스로 멈추게")

## 1. 목적과 배경

운영 DB의 데이터 정정(UPDATE·DELETE·INSERT)을 지금은 superuser로 `psql`에 직접 친다. 승인은 의도한 작업만 걸러 줄 뿐, 승인받은 SQL의 오타·잘못 잡은 WHERE·건수 폭주·백업 누락은 막지 못한다. 사람이 지키던 절차(트랜잭션, 백업 테이블, 예상 건수 대조, 쓰기 전 덤프)를 **스크립트 하나**가 대신 강제하게 한다. 데이터 정정은 앞으로 이 도구로만 한다. DDL은 대상이 아니다(추가형 DDL 절차는 따로 있다).

## 3. 고정 결정 (구현자가 바꾸지 않는다)

| # | 결정 | 이유 |
|---|------|------|
| K1 | **자유 SQL을 받지 않는다.** 입력은 작업 파일(TOML)이고 문장은 도구가 조립한다. 종류는 `update`·`delete`·`insert` 셋 | WHERE를 빠뜨린 UPDATE/DELETE, DROP, TRUNCATE를 "검사해서 거부"하는 대신 **표현할 수 없게** 한다(무조건 조건 `true`는 표현되지만 건수 대조와 대량 표시가 잡는다). **백업한 행 = 바꾼 행**은 조건을 단계마다 한 번만 평가해 얻은 행 식별자(ctid) 집합으로 보장한다(§4-3) — 같은 조건을 두 번 평가하면 `LIMIT`(ORDER BY 없음)·`random()` 같은 비결정 조건에서 둘이 갈릴 수 있다(검증 1차 H1) |
| K2 | **앱 역할 `sbshop`으로 접속한다**(superuser 아님). 쓰기 뒤 확인만 `sbshop_ro` | 정정에 superuser가 필요 없다(F2). 권한이 작을수록 실수의 범위가 작다 |
| K3 | **한 트랜잭션, `REPEATABLE READ`.** 건수 대조와 중단은 서버 안(`DO` 블록의 `RAISE EXCEPTION`)에서 한다 | 고르기·백업·변경이 한 스냅샷을 본다. 그 사이 다른 트랜잭션이 대상 행을 바꾸면 직렬화 오류로 전체가 취소되고, 스냅샷 안에서는 ctid가 변하지 않는다. 클라이언트가 죽어도 커밋 전이면 롤백이다 |
| K4 | 단계마다 **백업 테이블을 먼저** 만들고, 백업 행 수·영향 행 수가 모두 `expect`와 같을 때만 다음으로 간다. 하나라도 다르면 전체 `ROLLBACK`. `expect`는 필수이고 1 이상이다 | 건수 폭주·조건 오해를 스스로 멈춘다. "0건 성공"은 성공이 아니다 |
| K5 | 백업 테이블 이름은 `bak_d{결함번호}_{접미}` 하나로 통일. 이미 있으면 실행하지 않는다 | 이름 세 갈래(F7)를 끝낸다. 같은 작업을 두 번 실행해도 두 번째는 거부된다(재실행 안전) |
| K6 | `lock_timeout=5s`, `statement_timeout=120s` 고정. 인자로 못 바꾼다 | 앱과 같은 인스턴스다. 오래 걸리는 정정은 나눠서 한다 |
| K7 | `apply`의 선행 조건 넷: ① 같은 작업 파일(SHA-256)의 **dry-run 성공 기록** ② `--confirm <해시 앞 12자>` 일치 ③ **30분 이내의 전체 덤프**(F5의 완성 파일 + `.sha256` + 로그의 OK 줄) ④ **사전 확인** — 읽기 전용 역할로 이 작업의 백업 테이블이 하나도 없음을 확인(확인 자체가 안 되면 거부). 건너뛰는 옵션은 만들지 않는다 | dry-run을 먼저 돌린다는 규칙, 승인받은 그 파일만 실행한다는 규칙, 덤프 없이는 쓰지 않는다는 규칙을 코드로 옮긴 것. ④는 "실행 뒤 백업 테이블이 있다 = 이번 실행이 커밋됐다"를 모호함 없이 만들고, 쓰기 뒤 확인 경로가 살아 있는지를 쓰기 전에 본다 |
| K8 | 대량(단계 `expect` 합이 200 초과, 또는 어느 단계가 그 테이블 행의 5% 초과)은 `apply`에 `--bulk`가 있어야 한다. dry-run은 대량 여부를 보여 주기만 한다 | 대량은 승인 절차가 다르다(파일럿 → 본 실행). 도구가 그 사실을 드러낸다 |
| K9 | 조각(`where`·`set`·`from`·`source`)에는 문자열 밖의 `;`·주석(`--`, `/*`)·`$`·역슬래시(어디서든)·제어 문자·괄호 불균형·금지어가 있으면 거부한다. 판단이 안 서면 거부한다 | 조각이 문장 경계를 넘지 못하게 한다. 실수 방지 장치이지 보안 경계가 아니다 — 서버 안에서는 누구나 `psql`을 칠 수 있다(F3) |
| K10 | 대상 테이블은 public의 일반 테이블만. 이름이 `bak_`·`_bak`·`zz_`·`pg_`로 시작하면 거부 | 백업 테이블을 도구로 고치거나 지우지 않는다 |
| K11 | 실행 기록은 서버 `~/ops-write/`(저장소 폴더 밖)에 남긴다. 실행 전에 `START` 줄을 먼저 쓴다 | 배포가 저장소 폴더를 초기화한다. 중간에 끊겨도 흔적이 남는다 |
| K12 | 운영 대상(컨테이너·DB·역할·경로)은 코드 상수다. **환경 변수·인자로 바꿀 수 없다.** 시험은 `main()`에 설정 객체를 주입한다. 구체적으로: ① 홈 폴더는 `HOME`이 아니라 계정 DB(`pwd.getpwuid(os.getuid()).pw_dir`)에서 얻는다(`pwd`가 없는 개발 PC에서만 `Path.home()`) ② 하위 프로세스에는 부모 환경을 물려주지 않고 고정 환경(`PATH=/usr/sbin:/usr/bin:/sbin:/bin`, `HOME=<계정 DB의 홈>`, `LANG=C.UTF-8`)만 준다 — `DOCKER_HOST`·`DOCKER_CONTEXT`가 docker에 닿지 않게 ③ 덤프의 나이는 파일 수정 시각(epoch)으로 잰다 — `TZ`에 따라 달라지는 이름의 시각 해석에 기대지 않는다. 이름의 시각은 **코드 상수 KST(+09:00)** 로 해석해 수정 시각과 맞는지만 본다(수정 시각 − 이름 시각이 0~10분) — 오래된 덤프를 `touch`해도 통과하지 못한다(검증 2차 N-L2) ④ docker는 `--context default`로 부른다(계정의 저장된 컨텍스트에 기대지 않는다) ⑤ 스크립트로 실행할 때는 `python3 -I`(격리 모드)여야 한다 — 아니면 사용법 오류로 끝낸다. `PYTHONPATH`나 같은 폴더의 `.py`가 표준 모듈을 가로채지 못하게 | 실행 경로에 "다른 곳을 가리키게 하는 손잡이"를 두지 않는다. 검증 1차 M1: `HOME`을 바꾸면 dry-run 기록·덤프 폴더·백업 로그가 전부 다른 곳을 가리켰고, `TZ`를 바꾸면 30분 창이 몇 시간 밀렸다 |
| K14 | **연쇄 쓰기가 일어날 수 있는 테이블은 거부한다.** 대상 테이블에 사용자 트리거·규칙·상속 자식이 있으면 실패. delete 단계는 그 테이블을 참조하는 FK 가운데 ON DELETE가 NO ACTION/RESTRICT가 아닌 것이 있으면, update 단계는 ON UPDATE가 그런 것이 있으면 실패 | 다른 테이블의 행이 따라 바뀌면 백업에도 건수 대조에도 안 잡힌다(검증 1차 M3). 지금 운영 스키마에는 해당 테이블이 없다(F10) — 생기면 그때 도구를 고친다. ctid는 테이블 하나 안에서만 유일하므로 상속 자식이 있으면 식별자 집합도 성립하지 않는다 |
| K13 | 표준 라이브러리만 쓴다(Python 3.11+, `tomllib`). 파일 하나 | 서버에 아무것도 설치하지 않는다 |

**위임(구현자가 정한다):** 함수 분해, 한국어 안내 문구, 출력 표의 모양, 시험 이름. 단 `SBW|…` 표지 줄(§4-4)과 로그 줄의 형식(§5)은 고정이다.

### 4-2. 작업 파일 (TOML)

```toml
defect = "D-999"                 # 필수, ^D-\d{1,5}$ → 백업 테이블 접두 bak_d999_
title  = "주문 3건 상태 정정"      # 필수, 한 줄, 120자 이내. 개인정보를 쓰지 않는다

[[step]]
kind   = "update"                # update | delete | insert
table  = "sb_order"              # ^[a-z][a-z0-9_]*$, 63바이트 이내, K10
where  = "id IN (101, 102, 103)" # update·delete 필수
set    = "status = 'CANCELED'"   # update 필수
from   = "…"                     # update·delete 선택 (UPDATE … FROM / DELETE … USING)
expect = 3                       # 필수, 정수 ≥ 1 (bool 거부)
backup = "order_status"          # 선택, ^[a-z0-9_]+$. 기본값 s{단계번호}_{table}

[[step]]
kind    = "insert"
table   = "sb_example"
columns = "a, b"                 # 선택, 식별자 목록만
source  = "VALUES (1, 2)"        # 필수, VALUES 또는 SELECT로 시작. ON CONFLICT DO NOTHING 가능
expect  = 1
```

- 모르는 키, 빠진 필수 키, 종류에 맞지 않는 키(예: insert의 `where`), 타입 불일치는 전부 거부한다(오타 `expct` 방지).
- 단계는 1~20개. 백업 테이블 이름은 `bak_d{번호}_{접미}`, 63바이트 이내, 작업 안에서 중복 금지.
- 작업의 정체는 **파일 바이트의 SHA-256**이다. 표시·`--confirm`에는 앞 12자, 로그에는 전체를 쓴다.

**조각 검사(K9)** — `where`·`set`·`from`·`source`에 적용한다. 작은따옴표 문자열(`''` 이스케이프)과 큰따옴표 식별자 안은 건너뛰고 그 밖에서:
- 거부: `;`, `--`, `/*`, `$`, 닫히지 않은 따옴표, 괄호 깊이가 음수가 되거나 0으로 끝나지 않음, 빈 조각.
- 큰따옴표 식별자 안에는 줄바꿈·탭을 쓸 수 없고 63바이트를 넘을 수 없다(서버의 "identifier will be truncated" NOTICE에 원문이 실려 표지 줄처럼 보이는 것을 막는다 — 검증 2차 N-L1).
- 어디서든 거부: 역슬래시, NUL 등 제어 문자(줄바꿈·탭은 허용).
- 금지어(단어 단위, 대소문자 무시): `insert update delete merge truncate drop alter create grant revoke into copy call execute commit rollback`. (`update`를 막으므로 `ON CONFLICT DO UPDATE`는 못 쓴다 — 갱신된 행의 백업이 없기 때문이다.)
- 괄호 깊이 0에서 추가 금지: `set`에는 `where from using returning`, `from`에는 `where returning`, `source`에는 `returning`.
- `source`의 첫 단어는 `values` 또는 `select`. `columns`는 `^[a-z_][a-z0-9_]*([ \t]*,[ \t]*[a-z_][a-z0-9_]*)*$`.
- 조각이 조립 뒤의 달러 인용 태그(`$sbw_<해시12>$`)를 포함하면 거부한다.

### 4-3. 조립되는 스크립트

`T`=테이블, `B`=백업 테이블, `E`=expect, `h`=작업 해시 앞 12자. 조각은 그대로 끼운다. `title`은 SQL에 넣지 않는다.

```sql
\set ON_ERROR_STOP on
BEGIN ISOLATION LEVEL REPEATABLE READ;
SET LOCAL lock_timeout = '5s';
SET LOCAL statement_timeout = '120s';
SET LOCAL search_path = public;
SET LOCAL client_min_messages = notice;
DO $sbw_h$
#variable_conflict use_column
DECLARE
  _sbw_n bigint;
  _sbw_est double precision;
  _sbw_bulk boolean := false;
  _sbw_tids tid[];
BEGIN
  -- (단계마다 아래 블록)
  IF _sbw_bulk AND NOT <BULK_OK> THEN RAISE EXCEPTION 'SBW|FAIL|phase=bulk'; END IF;
END
$sbw_h$;
COMMIT;                 -- dry-run이면 ROLLBACK;
\echo SBW|END|COMMIT    -- dry-run이면 SBW|END|ROLLBACK
```

`<BULK_OK>`는 dry-run이거나 `--bulk`가 있으면 `true`, 아니면 `false`.

단계 공통 머리(모든 종류):

```sql
IF to_regclass('public.T') IS NULL THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=table_missing'; END IF;
IF (SELECT c.relkind FROM pg_catalog.pg_class c WHERE c.oid = to_regclass('public.T')) <> 'r' THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=not_a_table'; END IF;
IF to_regclass('public.B') IS NOT NULL THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=backup_exists'; END IF;
IF EXISTS (SELECT 1 FROM pg_catalog.pg_inherits i WHERE i.inhparent = to_regclass('public.T')) THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=has_children'; END IF;
IF EXISTS (SELECT 1 FROM pg_catalog.pg_trigger g WHERE g.tgrelid = to_regclass('public.T') AND NOT g.tgisinternal) THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=has_trigger'; END IF;
IF EXISTS (SELECT 1 FROM pg_catalog.pg_rewrite w WHERE w.ev_class = to_regclass('public.T')) THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=has_rule'; END IF;
-- delete 단계만 (update 단계는 confdeltype 대신 confupdtype, insert 단계는 이 줄 없음):
IF EXISTS (SELECT 1 FROM pg_catalog.pg_constraint k WHERE k.contype = 'f' AND k.confrelid = to_regclass('public.T') AND k.confdeltype NOT IN ('a', 'r')) THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=cascade_fk'; END IF;
SELECT CASE WHEN c.reltuples >= 100000 THEN c.reltuples END INTO _sbw_est FROM pg_catalog.pg_class c WHERE c.oid = to_regclass('public.T');
IF _sbw_est IS NULL THEN SELECT count(*) INTO _sbw_est FROM public.T; END IF;
```

(행이 10만 미만이거나 통계가 없으면 정확히 세고, 그보다 크면 통계 추정치를 쓴다.)

update·delete 공통 — **조건은 여기서 한 번만 평가한다.** 대상 행의 ctid를 배열로 모으고, 백업과 변경은 그 배열로 한다:

```sql
SELECT array_agg(T.ctid) INTO _sbw_tids FROM public.T AS T[, <from>] WHERE (<where>);
_sbw_n := coalesce(cardinality(_sbw_tids), 0);
IF _sbw_n <> E THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=target|got=%|expect=E', _sbw_n; END IF;
CREATE TABLE public.B AS SELECT T.* FROM public.T AS T WHERE T.ctid = ANY (_sbw_tids);
SELECT count(*) INTO _sbw_n FROM public.B;
IF _sbw_n <> E THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=backup|got=%|expect=E', _sbw_n; END IF;
```

(`from` 조인이 대상 행을 불리면 배열에 같은 ctid가 여러 번 들어가 `phase=target`에서, `expect`를 불어난 수에 맞춰 적었더라도 `phase=backup`에서 걸린다.)

이어서 실행:

```sql
-- update, from 없음: 조건을 다시 평가하지 않는다
UPDATE public.T AS T SET <set> WHERE T.ctid = ANY (_sbw_tids);
-- update, from 있음: SET이 from의 값을 쓰려면 조인 조건이 필요하다. 대상은 배열 안으로 묶인다
UPDATE public.T AS T SET <set> FROM <from> WHERE (<where>) AND T.ctid = ANY (_sbw_tids);
-- delete (from 유무와 무관): 조건을 다시 평가하지 않는다
DELETE FROM public.T AS T WHERE T.ctid = ANY (_sbw_tids);

GET DIAGNOSTICS _sbw_n = ROW_COUNT;
IF _sbw_n <> E THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=affected|got=%|expect=E', _sbw_n; END IF;
```

from 있는 update에서 조건이 비결정이라 두 번째 평가가 다른 행을 고르면, 배열 밖의 행은 바뀌지 않고 영향 행 수가 모자라 `phase=affected`로 전체 롤백된다. 어느 경우든 **바뀐 행 ⊆ 백업한 행이고 건수가 같으므로 둘은 같다.**

insert(백업 테이블에는 **넣은 행**을 남긴다 — 되돌릴 때 지울 대상):

```sql
CREATE TABLE public.B (LIKE public.T);
WITH _sbw_ins AS (INSERT INTO public.T[ (<columns>)] <source> RETURNING *) INSERT INTO public.B SELECT * FROM _sbw_ins;
GET DIAGNOSTICS _sbw_n = ROW_COUNT;
IF _sbw_n <> E THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=affected|got=%|expect=E', _sbw_n; END IF;
SELECT count(*) INTO _sbw_n FROM public.B;
IF _sbw_n <> E THEN RAISE EXCEPTION 'SBW|FAIL|step=N|phase=backup|got=%|expect=E', _sbw_n; END IF;
```

단계 공통 꼬리:

```sql
IF E > 200 OR E > 0.05 * _sbw_est THEN _sbw_bulk := true; END IF;
RAISE NOTICE 'SBW|STEP|step=N|kind=K|table=T|rows=%|backup=B|est=%|bulk=%', _sbw_n, _sbw_est::bigint, (E > 200 OR E > 0.05 * _sbw_est)::int;
```

쓰기 뒤 확인 스크립트(별도 접속, `sbshop_ro`) — 백업 테이블마다:

```sql
DO $sbw_c$ DECLARE n bigint; BEGIN
  IF to_regclass('public.B') IS NULL THEN RAISE NOTICE 'SBW|CHECK|backup=B|exists=0';
  ELSE EXECUTE 'SELECT count(*) FROM public.B' INTO n; RAISE NOTICE 'SBW|CHECK|backup=B|exists=1|rows=%', n; END IF;
END $sbw_c$;
```

### 4-4. 명령과 판정

```
sbshop_db_write.py check   JOB      # 정적 검사 + 해시 + 조립된 SQL 출력. DB에 닿지 않는다
sbshop_db_write.py dry-run JOB      # 같은 트랜잭션을 실행하고 ROLLBACK
sbshop_db_write.py apply   JOB --confirm HASH12 [--bulk]
sbshop_db_write.py --version        # 도구 버전 + 자기 파일 SHA-256 앞 12자
```

`JOB`이 `-`이면 표준 입력에서 읽는다.

접속(상수): 쓰기 `/usr/bin/docker --context default exec -i projects-postgres-1 psql -X -U sbshop -d sbshop -v ON_ERROR_STOP=1 -f -`, 확인은 같은 줄에서 역할만 `sbshop_ro`. 실행은 `python3 -I ~/ops-write/sbshop_db_write.py …`(K12 ⑤). 스크립트는 표준 입력(UTF-8)으로 넘긴다. 하위 프로세스 제한 시간 300초(서버 쪽 120초보다 넉넉히 — 도구가 서버보다 먼저 포기하지 않게).

| 종료코드 | 뜻 |
|---------|----|
| 0 | OK |
| 1 | FAIL — 실행했으나 롤백됐거나 결과를 확신할 수 없음 |
| 2 | REFUSED — 정적 검사·선행 조건에서 거부. 쓰기 트랜잭션을 시작하지 않았다(사전 확인의 읽기 접속은 있을 수 있다) |
| 64 | 사용법 오류 |

**OK의 조건:** psql 종료코드 0 **이고** 표준 출력에 명령 태그 줄 `COMMIT`(dry-run은 `ROLLBACK`)과 `SBW|END|COMMIT`(dry-run은 `…|ROLLBACK`) 표지가 있고 **이고** 모든 단계의 `SBW|STEP` 표지가 있고 그 `rows`가 `expect`와 같다. apply는 추가로 확인 스크립트에서 모든 백업 테이블이 `exists=1`이고 `rows=expect`. 표지는 줄 전체가 맞아야 인정한다(줄 중간·부분 일치 불인정).

**"끝까지 실행됨"이 오류처럼 보이는 줄보다 우선한다.** psql 종료코드 0 + 명령 태그 + 끝 표지가 모두 있으면 스크립트는 끝까지 돈 것이다(`ON_ERROR_STOP`이라 서버 오류가 있었다면 종료코드 3으로 멈췄다). 이때 표준 오류의 `ERROR:`처럼 보이는 줄은 NOTICE 본문의 일부로 보고 실패 사유·`committed` 판정에 쓰지 않는다. 끝까지 실행되지 않았을 때만 아래 순서를 쓴다(검증 2차 N-L1 — 실제로 커밋됐는데 `committed=no`가 나오는 경로를 닫는다).

**apply가 OK가 아닐 때도 확인 스크립트를 돌려 `committed=yes|no|unknown`을 출력·기록한다.** 판정 순서(끝까지 실행됐으면 1을 건너뛴다):
1. 쓰기 스크립트에서 서버가 `ERROR`를 냈다(`SBW|FAIL` 표지든 다른 서버 오류든 — psql이 낸 `ERROR:` 줄) → `no`. 스크립트의 모든 문장은 트랜잭션 안이거나 `COMMIT` 자신이라, 서버 오류가 하나라도 있으면 이번 실행은 커밋되지 않았다. (같은 작업 둘이 동시에 돌아 뒤의 것이 "이미 있는 테이블" 오류로 끝난 경우도 여기서 `no`가 된다.)
2. 확인 스크립트가 실패했거나 읽을 수 없다 → `unknown`.
3. 백업 테이블이 전부 있다 → `yes`(사전 확인에서 하나도 없었고, 백업 테이블은 같은 트랜잭션에서 만들어진다).
4. 전부 없다 → psql이 **스스로 오류로 끝났을 때만**(시간 초과·실행 오류가 아니고 종료코드가 2 또는 3) `no`. 그 밖(시간 초과, 클라이언트 강제 종료, 종료코드 0·1·음수·기타)은 `unknown` — `docker exec` 클라이언트가 죽어도 컨테이너 안 psql은 남은 스크립트를 읽고 나중에 커밋할 수 있다(검증 1차 M2). 화면에 "최대 2분 뒤 다시 확인"을 안내한다.
5. 일부만 있다 → `unknown`.

**apply의 순서:** 읽기·정적 검사 → 대량 표시(`expect` 합 > 200인데 `--bulk` 없음) → `--confirm` → dry-run 기록 → 덤프 → 사전 확인(확인 스크립트: 실패하면 `check-unavailable`, 백업 테이블이 하나라도 있으면 `backup-exists`로 거부) → (작업 파일과 SQL을 `jobs/`에 보관, `START` 기록) → 실행 → 확인 → 결과 기록 → 화면 출력. 화면 출력이 끊겨도(`BrokenPipe`) 기록은 이미 남아 있어야 하고, 실행 뒤의 기록 실패가 결과 출력과 종료코드를 가리지 않아야 한다.

**덤프 조건(K7 ③):** `~/backups/daily/`에서 `^sbshop-(pre-)?[0-9]{8}-[0-9]{6}\.dump$` 가운데 이름의 날짜·시각 문자열이 가장 큰 것을 고른다(문자열 비교 — 시간대 해석 없음). 통과 조건은 그 파일의 **수정 시각이 지금보다 0~30분 전**이고(epoch 비교, 미래면 거부), **수정 시각이 이름의 시각(KST 고정 해석)보다 0~10분 늦고**, 크기 10MB 이상이고, `<그 이름>.sha256`이 있고, 백업 로그에 `OK kind=(pre|daily) file=<그 이름>` 줄이 있는 것. 수정 시각은 덤프가 끝난 때라 스냅샷 시점보다 1분쯤 늦다. 덤프를 도구가 대신 뜨지 않는다.

## 7. 실 DB 통합 시험 항목

1. update 정상: 값이 바뀌고 백업 테이블에 **바꾸기 전** 값이 `expect`행 있다.
2. dry-run: 값이 그대로이고 백업 테이블이 없다.
3. `expect`가 실제보다 작다/크다: 아무것도 안 바뀌고 백업 테이블이 없다. 표지에 `got`이 실제 건수.
4. 여러 단계 중 뒤 단계가 틀리면 앞 단계까지 전부 되돌아간다.
5. delete 정상 → 백업 테이블을 `source`로 한 insert 작업으로 **원래대로 돌아온다.**
6. update 정상 → 백업 테이블을 `from`으로 한 update 작업으로 **원래대로 돌아온다.**
7. insert 정상: 백업 테이블에 넣은 행이 있다. 유일 제약 위반이면 전체 롤백.
8. `from` 조인이 행을 불리면(중복 매칭) 거부된다.
9. 같은 작업을 두 번 apply하면 두 번째는 사전 확인에서 `backup-exists`로 거부되고(종료 2) 값은 한 번만 바뀐 상태다. 같은 작업의 dry-run은 서버 안 가드(`phase=backup_exists`)로 실패한다.
10. 대량: 5% 초과 단계는 `--bulk` 없이 실패(롤백), 있으면 성공. dry-run은 `bulk=1`을 보여 주고 통과.
11. 없는 테이블·뷰 대상·SQL 문법 오류 조각: 실패하고 흔적이 없다.
12. 다른 접속이 대상 행을 잠그고 있으면 `lock_timeout`으로 실패한다(5초).
13. 조각 안의 문자열에 `;`·`--`·한글이 들어 있어도 그대로 저장된다.
14. 확인 스크립트가 읽기 전용 역할로 백업 테이블 행 수를 읽는다.
15. 비결정 조건: `where = "id IN (SELECT id FROM T ORDER BY random() LIMIT 5)"`(from 없는 update, delete 각각)로 apply하면 OK이고 **바뀐(지워진) 행의 id 집합 = 백업 테이블의 id 집합**이다.
16. from 있는 update에 같은 비결정 조건: OK이면 바뀐 행 = 백업한 행, 아니면 `phase=affected`로 실패하고 흔적이 없다. 어느 쪽이든 "바뀌었는데 백업에 없는 행"은 0이다.
17. K14: ON DELETE CASCADE로 참조되는 테이블의 delete는 `cascade_fk`, ON UPDATE CASCADE로 참조되는 테이블의 update는 `cascade_fk`, 사용자 트리거가 있는 테이블은 `has_trigger`, 규칙이 있는 테이블은 `has_rule`, 상속 자식이 있는 테이블은 `has_children`으로 실패하고 흔적이 없다. NO ACTION FK로만 참조되는 테이블은 통과한다.
18. 조립 SQL의 `T.ctid = ANY (_sbw_tids)`가 PL/pgSQL 변수로 `CREATE TABLE … AS`·`UPDATE`·`DELETE`에서 동작한다(1·5번이 통과하면 확인된 것).

## 8. 등급과 운영 쓰기

- 코드: **중대**. 검증자는 운영 쓰기 도구 체크리스트(dry-run이 정말 쓰기를 건너뛰는가, 건수 상한이 실효인가, 재실행이 안전한가, 쓰기 응답과 반영 확인이 분리돼 있는가 등)를 이 설계서와 코드에 대입한다.
- 이 작업이 운영에 하는 쓰기는 둘이고 **각각 승인이 필요하다:**
  1. (통합 시험을 서버에서 돌릴 경우) 임시 DB `sbshop_dbwrite_test` 생성 → 시험 → 삭제. 운영 `sbshop` DB의 데이터·스키마는 건드리지 않는다. D-363 복구 연습과 같은 형태다.
  2. 설치: `~/ops-write/`(700) 생성, 도구 파일 복사, `--version`의 해시를 저장소 파일의 SHA-256과 대조. 되돌리기는 폴더 삭제.
- 도구의 첫 실제 사용은 별도의 운영 쓰기이고 그때 계획서·승인을 따로 받는다.

## 9. 멈춤 조건

- §2의 사실이 다르다(권한, 로그 형식, 경로).
- §4-3의 구문이 PostgreSQL 16에서 설계대로 동작하지 않는다 → 고쳐 쓰지 말고 보고한다(고정 결정 K3·K4에 닿는다).
- 고정 결정을 지키면서는 구현할 수 없는 항목이 나온다.
- 단위 시험이 Red 없이 처음부터 통과한다.

- 실 DB 통합 시험 18항목 통과(PostgreSQL 16).

## 11. 알려진 한계

- 조각 검사는 실수를 막는 장치다. 부작용이 있는 함수 호출(`setval`, `pg_terminate_backend`, 제한 시간을 바꾸는 `set_config` 등)까지 가려내지 않는다. 쓰기 역할이 앱과 같은 `sbshop`이라 그런 호출은 앱 접속에도 닿는다.
- DB 수준 이벤트 트리거(DDL에 반응)는 가드가 보지 않는다. 지금은 0개다(F12).
- dry-run 성공 기록에는 유효 기간이 없다. apply가 건수를 다시 대조하므로 오래된 dry-run으로 틀린 쓰기가 나가지는 않는다.
- 되돌리기 작업의 한계: 여러 단계 작업은 **역순으로** 되돌린다. IDENTITY ALWAYS·GENERATED 열이 있는 테이블은 `SELECT *` 되돌리기 insert가 안 된다(지금 운영에는 그런 열이 없다 — F10).
- 도구는 다른 쓰기 경로(스케줄러·소싱처 배치)를 멈추지 않는다. 대상 행을 다른 경로가 다시 쓰는지는 실행 계획서에서 사람이 확인한다(README 절차에 넣는다). 실행 중 겹치면 직렬화 오류·잠금 시간 초과로 전체 롤백된다.
- 덤프와 쓰기 사이(최대 30분)에 들어온 다른 변경은 덤프 복원으로 돌아오지 않는다. 방금 바꾼 행은 백업 테이블이 돌려준다.
- 마켓에 이미 나간 값은 DB를 되돌려도 돌아오지 않는다.
- 작은 테이블에서는 한 행도 5%를 넘어 대량이 된다(정책 테이블 5~6행). 규칙을 글자 그대로 적용한 결과이고, 그런 테이블의 한 줄은 실제로 영향이 크다.
- dry-run도 대상 행을 잠깐 잠그고(롤백까지), insert 단계는 시퀀스 번호를 소모한다(시퀀스는 롤백되지 않는다). 데이터는 남지 않는다.
- CI는 이 폴더의 시험을 돌리지 않는다(F8). 워크플로 수정은 업무 범위 밖이라 사용자 결정이 필요하다.
