# 배포 구조 딥다이브 — 지금 우리가 하는 방식과, 가야 할 정석

작성 2026-09-19. 배포기 이중화 사고(GitHub Actions ↔ 웹훅 충돌)를 계기로 정리했다.
**목표: 초보자도 "왜 이렇게 하는지"까지 이해하고, 앞으로 뭘 바꿀지 판단할 수 있게 한다.**

---

## 0. 먼저, 배포가 뭔가

우리가 맥에서 코드를 고친다. 그 코드가 **오라클 서버(168.107.31.154)에서 24시간 도는 프로그램**이 되어야 사장님과 직원이 쓸 수 있다. 그 "옮기고 갈아끼우는 일" 전부가 배포다.

우리 시스템은 이렇게 돈다.

```
[맥: 코드 수정]
      │ git push
      ▼
[GitHub: 코드 보관소]
      │ (누군가 서버에 알려줘야 함)
      ▼
[오라클 서버]
   ├─ 코드 내려받기 (git pull)
   ├─ 빌드 (자바 → 실행 가능한 jar → 도커 이미지)
   ├─ 옛 컨테이너 끄기 / 새 컨테이너 켜기
   └─ nginx 재적용
```

## 1. 용어 10개 — 이것만 알면 나머지가 읽힌다

| 용어 | 쉬운 뜻 | 우리 예 |
|---|---|---|
| **이미지(image)** | 프로그램 + 실행에 필요한 모든 것을 한 덩어리로 구운 **붕어빵 틀** | `sbshop-agent-sbshop-api:latest` |
| **컨테이너(container)** | 그 틀로 찍어낸 **붕어빵 하나**. 실제로 도는 프로세스 | `projects-sbshop-api-1` |
| **빌드(build)** | 소스코드로 이미지를 굽는 일. 우리는 2~3분 걸린다 | `docker compose build` |
| **레지스트리(registry)** | 이미지를 보관·배포하는 **창고**. GitHub는 GHCR을 준다 | 지금 **안 쓴다** |
| **태그(tag)** | 이미지에 붙이는 이름표. `latest`는 "가장 최근"이라 롤백에 쓸모없다 | 지금 전부 `latest` |
| **CI** | Continuous Integration. push하면 자동으로 **빌드·테스트**해주는 것 | GitHub Actions |
| **CD** | Continuous Deployment. 그걸 **서버에 배포**까지 해주는 것 | 우리 `deploy.yml` |
| **롤백(rollback)** | 배포가 잘못됐을 때 **직전 버전으로 되돌리기** | 지금은 "옛 커밋으로 되돌려 재빌드"뿐 |
| **헬스체크** | 새로 띄운 게 진짜 살아있는지 **확인 사격** | Actions에만 있음 |
| **무중단 배포** | 서비스를 끊지 않고 갈아끼우기 | 지금은 **끊긴다**(수 초~수십 초) |

## 2. 지금 우리 구조 — 정확히 어떻게 돌아가는가

### 2-1. 배포를 시작시키는 길이 **둘**이다 (이게 사고의 원인)

```
git push origin main
   │
   ├──────────────► ① GitHub Actions (.github/workflows/deploy.yml)
   │                    GitHub 서버 → SSH → 우리 서버
   │                    docker compose up -d --build
   │
   └──────────────► ② 웹훅 (서버의 canagent-webhook.service, 9000포트)
                        GitHub가 우리 서버를 직접 호출
                        → /home/ubuntu/webhook/deploy-sbshop.sh 실행
```

**둘 다 같은 서버에서 같은 컨테이너를 건드린다.** 2026-09-19에 웹훅을 되살리면서 둘이 동시에 돌기 시작했고, 한쪽이 컨테이너를 지우는 사이 다른 쪽이 만들려다 실패했다.

```
Error response from daemon: removal of container 5c059c02... is already in progress
```

### 2-2. ① GitHub Actions가 하는 일

`.github/workflows/deploy.yml`:

1. GitHub가 빌려주는 임시 리눅스(`ubuntu-latest`)를 켠다
2. 저장소 시크릿 `SBSHOP_DEPLOY_KEY`(SSH 개인키)로 우리 서버에 접속
3. 서버에서 `git pull` → 디스크 10GiB 여유 확인 → `docker compose up -d --build` → nginx reload
4. 밖에서 `https://…/sbshop-agent/`를 최대 2분간 찔러 200이 뜨는지 확인(헬스체크)

**좋은 점**: 배포 이력이 GitHub에 남고, 실패하면 **메일이 온다**. 시크릿 관리가 깔끔하다. 디스크 가드·잠금(flock)이 있다.

**나쁜 점**: `docker compose up -d --build`가 **모든 서비스**(api·frontend·scraper)를 건드린다. 그리고 다음 항목의 함정에 걸린다.

### 2-3. ② 웹훅이 하는 일

서버에서 파이썬 리스너가 9000포트를 열고 기다린다(`deploy.py`).

- GitHub가 보낸 서명(`X-Hub-Signature-256`)을 검증 → 위조 요청은 403
- `main` 브랜치 push만, **`.md`·`docs/`만 바뀐 push는 건너뜀**
- 조건을 통과하면 `/home/ubuntu/webhook/deploy-sbshop.sh` 실행

그 스크립트는 **이름충돌을 피하도록 특별히 만들어졌다**:

```bash
docker compose build sbshop-api sbshop-frontend     # 1) 먼저 굽는다 (실패해도 옛 컨테이너 유지)
docker rm -f projects-sbshop-api-1 …                # 2) 옛 컨테이너를 확실히 제거
docker compose up -d --no-build sbshop-api …        # 3) 그다음 새로 띄운다
docker exec projects-nginx-1 nginx -s reload        # 4) nginx가 옛 IP를 캐시하므로 재적용
```

**좋은 점**: 빌드 실패 시 기존 서비스가 그대로 살아있다. 이름충돌을 원천 차단한다. push 1초 뒤 시작해 96초에 끝난다.

**나쁜 점**: 실패해도 **아무도 모른다**(알림 없음). 이력이 서버 로그 파일뿐. 9000포트를 인터넷에 열어야 한다. 시크릿이 systemd 유닛 파일에 평문으로 있다.

### 2-4. 왜 "이름충돌"이 자꾸 나는가 — 핵심 함정

`docker-compose.yml`에 이렇게 써 있다.

```yaml
sbshop-api:
  container_name: projects-sbshop-api-1   # ← 이름을 못 박았다
```

도커 컴포즈는 원래 컨테이너 이름을 알아서 관리한다(`프로젝트_서비스_번호`). 그런데 **이름을 못 박으면** 컴포즈가 "옛것을 임시 이름으로 바꿔두고 새것을 만드는" 안전한 교체를 못 한다. 그래서 옛것이 완전히 사라지기 전에 새것을 만들려다 이렇게 죽는다.

```
Conflict. The container name "/projects-sbshop-scraper-1" is already in use
```

2026-09-19 03:27 Actions 실패가 정확히 이것이다. **웹훅과 무관하게, Actions 혼자서도 터졌다.**

### 2-5. 실제로 터진 사고들 (2026-09-19 하루치)

| 시각 | 무엇이 | 왜 |
|---|---|---|
| 02:08 | Actions 실패 | 프론트 `npm install` 실패 — 이미지가 Node 20인데 vitest가 Node 22+ 요구 |
| 03:27 | Actions 실패 | 컨테이너 **이름충돌**(scraper) — 2-4의 함정 |
| 07:57 | Actions 실패 | 웹훅과 **동시 실행** 충돌 |
| 11:33 | Actions 실패 | 같은 이유 |

웹훅 쪽은 같은 시각 전부 성공했다. **배포 방식 자체는 웹훅 스크립트가 더 안전하고, 운영 편의(이력·알림)는 Actions가 낫다.**

## 3. 지금 구조의 진짜 문제 — 5가지

### ① 배포기가 둘이다
가장 급한 문제. 같은 자원을 두 주체가 동시에 건드리면 반드시 깨진다. **하나로 줄여야 한다.**

### ② 운영 서버에서 빌드한다 ← 근본 문제
지금은 서버가 직접 소스를 받아 자바를 컴파일하고 이미지를 굽는다. 그래서:

- **운영 서버 CPU·디스크를 빌드가 먹는다.** 그래서 워크플로에 "10GiB 여유 없으면 중단" 가드가 붙어 있고, 과거에 디스크가 차서 배포가 깨진 적이 있다.
- **빌드가 실패하면 그때서야 안다.** 이미 서버에 들어와서 하는 일이라 되돌리기도 번거롭다.
- **느리다.** 2~3분. 급할 때 뼈아프다.

### ③ 롤백이 사실상 없다
모든 이미지가 `latest` 하나다. "어제 잘 돌던 그 이미지"가 남아 있지 않다. 되돌리려면 옛 커밋으로 되돌려 **다시 빌드**해야 한다 — 또 2~3분, 그리고 그 사이 장애는 계속된다.

### ④ 배포할 때 서비스가 끊긴다
옛 컨테이너를 지우고 새것을 띄운다. 부팅에 약 16초. 그동안 요청은 실패한다. 더 중요한 건 — **도는 배치가 죽는다.** (소싱처 가격·재고 배치가 몇 시간짜리라 배포 한 번에 통째로 날아간다.)

### ⑤ 실패를 조용히 넘어갈 수 있다
웹훅 경로는 실패해도 알림이 없다. "배포됐겠지" 하고 넘어가면 옛 코드가 계속 도는데 아무도 모른다.

## 4. 정석 방식 — 3단계로 올라가기

한 번에 다 바꿀 필요 없다. **단계마다 그 자체로 이득이 있다.**

### 1단계: 배포기를 하나로 (오늘 할 일, 30분)

**GitHub Actions만 남기고, Actions가 서버의 안전 스크립트를 부르게 한다.**

```yaml
# 지금
docker compose up -d --build        # ← 이름충돌 함정

# 바꿀 것
/home/ubuntu/webhook/deploy-sbshop.sh   # ← 이미 검증된 안전 스크립트
```

- 웹훅(9000포트·systemd 서비스)은 끈다 → 충돌 사라짐, 포트 닫힘
- Actions의 **이력·실패 메일·시크릿 관리**는 유지
- 스크립트의 **이름충돌 회피·빌드 선행**도 유지

얻는 것: 실패 메일이 멈추고(진짜 실패할 때만 옴), 03:27류 이름충돌도 사라진다.

### 2단계: 빌드와 배포를 분리 (레지스트리 도입) ← **여기가 "세련된 정석"**

```
지금:   push → 서버가 소스 받아서 빌드 → 띄움
정석:   push → GitHub가 빌드 → 창고(GHCR)에 이미지 올림 → 서버는 받아서 교체만
```

```
[GitHub Actions]
   ├─ 테스트 실행 (실패하면 여기서 멈춤 — 서버는 건드리지도 않음)
   ├─ 이미지 빌드
   └─ ghcr.io/goottjason/sbshop-api:2026-09-19-a1b2c3d 로 push
                          │
                          ▼
[오라클 서버]  docker compose pull && up -d   ← 빌드 없음, 20초면 끝
```

이게 왜 훨씬 나은가:

- **서버가 빌드를 안 한다.** CPU·디스크 걱정이 사라지고 디스크 가드도 필요 없어진다.
- **배포가 빨라진다.** 2~3분 → 20~30초.
- **롤백이 한 줄이 된다.** `:2026-09-18-...` 태그로 바꿔 다시 올리면 끝. 재빌드 없음.
- **테스트를 먼저 통과시킬 수 있다.** 지금은 테스트와 배포가 따로 놀지만, 정석은 "테스트 통과 → 그다음 배포"다. 깨진 코드가 서버에 못 들어간다.
- **커밋마다 이미지가 남는다.** "언제 뭐가 배포됐는지"가 태그로 증명된다.

바뀌어야 할 것: `docker-compose.yml`이 `build:` 대신 `image: ghcr.io/...:태그`를 보게 하고, 서버에 GHCR 로그인(읽기 전용 토큰)을 한 번 해두면 된다.

### 3단계: 끊김 없애기·자동 롤백 (나중에, 필요해지면)

- **헬스체크 후 교체**: 새 컨테이너를 띄우고 "정상"이 확인된 뒤에 옛것을 내린다. 그때까지 옛것이 요청을 받는다 → **끊김 0**.
- **자동 롤백**: 헬스체크가 실패하면 새것을 버리고 옛 태그로 되돌린다.
- **배치 보호**: 도는 배치가 있으면 배포를 미룬다(지금은 사람이 기억해서 피하고 있다).

여기까지 오면 "배포 때문에 조마조마할 일"이 거의 없어진다. 다만 손이 더 가니 2단계를 먼저 하고 판단하면 된다.

## 5. 우리 프로젝트에만 있는 제약 — 정석을 그대로 못 따르는 부분

정석 문서에 안 나오는, 우리 사정이다.

| 제약 | 내용 | 배포에 주는 영향 |
|---|---|---|
| **배치가 길다** | 소싱처 가격·재고 배치가 수백~수천 상품, 몇 시간짜리 | **배포 = 컨테이너 재시작 = 배치 중단.** 배치 중에는 배포하면 안 된다 |
| **스키마 수동 관리** | Flyway를 뺐고 운영 DB가 스키마 단일 원본 | 엔티티에 컬럼을 더하면 **배포 전에 사람이 DDL을 먼저 적용**해야 한다. 안 그러면 앱은 뜨는데 조회가 500 난다 |
| **단일 JVM** | worker가 api에 합쳐져 컨테이너 하나 | 스케줄러·이메일 수집이 전부 같이 죽었다 살아난다 |
| **마켓 API 쓰기** | 배포가 잘못되면 마켓에 잘못된 값이 나간다 | 롤백 속도가 중요하다 — 2단계의 실익이 큰 이유 |

## 6. 자주 하는 오해

**"서버 저장소가 최신 커밋이면 배포된 것이다"** → 아니다. `git pull`은 빌드보다 먼저 끝난다. 빌드가 실패해도 저장소만 최신이고 컨테이너는 옛것이다. **컨테이너 생성 시각이 커밋 시각보다 뒤인지**를 봐야 한다.

**"`Started ApiApplication`이 찍혔으면 성공이다"** → 아니다. 스키마가 안 맞아도 앱은 뜬다. 실제 조회를 한 번 해봐야 한다.

**"헬스체크 200이면 새 코드다"** → 아니다. 옛 컨테이너가 200을 줄 수도 있다. 이번에도 빌드가 캐시로 3초 만에 끝나 의심스러워, 컨테이너 안 jar에서 새 코드의 문자열을 직접 찾아 확인했다.

## 7. 이행 계획 요약

| 단계 | 할 일 | 파일 | 효과 | 난이도 |
|---|---|---|---|---|
| **1** | 웹훅 끄고 Actions가 안전 스크립트 호출 | `.github/workflows/deploy.yml`, 서버 systemd, CLAUDE.md | 실패 메일 멈춤, 이름충돌 해소 | 낮음 |
| **2** | 레지스트리(GHCR) 도입, 서버는 pull만 | `deploy.yml`, `docker-compose.yml`, 서버 GHCR 로그인 | 배포 20초, **롤백 한 줄**, 서버 빌드 부담 0 | 중간 |
| **3** | 헬스체크 후 교체 + 자동 롤백 + 배치 가드 | compose, 배포 스크립트 | 무중단, 사고 자동 복구 | 높음 |

권장: **1단계는 지금, 2단계는 가까운 시일에.** 3단계는 2단계를 써보고 필요를 느낄 때.
